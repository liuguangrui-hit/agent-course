4.3 结果展示

课后深入，约 45 分钟。

早上打开结果页，看到完成了十轮。你下一步要做什么？页面需要把值得行动的信息摆出来，并让每项判断能追回原件。

首页内容与状态

最上方写当前主要问题的结论，执行状态和下一步。下面列出每轮结果与审阅判定，再给通往预测，原始数据和运行身份的入口。

运行失败，分析待核，科学负结果分别显示。一次任务尚在执行，不能算进已完成实验的分母；审查退修保留在总表里，不能因为没有通过就消失。

从结构化记录生成

页面由文件生成，指标定义与代码版本一起保存。尽量让状态和数字来自结构化字段，审阅结论也保留单独判定，减少从自由文本猜状态。

读全部轮次的执行记录与结果，生成本地结果页。
校验运行编号唯一，预测与结果一一对应，完成轮次存在预期产物。
分别统计执行成功率、审查通过率和主要研究指标，逐项写分母。
缺失字段显示待核，并生成错误清单。

现有 make_page.py 可展示完整记录。先看它读取哪些字段，再决定怎样接到自己的运行器。页面生成成功后，抽一个值回查源记录。

公开字段的选择

研究问题、预测和对错本身，也可能透露未发表成果。内部页可以完整展示，公开页先由你选哪些字段可发布。默认公开页面的访问范围与仓库可见性分别核对。

把已批准公开的投影单独保存，由生成器只读这份投影。每次发布前比较新增字段，避免内部模板更新后带出额外内容。

发布有自己的完成条件

本地构建完成，生成文件已经存在；远端上传成功，服务器收到了文件；部署成功，线上服务已经更新；打开页面核验，才看到了实际版本。把这些状态分开记录。

页面可以带短版本标识和生成时间，便于核对缓存。发布失败时从失败步骤继续，同一轮结果仍引用同一份记录。

通知内容与后续操作

通知回答完成还是卡住，哪个问题改变了判断，点哪里继续。长日志留在运行目录，通知只链接到需要看的位置。

通知渠道使用已配置的认证和访问控制。把随机频道名当作唯一保护，很难知道谁能订阅或发布。先做测试，再按研究内容决定通知粒度。

练习

给生成器放入三轮：一轮成功，一轮执行失败，一轮完成但审查退修。检查汇总和分母，再故意移走一份结果文件，确认页面显示待核。最后为同一记录生成一份你愿意公开的投影。

常见错误与处理方法

汇总率只算成功案例。 定义分母，失败和待核保留状态。

公开页没有数字就默认安全。 问题和预测也要逐字段确认公开范围。

推送完成就宣布发布成功。 核对部署状态，再打开实际页面确认版本。

参考 GitHub Pages 文档 与 ntfy 文档。

4.3 Presenting results

After-class deep dive, about 45 minutes.

In the morning you open the results page and see that ten rounds finished. What do you do next? The page has to lay out the information worth acting on, and let every judgment trace back to the originals.

Lead with the current conclusion and status

At the top, write the conclusion on the current main question, the execution status and the next step. Below, list each round’s results and review verdict, then link to the predictions, raw data and run identities.

Show failed runs, analyses pending checks and negative scientific results separately. A task still running cannot count in the denominator of completed experiments; a review that returned the work for revision stays in the master table and does not vanish because it did not pass.

Generate from structured records

The page is generated from files, and metric definitions are saved with the code version. Let states and numbers come from structured fields wherever possible, and keep review conclusions as separate verdicts, to reduce guessing states from free text.

Read the execution records and results of all rounds and generate a local results page.
Check that run IDs are unique, predictions and results correspond one to one, and completed rounds have their expected products.
Count the execution success rate, the review pass rate and the main research metrics separately, writing the denominator for each.
Show missing fields as pending checks, and generate an error list.

The existing make_page.py can display the complete record. First see which fields it reads, then decide how to connect it to your own runner. Once the page is generated, take one value back to its source record.

Decide what is public field by field

Research questions, predictions and whether they were right can themselves reveal unpublished results. The internal page can show everything; for the public page, you first choose which fields may be published. Check the access scope of the default public page and the repository’s visibility separately.

Save the projection approved for publication on its own, and have the generator read only this projection. Before each publication, compare newly added fields, so updates to the internal template do not expose additional content.

Publishing has its own completion conditions

When the local build is done, the generated files exist; when the remote upload succeeds, the server has received the files; when deployment succeeds, the online service has been updated; only when you open the page and check do you see the actual version. Record these states separately.

The page can carry a short version tag and generation time, to help detect stale cached pages. When publishing fails, continue from the failed step, and the same round’s results still refer to the same record.

Make notifications actionable

A notification answers whether something finished or got stuck, which research question has an updated conclusion, and where to click to continue. Long logs stay in the run directory; the notification only links to the place that needs looking at.

Notification channels use configured authentication and access control. If a random channel name is the only protection, it is hard to know who can subscribe or post. Test first, then decide how fine-grained notifications should be according to the research content.

Exercise

Give the generator three rounds: one success, one execution failure, and one completed but returned for revision. Check the summary and denominators, then deliberately remove one result file and confirm the page shows a pending check. Finally, generate from the same record a public view containing only the fields you would share.

Common mistakes and how to fix them

Computing summary rates from successful cases only. Define the denominator, and keep the status of failures and pending checks.

Assuming the public page is safe because it has no numbers. Questions and predictions also need their public scope confirmed field by field.

Declaring publication successful once the push is done. Check the deployment status, then open the actual page to confirm the version.

See the GitHub Pages docs and the ntfy docs.
