4.3 结果展示

学习目标

  1. 设计由结构化记录生成的结果页，使执行失败、待核、科学负结果与审阅退修分别呈现，并为每项汇总写明分母。
  2. 区分内部记录与公开投影，逐字段评估公开范围。
  3. 区分构建、上传、部署与线上核验等发布状态，并据此设计通知内容。

课后深入专题，约 45 分钟。

结果页显示已完成十轮，读者接下来应该做什么？结果页需要呈现可据以行动的信息，并使每项判断都能追溯到原件。

首页内容与状态

页面最上方写明当前主要问题的结论、执行状态和下一步工作。其下列出每轮结果与审阅判定，并提供通往预测、原始数据和运行身份的入口。

运行失败、分析待核与科学负结果分别显示。尚在执行的任务不计入已完成实验的分母；审阅退修的轮次保留在总表中，不能因未通过而消失。

由结构化记录生成

页面由文件生成，指标定义与代码版本一并保存。状态和数字尽量来自结构化字段，审阅结论也单独保存判定，以减少从自由文本中推测状态。

读全部轮次的执行记录与结果，生成本地结果页。
校验运行编号唯一，预测与结果一一对应，完成轮次存在预期产物。
分别统计执行成功率、审查通过率和主要研究指标，逐项写分母。
缺失字段显示待核，并生成错误清单。

现有的 make_page.py 可以展示完整记录。先查看它读取哪些字段，再决定怎样接入自己的运行器。页面生成后，抽取一个数值回查源记录。

公开字段的选择

研究问题、预测及其正误本身也可能透露未发表的成果。内部页可以完整展示，公开页则由研究者逐项选择可发布的字段。公开页面的访问范围与仓库可见性须分别核对。

已批准公开的投影单独保存，生成器只读取这份投影。每次发布前比较新增字段，避免内部模板更新后带出额外内容。

发布的完成条件

本地构建完成，说明生成文件已经存在；远端上传成功，说明服务器收到了文件；部署成功，说明线上服务已经更新；打开页面核验，才能确认看到的是实际版本。这些状态应分别记录。

页面可以带有简短的版本标识和生成时间，便于核对缓存。发布失败时从失败步骤继续，同一轮结果仍引用同一份记录。

通知内容与后续操作

通知应回答三件事：任务完成还是受阻，哪个问题的判断发生了变化，从哪里继续处理。长日志保留在运行目录，通知只链接到需要查看的位置。

通知渠道使用已配置的认证和访问控制。若只依靠随机频道名保护，很难确定谁能订阅或发布。先做测试，再根据研究内容确定通知粒度。

练习

为生成器提供三轮记录：一轮成功，一轮执行失败，一轮完成但审阅退修。检查汇总值和分母，再故意移走一份结果文件，确认页面显示待核。最后为同一记录生成一份愿意公开的投影。

常见错误与处理方法

汇总比率只统计成功案例。 明确定义分母，失败与待核轮次保留状态。

公开页没有数字即默认安全。 问题和预测也须逐字段确认公开范围。

推送完成即宣布发布成功。 核对部署状态，再打开实际页面确认版本。

参考资料：GitHub Pages 文档 与 ntfy 文档。

4.3 Presenting results

Learning outcomes

After this section, students should be able to:

  1. Design a results summary generated from structured records, with explicit denominators and with failures, pending checks and negative results shown separately.
  2. Decide field by field which research information may be made public, and keep the public view consistent with that decision.
  3. Distinguish the completion conditions of building, uploading, deploying and verifying a publication, and design notifications that point to the information requiring action.

Extension reading and exercises, about 45 minutes.

A results page is read in order to decide what to do next. A statement that ten rounds have finished does not support that decision. The page has to present the information on which action depends and allow every judgment to be traced back to the original records.

Leading with the current conclusion and status

The top of the page states the conclusion on the current main question, the execution status and the next step. Below this, each round’s results and review verdict are listed, with links to the predictions, raw data and run identities.

Failed runs, analyses pending checks and negative scientific results are shown separately. A task still running cannot be counted in the denominator of completed experiments; a review that returned the work for revision remains in the master table and does not disappear because it did not pass.

Generating the page from structured records

The page is generated from files, and metric definitions are saved with the code version. States and numbers come from structured fields wherever possible, and review conclusions are kept as separate verdicts, to reduce inference of states from free text.

Read the execution records and results of all rounds and generate a local results page.
Check that run IDs are unique, predictions and results correspond one to one, and completed rounds have their expected products.
Count the execution success rate, the review pass rate and the main research metrics separately, writing the denominator for each.
Show missing fields as pending checks, and generate an error list.

The existing make_page.py can display the complete record. First establish which fields it reads, then decide how to connect it to your own runner. Once the page is generated, trace one value back to its source record.

Deciding field by field what is public

Research questions, predictions and whether they were correct can themselves reveal unpublished results. The internal page can show everything; for the public page, the fields that may be published are chosen first. The access scope of the default public page and the visibility of the repository are checked separately.

The projection approved for publication is saved on its own, and the generator reads only this projection. Before each publication, newly added fields are compared, so that changes to the internal template do not expose additional content.

Publication has its own completion conditions

When the local build is complete, the generated files exist; when the remote upload succeeds, the server has received the files; when deployment succeeds, the online service has been updated; only opening and checking the page shows the version actually served. These states are recorded separately.

The page can carry a short version tag and generation time to help detect stale cached pages. When publication fails, it resumes from the failed step, and the results of the same round still refer to the same record.

Actionable notifications

A notification states whether something finished or stalled, which research question has an updated conclusion, and where to continue. Long logs remain in the run directory; the notification only links to the place that requires attention.

Notification channels use configured authentication and access control. If a random channel name is the only protection, it is difficult to know who can subscribe or post. Test first, and then decide how detailed notifications should be according to the research content.

Exercise

Give the generator three rounds: one success, one execution failure, and one completed but returned for revision. Check the summary and denominators, then deliberately remove one result file and confirm that the page shows a pending check. Finally, generate from the same record a public view containing only the fields you would share.

Common errors and corrections

Computing summary rates from successful cases only. Define the denominator, and retain the status of failures and pending checks.

Assuming that a public page without numbers is safe. Questions and predictions also require their public scope to be confirmed field by field.

Treating a completed push as a successful publication. Check the deployment status, then open the actual page to confirm the version.

See the GitHub Pages docs and the ntfy docs.
