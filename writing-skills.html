1.5 经验留档

课后深入，约 25 分钟。

第二次改论文时，如果还要完整重复上次的要求，说明经验尚未形成可调用的方法。找出反复有效的判断，将它们保存为后续任务能加载的约定或 Skill。

稳定约定与可调用方法

项目约定写每次都适用的事：原件放在哪里，编译入口是什么，哪些数据不能覆盖。Skill 写只在某类任务中使用的方法：怎样分析范文，怎样从数据核对到整稿重讲，交给谁审。

位置 放什么 什么时候读
本次任务卡 当前材料和交付位置 开始这件事时
AGENTS.md 稳定的工程约定 项目开工时
SKILL.md 及附件 完整方法、模板与脚本入口 命中相应任务时
运行记录 这一次发生了什么 复现或复盘时

每次增加约定前先删重。反复出现的问题，优先看能否修进生成脚本或检查器。

提炼可复用方法

回顾这次改稿的产物和我的纠正，提炼 paper-retell Skill。
说明输入与适用任务，再列出关键判断、需要调用的脚本及交付条件。
把本次论文的专用配置留在项目里，Skill 使用相对路径。

入口至少有名称与描述：

---
name: paper-retell
description: Retell a complete research paper around its central finding, verify results against data, and hand the new version to an independent editorial reader.
---

描述影响 Skill 在哪些任务中被发现。正文再解释方法，附件提供表达表和脚本。对于只改一句话的请求，Skill 应能判断无需启动全文流程。

两家共用时检查入口

Claude Code 使用自己的 CLAUDE.md 入口，可用 @AGENTS.md 导入共用约定。Skill 通常放在项目 .claude/skills/；Codex 的项目技能可放在 .agents/skills/。用户级目录按各自当前文档配置，避免从旧文章照抄。

同一份内容可以链接或复制到各入口。复制时写明哪一份是维护源，每次改动同步。是否发现并加载，用新会话验证。具体入口见 Claude Code Skills 与 Codex Skills。

三次测试，判断能不能复用

第一篇用刚完成的稿子，检查 Skill 能否被调用。第二篇换一份结构相似的材料，检查是否还依赖第一篇的隐含信息。第三次只给摘要编辑任务，检查它能否选择合适的工作量。

再记录一次失败。若 Skill 跳过核数，先查入口是否实际加载，再查脚本路径和停止条件。把失败原因修到对应位置，不要一再追加务必遵守之类的叮嘱。

练习

把参考答案中的 skills/paper-retell 装到自己的练习项目，新开会话完成三次测试。每次只记录触发结果、调用文件与缺失环节。比较修改前后，留下能迁移的最小版本。

常见错误与处理方法

把整段聊天存成 Skill。 读者不知道哪些是方法，哪些只是这次的决定。提炼输入和判断，运行过程另存。

Skill 写死这台电脑的路径。 换项目就失败。路径相对于项目或 Skill 文件夹，机器信息由配置提供。

内容写得完整，却从未在新会话调用。 新会话实测入口，再换材料测方法。两项分别通过才算可复用。

1.5 Reusable methods

After-class deep dive, about 25 minutes.

If on your second paper revision you have to state every requirement from the first time again, that experience has not yet become a tool. First find the judgments that kept working, then save them where the next session can find them.

Stable conventions and callable methods

Project conventions record what applies every time: where originals live, how to compile the paper, which data must not be overwritten. A Skill records methods used only for a certain kind of task: how to analyze an exemplar, how to check data and restructure the full draft, whom to hand it to for review.

Location What goes there When it is read
This task card Current materials and delivery location When starting this piece of work
AGENTS.md Stable engineering conventions When work on the project starts
SKILL.md and attachments The full method, templates and script entry points When a matching task comes up
Run record What happened this time When reproducing or reviewing

Before adding a convention, remove duplicates first. For a problem that keeps recurring, first see whether it can be fixed in the generation script or the checker.

Extract a reusable method

Look back over the products of this revision and my corrections, and distill a paper-retell Skill.
State its inputs, the tasks it applies to, the key judgments, the scripts to call and the delivery conditions.
Leave the configuration specific to this paper in the project, and use relative paths in the Skill.

The Skill needs at least a name and a description:

---
name: paper-retell
description: Retell a complete research paper around its central finding, verify results against data, and hand the new version to an independent editorial reader.
---

The description helps the agent discover the Skill for relevant tasks. The body then explains the method, and attachments provide the style table and scripts. For a request to change one sentence, the Skill should be able to judge that the full-paper process is not needed.

Check the entry points when both vendors share it

Claude Code uses its own CLAUDE.md entry and can import shared conventions with @AGENTS.md. Skills usually go in the project’s .claude/skills/; Codex project skills can go in .agents/skills/. Configure user-level directories according to each vendor’s current docs, rather than copying from old articles.

The same content can be linked or copied to each entry point. When copying, state which copy is the maintained source and sync every change. Check in a new session that the agent discovers and loads it. For specific entry points, see Claude Code Skills and Codex Skills.

Three tests to judge whether it can be reused

The first uses the draft you just finished, to check that the Skill can be called. The second switches to material with a similar structure, to check whether it still relies on hidden information from the first. The third gives only an abstract-editing task, to check whether it chooses an appropriate amount of work.

Then record one failure. If the Skill skips the number check, first check whether the entry was actually loaded, then the script paths and stop conditions. Fix the cause of failure in the right place, rather than adding yet another “must follow”.

Exercise

Install skills/paper-retell from the reference answers in your own exercise project, and do the three tests in new sessions. Each time, record only whether it triggered, which files it used and which steps were missing. Compare before and after your changes, and keep the smallest version that transfers.

Common mistakes and how to fix them

Saving a whole chat as a Skill. The reader cannot tell the reusable method from decisions specific to this task. Distill the inputs and judgments, and save the run separately.

The Skill hard-codes this computer’s paths. It fails in another project. Paths are relative to the project or the Skill folder, and machine information comes from configuration.

The content is complete but has never been called in a new session. Test the entry in a new session, then test the method on other material. It is reusable only when both pass.
