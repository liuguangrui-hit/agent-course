3.3 结果能说明什么

课后深入，约 30 分钟。

Agent 能在一下午跑完以前一周的实验，也能在一下午写出一份看起来很扎实、其实什么都没证明的结果说明。这一节讲怎样让一个实验真的说明点什么：实验前写预测，实验里放对照，实验后有人审。

预测怎么写

一条有用的预测有三部分：

  1. 一个数字或者方向：带噪验证集早停，最终准确率比干净验证集低 2 到 5 个点。
  2. 一句理由：验证集的噪声让停止点晚几轮，网络已经开始记错误标签。
  3. 怎样判对错：低 2 到 5 个点算对，其余都算错。

第三部分最容易漏。没有它，任何结果都能被说成大致符合预期。

预测写完立刻提交到 Git。提交记录摆明了预测在先，结果在后。

对照

只跑自己的方法，结果再好也说明不了它好在哪里。一个实验至少要有：

对照 回答的问题
不加任何处理的基线 有没有提升
已知有效的方法 提升算不算大
本该没有效果的处理 提升是不是来自别的东西

第三种最容易被忽略。比如你在提示里加了一段经验让 Agent 做得更好，那就再跑一组加同样长度、但内容无关的文字，看提升还在不在。很多看起来漂亮的效果，加上这种对照后就消失了，原来只是因为提示变长了。

种子和波动

同一个实验换个随机种子，结果会变。第 1 课的实验每个设置跑五个种子。比较两个方法时，两边用同样的种子，按种子配对相减，看这五个差值：均值多大，95% 置信区间跨不跨过零。区间跨过零，就不能说一个比另一个好。

对 results.csv 里每个设置，报五个种子的均值和标准差。
对比两种早停时，按种子配对算差值，报差值的均值和 95% 置信区间；区间跨过零的，结论写差别不明显。

怀疑好结果

坏结果大家都会查：代码有没有错，参数对不对。好结果往往直接写进论文。对好结果用同样的标准：

  • 换一组种子，效果还在不在？
  • 换一个噪声水平，方向一致吗？
  • 加上本该没效果的对照，差距还在吗？
  • 是不是测试集泄漏进了训练或者早停？

最后一条在早停实验里尤其常见：用测试集选停止点，结果当然好。

结果说明的样子

# 带噪验证集早停

提交 3f2a1c9

这张表摘自第 3 课预览的真实结果。

## 预测与结果
| 预测 | 结果 | 对错 |
|---|---|---|
| 准确率比干净验证集低 2 到 4 点 | 高 0.99 点，配对差的 95% 置信区间跨过零 | 错 |
| 停止点晚 2 到 6 轮 | 早 2.6 轮 | 错 |
| 最终准确率 92% 到 96% | 93.25% | 对 |

## 这说明了什么
带噪验证集照样看得出网络何时开始记错误标签，早停把准确率从 68.37% 拉回 93.25%。

## 没说明什么
一段话：只在这个合成任务上试过，没有试非对称噪声。

没说明什么那一段写一次，写在这里。不要把限定拆开散到每一句话里，满篇的可能和在一定程度上，读者反而找不到你真正的结论。

审查

写说明的 Agent 和跑实验的是同一个，看不出自己的盲点。审查交给另一家，只看预测、结果文件和说明三样东西，查数字是否对得上，结论是否超出数字，提交编号是否对应。

审查意见对应具体的提交编号。说明改了，旧意见就过期了，要重审。审查做完也不等于通过，要看意见里的判断。

预测错了怎么办

预测错了是这个流程里最有价值的结果。它说明你对这个现象的理解有一处不对。让 Agent 把错的那条预测和实际结果写进知识库的分歧表，第 4 课的循环会从这里接着提下一个问题。

练习

在练习 3 的结果上，补一个本该没有效果的对照：验证集换成完全随机的标签，按它早停。预测它的结果，跑，对照。

会看到什么

随机标签的验证集里没有关于真实标签的信息，按它选停止点，通常停得很早或者很随意。如果它也带来和带噪验证集差不多的提升，说明提升主要来自早停这个动作本身，而不是验证集里的信息。这本身就是一个值得写进分歧表的发现。

最容易出错的地方

限定散在每一句里。 每句话都加可能，读者找不到结论。没说明什么集中写一段。

差距小于波动还说更好。 0.3 个点的平均差距，五个种子里有正有负，不能说谁更好。按种子配对算差值的置信区间，跨过零就写差别不明显。

测试集参与了选择。 用测试集早停或调参，结果当然好看。验证集从训练集里切，测试集只在最后用一次。

3.3 What results show

Self-study, about 30 minutes.

An agent can finish a week’s experiments in an afternoon. It can also spend that afternoon writing a solid-looking report that proves nothing. This section covers how to make an experiment show something: predictions before it, controls during it, and a review after it.

Writing predictions

A useful prediction has three parts:

  1. A number or direction: with early stopping on a noisy validation set, final accuracy will be 2 to 5 percentage points below that with a clean validation set.
  2. A one-sentence reason: validation noise delays stopping by a few epochs, by which time the network has started memorizing wrong labels.
  3. A rule for right or wrong: a drop of 2 to 5 points is right; anything else is wrong.

The third is easiest to miss. Without it, any result can be described as broadly expected.

Commit predictions to Git as soon as you write them. The commit history makes the order clear: predictions first, results later.

Controls

Running only your method cannot show what makes it good, however good the result. An experiment needs at least:

Control Question it answers
A baseline with no treatment Is there an improvement?
A method known to work Is the improvement large?
A treatment that should have no effect Does the improvement come from something else?

The third is often overlooked. If adding experience to a prompt helps the agent, run another group with equally long but irrelevant text. Does the gain remain? Many impressive effects disappear with this control: the prompt was simply longer.

Seeds and variation

Change the random seed and the result changes. Session 1’s experiment runs five seeds per setting. To compare methods, use the same seeds for both and subtract within each pair. Look at the five differences: how large is the mean, and does its 95% confidence interval cross zero? If it crosses zero, you cannot say one is better.

For each setting in results.csv, report the mean and standard deviation across five seeds.
Compare the two early-stopping methods with paired differences by seed. Report the mean difference and its 95% confidence interval. If the interval crosses zero, say the difference is not clear.

Question good results

Everyone checks bad results: is the code wrong, are the parameters right? Good results often go straight into the paper. Apply the same standard to them:

  • Does the effect remain with another set of seeds?
  • Is the direction consistent at another noise level?
  • Does the gap remain with a control that should have no effect?
  • Did the test set leak into training or early stopping?

The last is especially common in early-stopping experiments. Of course the result looks good if you choose the stopping point with the test set.

What a result report looks like

# Early stopping with a noisy validation set

Commit 3f2a1c9

This table comes from Session 3's real preview results.

## Predictions and results
| Prediction | Result | Right or wrong |
|---|---|---|
| Accuracy 2 to 4 points below clean validation | 0.99 points above; the paired difference's 95% confidence interval crosses zero | Wrong |
| Stops 2 to 6 epochs later | 2.6 epochs earlier | Wrong |
| Final accuracy 92% to 96% | 93.25% | Right |

## What this shows
Noisy validation still reveals when the network starts memorizing wrong labels. Early stopping brings accuracy back from 68.37% to 93.25%.

## What it does not show
One paragraph: tested only on this synthetic task, not with asymmetric noise.

State what it does not show once, here. Do not scatter qualifications across every sentence. With “may” and “to some extent” everywhere, readers cannot find your actual conclusion.

Review

The agent writing the report also ran the experiment and cannot see its own blind spots. Give the review to another vendor. It reads only predictions, result files and the report, checking whether numbers match, conclusions go beyond them, and commit IDs correspond.

Review comments apply to a specific commit ID. Once the report changes, old comments expire; review again. A completed review is not a pass. Read its judgment.

When a prediction is wrong

A wrong prediction is the most valuable result in this workflow. It shows a gap in your understanding of the phenomenon. Have the agent write the wrong prediction and actual result into the knowledge base’s conflict table. Session 4’s loop draws its next question from there.

Exercise

Add a control that should have no effect to Exercise 3’s results: replace validation labels with completely random labels and use them for early stopping. Predict, run, compare.

What you will see

A validation set with random labels has no information about the true labels. Using it to choose a stopping point usually stops very early or arbitrarily. If it gives about the same gain as noisy validation, the gain mainly comes from stopping early itself, rather than information in the validation set. That is a finding worth putting in the conflict table.

Where agents go wrong most

Qualifications in every sentence. Put “may” in every sentence and readers cannot find the conclusion. Keep what the result does not show in one paragraph.

Calling a gap smaller than the variation an improvement. A mean gap of 0.3 points, positive for some of five seeds and negative for others, cannot tell you which is better. Compute the confidence interval of paired differences by seed. If it crosses zero, say the difference is not clear.

The test set helps make choices. Early stopping or tuning with the test set makes results look good. Hold validation data out of training; use the test set only once, at the end.
