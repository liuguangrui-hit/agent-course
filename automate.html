4 Agent 自动化与自进化

一小时后，你的工作台会在夜里自己干活：晚上十点从问题清单里挑一个问题，写预测，把实验送上服务器；早上七点收回结果，请另一家 Agent 审，把这一轮学到的做法记进经验榜，更新一个手机上就能打开的结果网页，再推一条通知到你手机上。每过三轮，一个独立的反思检查会判断这个循环是否还在正道上，必要时让它停下。

课堂核心 60 分钟。课后深入 4.1 至 4.3 共约一个半小时，按需选读。

下载第 4 课练习材料

练习材料接着第 3 课的仓库，多了几样：LOOP.md 写一轮循环怎么走，STATE.md 记到哪一步了，playbook.md 是空的经验榜，review_task.md 和 reflection_task.md 是审查和反思的任务，code/make_page.py 生成结果页，ledger.csv 是空的用量账本。

开课先装工具，1 分钟发出去

本课暗线：让 Agent 不用你叫也会开工，干完会告诉你。 到第 3 课为止，每件事都从你在对话框里发一句话开始。这一课添五样：定时任务让它按时开工；命令行版的 Claude 和 Codex 让一个 Agent 在无人值守时把事交给另一家；手机通知让它跑完叫你；经验榜让它每轮把做法记下来；GitHub Pages 把结果变成网页。

在 Claude 里打开 lesson-4 文件夹，先发：

先读 ../lesson-3/AGENTS.md，把里面的工具用法抄进本文件夹的 AGENTS.md。
这个项目还要在夜里无人值守地跑。检查并补上：
1. Claude Code 和 Codex 的命令行版，各用一句话测试能在命令行里无人值守地回答；
2. 手机通知：用 ntfy，起一个别人猜不到的频道名，告诉我手机上装哪个应用、订阅哪个频道，然后发一条测试通知；
3. 在我的 GitHub 上建一个公开仓库 lab-results，打开 GitHub Pages，放一个只有标题的 index.html，给我网址。
装之前列出打算装什么、装在哪，等我同意。
最后在 AGENTS.md 里补几行：通知怎么发，结果页在哪个仓库，未发表的数字和代码不进公开仓库。

手机上收到测试通知，打开网址看到标题，就装好了。五样里另外两样不用装：经验榜就是练习材料里的 playbook.md，练习 1 第一次写进去；定时任务在练习 2 里让它自己建。

先看成品，5 分钟

打开练习材料 preview/site/ 里的结果页。它用第 3 课的真实结果当第一轮：顶上一行是跑了几轮，预测命中了几次；下面每轮一行：问题，预测，对错，审查是否通过；页尾是经验榜，每条后面写着它来自哪一轮。这是公开页，只到对错这一层；完整的数字和图在 preview/internal/ 的内部页里。

再打开 preview/notification.txt，这是早上七点推到手机上的那条通知：一句话结论加结果页的链接。

讲，10 分钟

每一轮都是一个新对话。 一个对话开着跑一周，每醒一次都要把一周的内容重读一遍，越跑越慢，越跑越贵，也越容易忘掉第一天的要求。正确的做法是每次定时开工都开一个新对话，从 STATE.md 读到上次停在哪里，干完把进度写回去。记忆在文件里，不在对话里。

一件事只有一个对话在干。 两个定时任务撞在一起，或者昨晚那轮还没收工今晚的又开工，两个对话会同时改同一批文件。开工第一步是占锁：建一个 .lock 文件夹，建不成说明别人在干，退出。

自进化靠经验榜，不靠改规则。 每轮收工时，把这一轮哪个做法有效、哪个出了问题，写成一两条经验，下一轮开工先读。经验榜只记做法，评价标准不归它改：预测命中率和审查是否通过，是这个循环的尺子，尺子不能跟着被量的东西一起变。

放手之前装一个刹车。 全自动的循环最常见的失败，是沿着一个错的方向认真地跑很久。每三轮让一个独立的对话读一遍全部记录，判断方向对不对，它有权写一个 STOP 文件让循环停下来等你。

练习 1：先手动跑一轮，15 分钟

读一遍 LOOP.md，它把一轮分成开工和收工两半：

按 LOOP.md 跑一轮开工：读 STATE.md 和 playbook.md，从 ../lesson-2/vault/questions.md 里挑一个还没做过的问题，
写预测并提交，改代码，冒烟测试，送上服务器。这一轮为了课上演示，只跑 1 个种子、10 轮。
干完把进度写进 STATE.md，然后停下。

几分钟后实验跑完，开一个新对话：

按 LOOP.md 跑一轮收工。

收工会拉回结果，写结果说明，用 Codex 的命令行版审，把结果和错了的预测写回第 2 课的知识库，按新的分歧补一个问题进问题清单，再更新经验榜和结果页，发通知。看手机。最后一步让循环不会做完三个问题就断粮。

练习 2：让它自己按时开工，15 分钟

建两个定时任务，都在本文件夹里运行：
每晚 22:00 按 LOOP.md 跑开工，每早 07:00 按 LOOP.md 跑收工。
每次都是新对话，开工前先看 STATE.md 和有没有 STOP 文件。
定时任务用 Accept edits 模式，用到的命令写进项目设置的允许表，别的命令一律不放行。
建好后各手动触发一次测试，告诉我它们在哪里能看到，怎样暂停。

Claude 桌面版的定时任务在侧栏里能看到，可以暂停和手动运行。电脑要开着；合上盖子的笔记本到点不会开工，这时把定时任务换到服务器上，用命令行版跑，见 4.1。

练习 3：装刹车，10 分钟

再建一个定时任务，每天 08:00 看一眼：自上次反思以来如果又完成了三轮，就运行一次反思检查，否则直接退出。反思检查是一个独立的新对话，读 STATE.md，playbook.md，所有轮次的预测、结果和审查意见，不改它们，只写反思报告，必要时写 STOP。
回答三个问题：预测命中率在变好还是变坏；最近几轮的问题是否越来越小、越来越像；经验榜里有没有哪条经验其实是在掩盖问题。
写成 reflections/日期.md。如果它认为方向错了，写一个 STOP 文件说明理由，并推一条通知给我。

最容易出错的地方

一个对话跑一周。 每次醒来都重读一周的上下文，又慢又贵，早先的要求也忘了。每轮开新对话，进度存在文件里。

两轮撞车。 昨晚的实验还没跑完，今晚的又开工，两个对话改同一批文件，结果对不上预测。开工先占锁，占不到就退出。

认真地跑错方向。 循环每晚都顺利完成，结果页每天都有新的一行，但问题一轮比一轮小，或者某个好结果其实来自一个没控制住的因素。设一个独立的反思检查，有权叫停。好结果和坏结果一样要被检查。

等待时空转。 一轮里有一步要等实验，整个循环就停在那里，几个小时没有人看。只让真正依赖这个结果的步骤等，其他事照做；等待时一定有监视器挂着，不然一停就是一夜。

经验榜越来越长。 每轮加两条，一个月后六十条，互相矛盾，下一轮根本读不完。经验榜限定条数，新经验和旧的相近就合并，挤出去的进归档。

让循环改自己的尺子。 经验榜里出现一条把预测写宽一点，命中率立刻上升。评价标准和预测格式固定在 LOOP.md 里，经验榜只能改做法。

半夜额度用完。 定时任务跑到一半额度耗尽，它会反复重试，或者停在半截没人知道。开工前看一眼额度，不够就在状态文件里记下来，等下一个时间点，同时推一条通知。

在 AI 科学家里。 AI 科学家就是这个循环放大后的样子：问题来自文献森林，预测登记进假设森林，实验结果回来后对照，经验写进按行为分开的经验榜，每个季度一次独立反思，可以叫停整个流程。它的经验榜先从几千篇已发表论文里学，再用到自己的课题上，评价它的尺子只有一把：用学到的认识去预测还没看过的论文结果，准不准。

换成你自己的课题

拿你自己的问题清单和实验代码，按 LOOP.md 的格式写一份你的循环，先手动跑两轮，确认每一步都能从文件接上，再交给定时任务。头几天每天早上看一眼结果页和反思检查，确认它稳了，再改成只看通知。

4 Automation and Self-Evolution

In an hour your workbench will be ready to work overnight: at 10 pm it picks a question, writes predictions and sends the experiment to the server. At 7 am it brings back results, asks another vendor’s agent to review, records what it learned in the playbook, updates a results page you can open on your phone, and sends you a notification. Every three rounds, an independent reflection check judges whether the loop is still on track and stops it if needed.

Core class: 60 minutes. Self-study sections 4.1 to 4.3 take about an hour and a half in total; read what you need.

Download the Session 4 materials

The materials extend Session 3’s repository with a few additions: LOOP.md describes a round, STATE.md records progress, playbook.md is an empty playbook, review_task.md and reflection_task.md are the review and reflection tasks, code/make_page.py builds the results page, and ledger.csv is an empty usage ledger.

Install tools at the start: send the card in 1 minute

This session’s hidden thread: let the agent start without you calling it, and tell you when it finishes. Through Session 3, every job began with a message from you. This session adds five things: scheduled tasks to start on time; command-line Claude and Codex so one agent can hand work to another vendor unattended; phone notifications when work finishes; a playbook to record methods each round; and GitHub Pages to turn results into a web page.

Open the lesson-4 folder in Claude and send:

First read ../lesson-3/AGENTS.md and copy its tool instructions into this folder's AGENTS.md.
This project also needs to run unattended overnight. Check and set up:
1. Command-line Claude Code and Codex. Test each with one sentence to show it can answer unattended from the command line;
2. Phone notifications with ntfy. Choose a channel name others cannot guess, tell me which phone app to install and which channel to subscribe to, then send a test notification;
3. A public repository on my GitHub called lab-results. Enable GitHub Pages, add an index.html containing only a title, and give me the URL.
Before installing, list what you plan to install and where, and wait for my OK.
Finally add a few lines to AGENTS.md: how to send notifications, which repository holds the results page, and that unpublished numbers and code stay out of the public repository.

Once the test notification reaches your phone and the URL shows the title, setup is done. The other two need no installation: the playbook is playbook.md in the materials, first filled in Exercise 1; the agent creates scheduled tasks in Exercise 2.

See the finished product, 5 minutes

Open the results page under preview/site/. It uses Session 3’s real results as round one. The top line shows how many rounds ran and how many predictions were right. Below, each round has a row: question, prediction, right or wrong, and whether the review passed. At the bottom is the playbook, each entry naming the round it came from. This is the public page, so it stops at right or wrong; the full numbers and figures are on the internal page under preview/internal/.

Then open preview/notification.txt: the notification sent to your phone at 7 am, with a one-sentence conclusion and a link to the results page.

Talk, 10 minutes

Every round is a new conversation. Keep one conversation running for a week, and each wake-up rereads the whole week. It gets slower, more expensive, and more likely to forget day one’s requirements. Start a new conversation for every scheduled run. Read STATE.md to find where the last one stopped, then write progress back when done. Memory lives in files.

Only one conversation works on a task. Two scheduled tasks may overlap, or tonight’s round may begin before last night’s ends. Both then edit the same files. First acquire a lock: create a .lock folder. If creation fails, someone else is working; exit.

Self-evolution comes from the playbook, not changing rules. At the end of each round, record one or two entries on what worked and what failed. Read them at the start of the next round. The playbook records methods; it cannot change the evaluation criteria. Prediction accuracy and passing review are the loop’s yardstick. The yardstick cannot change along with what it measures.

Fit a brake before letting go. A common failure of a fully automated loop is diligently following a wrong direction for a long time. Every three rounds, have an independent conversation read all records and judge the direction. It can write a STOP file to halt the loop and wait for you.

Exercise 1: run one round manually, 15 minutes

Read LOOP.md. It splits a round into starting work and wrapping up:

Follow LOOP.md to start one round: read STATE.md and playbook.md, and pick an untried question from ../lesson-2/vault/questions.md.
Write and commit predictions, change the code, run a smoke test, and send the experiment to the server. For this class demo, use only 1 seed and 10 epochs.
Write progress to STATE.md, then stop.

A few minutes later, when the experiment finishes, start a new conversation:

Follow LOOP.md to wrap up one round.

Wrapping up brings back results, writes the report, calls command-line Codex to review, writes results and wrong predictions back to Session 2’s knowledge base, adds a question based on the new disagreement, updates the playbook and results page, and sends a notification. Check your phone. Adding a question keeps the loop from running out after the first three.

Exercise 2: let it start on schedule, 15 minutes

Create two scheduled tasks, both running in this folder:
at 22:00 each night, follow LOOP.md to start work; at 07:00 each morning, follow LOOP.md to wrap up.
Use a new conversation each time. Before starting, check STATE.md and whether a STOP file exists.
Use Accept edits mode for the scheduled tasks. Put the commands they need in the project's allow list; allow no other commands.
Trigger each once manually to test. Tell me where I can see them and how to pause them.

Claude desktop’s scheduled tasks appear in the sidebar, where you can pause or run them manually. The computer must stay awake. A laptop with its lid closed will not start at the scheduled time. Move tasks to the server and use the command-line version in that case; see 4.1.

Exercise 3: fit the brake, 10 minutes

Create another scheduled task to check daily at 08:00: if three more rounds have finished since the last reflection, run a reflection check; otherwise exit. The check is an independent new conversation. It reads STATE.md, playbook.md, and every round's predictions, results and reviews, changes none of them, and writes only its reflection report, plus STOP when needed.
Answer three questions: is prediction accuracy improving or worsening? Are recent questions getting smaller and more alike? Does any playbook entry hide a problem?
Write to reflections/<date>.md. If the direction looks wrong, write a STOP file with the reason and send me a notification.

Where agents go wrong most

One conversation runs for a week. Each wake-up rereads a week’s context, slowly and expensively, and forgets early requirements. Start a new conversation each round and keep progress in files.

Rounds collide. Tonight’s round starts before last night’s experiment finishes. Two conversations edit the same files and results no longer match predictions. Acquire the lock first; exit if you cannot.

Diligently following a wrong direction. The loop finishes every night and adds a row each day, but questions keep shrinking, or a good result comes from an uncontrolled factor. Add an independent reflection check with power to stop it. Check good results as well as bad ones.

Idle waiting. One step waits for an experiment, and the whole loop sits there for hours. Wait only on steps that need the result; keep doing other work. Always leave a monitor running while waiting, or a pause can last all night.

The playbook keeps growing. Two entries per round become sixty in a month, contradicting each other and too long to read. Cap the entries, merge similar ones, and archive displaced entries.

The loop changes its own yardstick. A playbook entry says to widen predictions, and accuracy rises at once. Fix evaluation criteria and the prediction format in LOOP.md. The playbook changes only methods.

Quota runs out at midnight. A scheduled task exhausts the quota halfway through, then retries repeatedly or stops without anyone knowing. Check quota before starting. If it is insufficient, record that in the state file, wait for the next scheduled time, and send a notification.

Inside the AI Scientist. The AI Scientist is this loop at a larger scale: questions from the literature forest, predictions in the hypothesis forest, comparisons when results return, and experience in playbooks separated by behaviour. An independent quarterly reflection can stop the whole workflow. Its playbooks first learn from thousands of published papers, then apply that learning to its own topics. There is one yardstick: how accurately do learned insights predict results in papers it has not yet seen?

Now with your own topic

Use your own question list and experiment code to write a loop in the format of LOOP.md. Run two rounds manually first and confirm each step can pick up from files. Then hand it to scheduled tasks. For the first few days, check the results page and reflection each morning. Once it is stable, read only the notifications.
