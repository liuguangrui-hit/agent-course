4 自动化

让一轮研究在新会话里接得上，中断后能恢复，失败后留下原因。再从运行中提炼一条候选经验，设计它怎样在下一批任务上接受检验。

课前完成准备，课上 60 分钟，课后先复习再选做深入。

课前预备 · 课上一小时 · 课后复习与拔高

凌晨实验已经启动，写状态时连接断了。早上的 Agent 读到未完成，是否会再启动一份？夜间运行最需要先解决的，是它醒来时怎样知道已经发生了什么。

研究循环还有第二个问题。它每天完成一轮，产物越来越多，能力是否也在提高？把流程接起来以后，再给经验设置独立的检验。

课前预备

预留 15 至 30 分钟，沿用前几课环境。

课前工具准备。 下载材料并补齐依赖，准备本地结果页和命令行入口。恢复逻辑、状态转移和经验检验都在课堂里做。

把 lesson-2，lesson-3，lesson-4 放成相邻目录，确认自己的问题清单和上一课结果能找到。
按 README.md 准备锁定环境与 logs/，保留第 3 课可运行实现；没有完成时记下，使用包内预览作课堂起点。
检查所选官方非交互入口，用包内 wake_review.py 对 preflight-input.md 做一次零延迟调用，确认当前账号可用。
本例用 Claude 的受限无工具调用，输入由脚本经 stdin 提供；命令说明见 README.md。不开长期定时。
打开 preview/site/index.html 和 preview/internal/round-1.html，只确认页面可读。
列出已有调度器和通知渠道，不新增频道，不发送消息，不进行部署。
把实际命令、文件位置和未解决项写入 preflight.md，稳定入口写入 AGENTS.md。

开课前应能找到 LOOP.md 与 STATE.md，恢复演示和本地预览。这里不提前运行故障演示，也不填写恢复结论，故障会怎样影响下一步要在课堂观察。

课堂一起接一次真实的短延迟唤醒，核对机器、时区与执行状态。定时器只触发一次，进程退出便停止；课后再扩到少量周期运行。外部通知和发布另选具体目标与范围。

课上一小时

先看一轮的记录与交接，5 分钟

先核对 preflight.md，确认本课的本地演练条件，再查看上一轮留下的状态。

练习材料的 LOOP.md 是交接规则，STATE.md 记当前步骤，每轮在自己的目录留下预测、结果与审阅。预览网页使用第 3 课的实跑结果生成，打开内部页可以追回原始数字。

恢复演示把一个故障做给你看：产物已写出，状态还没来得及提交，程序退出。再次执行时先核查产物，再补状态，输出数量仍然是一份。你会看到它怎样从已存在的产物接上状态。

研究循环的状态转移，10 分钟

一轮研究先选题并冻结预测，再执行与校验，最后审阅并归档。每条转移都要有完成条件，例如执行转到校验时，退出码和产物清单都要满足要求。

状态未知要先查询，运行失败按原因恢复，研究假设被否定则正常进入结论。程序失败与科学负结果分开，循环才知道该修代码还是改理解。

自动化固定了这些转移。系统学习则改变以后的选择或做法，并要在未见任务上测出改进。两者在记录里分别展示。

练习一，做一次中断恢复，15 分钟

先读 recovery_demo.py，说明它模拟的动作与故障点。
按 README 在独立演示目录运行，模拟产物写出后退出，再重新运行。
核对输出数量、事件记录与最终状态，解释它怎样识别同一动作。
随后用同样思路检查 LOOP.md：找出启动实验与写状态之间的空档。

同一动作重复请求后，只产生一次预定效果，叫作幂等。一次网络超时不告诉你动作有没有发生，所以恢复时要能查询已知身份，或在本地核对对应产物。

练习二，定时审阅与收工交接，15 分钟

沿用第 3 课已完成的一轮，或从包内预览复制为演练起点，标明来源。
把本轮 result.md 交给 wake_review.py，设五秒后触发一次，调用最长九十秒，输出到新的 one-shot-review/。
一起检查 run.json 中的主机与时区、计划时间与实际时间，再核对输入哈希和退出码，并查看最终的 review.md。
只有 completed 才把审阅意见交给新会话；超时、失败和空输出先记录原因，不推进审阅完成状态。
新会话只读 LOOP.md、STATE.md 与本轮记录，核查后接手收工，生成本地页并检查重复效果。

命令由老师和学员一起核对后运行。路径换成这一轮实际记录，输出目录每次另起：

python3 wake_review.py --input preview/runs/1/result.md --out one-shot-review --delay-seconds 5 --timeout-seconds 90

计划等待时按 Ctrl+C，再检查 cancelled 与 calls_started 为零，可验证尚未发起调用。运行中按 Ctrl+C 会停止本次子进程。最后确认进程已退出，没有留下周期唤醒。

任务锁决定哪个会话能写，运行身份决定它写的是哪次动作。锁超时需要核查持有者与进程；旧会话仍能恢复写入时，仅按时间删锁会制造两个写作者。

练习三，留下候选经验和测试，10 分钟

从本轮失败或成功里提炼至多一条经验，写适用条件、具体动作和来源。
列出它预期会改变哪类未见任务，主要评估指标是什么。
保留一份无经验对照，再设计同格式近似长度的安慰剂对照。
经验先标为候选，测试方案放入下一批任务，不把本次成功直接当成有效性证明。

当前循环完成后，课后再设置少量定时运行。先确认停止条件、恢复方法和额度耗尽的行为，再延长无人值守时间。

检查与工作台小结，5 分钟

常见错误与处理方法

每次醒来都从第一步重做。 状态指向产物与动作身份，恢复先核查已发生的效果。

有锁就认为没有并发。 核查锁由谁持有、接管后旧会话能否继续写，所有共享写入走同一入口。

轮数增加就说系统进化。 固定未见任务和评分标准，比较是否产生可重复收益。

把运行失败丢掉，结果页只留成功。 失败轮次保留状态与原因，才能判断改进作用在哪一环。

工作台小结

前几课的文件现在被状态转移连接起来。课堂的单次定时器按时触发任务，运行器记录执行身份。审阅给出结论判定，经验榜提出下一次的做法。结果页把它们汇到同一个入口，帮助你决定下一步工作。

AI 科学家把类似职责分给独立模块。本课先用自己的一个问题把最小循环走通，再考虑扩大任务量。

课后复习与拔高

先复盘，15 分钟

只读课堂的 STATE.md 和本轮文件，列出下一位接手者应先查询什么。再关掉 Agent，从状态图走一遍失败恢复，区别程序执行失败和科学负结果。把仍靠猜测的转移写到 review-after-class.md，补上可核查的完成条件。

正反例辨析，20 分钟

甲看到状态仍是未启动，直接重发实验。乙先用已记任务标识查询，发现产物已生成，只补状态。分别指出二者在断连窗口中可能造成的效果。再看一轮正常执行但否定了预测的实验：它该重试程序，还是进入结论与经验候选？写出理由。

先画恢复路径，再看对照思路

状态落后于实际动作时，甲可能重复执行。乙依据动作身份核查效果，恢复才有依据。程序成功且产物完整的科学负结果可以正常归档；经验是否有效继续交给未见任务测试。

沿课堂往深处做

先重做一次中断恢复，再从课堂单次唤醒选一条路径。周期调度先安排少量运行，核对暂停与删除入口；外部通知和部署沿用已经明确的目标与授权范围。

4 Research automation

Build a research loop that a new session can resume, that recovers from interruptions and records the reasons for failures. Extract one candidate playbook entry from a run and design a test on the next batch of tasks.

Prepare before class, spend 60 minutes in class, then review and choose an optional extension.

Before class · In class · After class: review and extension

An experiment started in the early morning, and the connection dropped while the status was being written. Will the morning agent read “not finished” and start another copy? An overnight workflow needs a reliable way to determine what has already happened when a session resumes.

A research loop has a second problem. It finishes one round a day and produces more and more, but is its capability improving too? Once the process is connected, give the lessons it learns an independent test.

Before class

Allow 15 to 30 minutes, reusing the environment from earlier lessons.

Before-class setup. Download the materials and install missing dependencies, and prepare a local results page and a command-line entry point. Recovery logic, state transitions and testing playbook entries are all done in class.

Place lesson-2, lesson-3 and lesson-4 as neighboring directories, and confirm that my question list and the previous lesson's results can be found.
Prepare the locked environment and logs/ as README.md says, keeping the runnable implementation from Lesson 3; if it was not finished, note that and use the packaged preview as the starting point in class.
Check the official non-interactive entry I chose, and make one zero-delay call on preflight-input.md with the packaged wake_review.py to confirm the current account works.
This example uses a restricted, tool-free Claude call, with input supplied by the script through stdin; the command is explained in README.md. Do not set up a long-term schedule.
Open preview/site/index.html and preview/internal/round-1.html, and only confirm that the pages are readable.
List the existing schedulers and notification channels. Do not add channels, send messages or deploy anything.
Write the actual commands, file locations and unresolved items into preflight.md, and the stable entry points into AGENTS.md.

Before class you should be able to find LOOP.md and STATE.md, the recovery demonstration and the local preview. Do not run the failure demonstration in advance or fill in the recovery conclusion; how a failure affects the next step is observed in class.

In class we connect one real short-delay wake-up together and check the machine, time zone and execution status. The timer fires only once and stops when the process exits; after class it is extended to a few periodic runs. External notifications and publishing each need a specific target and scope chosen separately.

In class

Records and handoff between rounds, 5 minutes

First check preflight.md and confirm that this lesson only needs a local rehearsal, then look at the state left by the previous round.

In the exercise materials, LOOP.md holds the handover rules and STATE.md records the current step; each round leaves its prediction, result and review in its own directory. The preview pages are generated from the actual runs of Lesson 3, and opening the internal page traces back to the raw numbers.

The recovery demonstration shows you a failure: the output has been written, the status has not yet been committed, and the program exits. On the next run it checks the output first, then fills in the status, and the number of outputs is still one. You will see how it picks up the status from an output that already exists.

Draw the loop as state transitions, 10 minutes

A round of research goes through topic selection, prediction freeze, execution, verification, review and archiving. Every transition needs a completion condition; for example, moving from execution to verification requires both the exit code and the product list to meet their requirements.

An unknown status is queried first, a failed run is recovered according to its cause, and a refuted research hypothesis moves normally into the conclusion. Only when program failures and negative scientific results are kept apart does the loop know whether to fix the code or change its understanding.

Automation implements these transitions. System learning changes later choices or methods, and the improvement has to be measured on unseen tasks. The two are shown separately in the record.

Exercise 1: recover from one interruption, 15 minutes

First read recovery_demo.py and explain which action and which failure point it simulates.
Run it in a separate demonstration directory as the README says, simulating an exit after the product is written, then run it again.
Check the number of outputs, the event record and the final state, and explain how it recognizes the same action.
Then use the same idea to check LOOP.md: find the gap between starting the experiment and writing the state.

When repeated requests for the same action produce the intended effect only once, the action is idempotent. A network timeout does not tell you whether the action happened, so recovery must be able to query a known action ID, or check the corresponding output locally.

Exercise 2: schedule a read-only review and hand the wrap-up to a new session, 15 minutes

Reuse a round completed in Lesson 3, or copy the packaged preview as a rehearsal starting point, and state its source.
Give this round's result.md to wake_review.py, set to fire once after five seconds with a maximum call time of ninety seconds, writing to a new one-shot-review/.
Together check the host and time zone in run.json, the planned and actual times, the input hash, the exit code and the final review.md.
Only a completed run hands its review comments to a new session; for a timeout, failure or empty output, record the reason first and do not advance the review to completed.
The new session reads only LOOP.md, STATE.md and this round's records, checks them, then takes over and finishes the round, generating the local page and checking for duplicated effects.

The teacher and students check the command together before running it. Replace the path with this round’s actual record, and use a new output directory each time:

python3 wake_review.py --input preview/runs/1/result.md --out one-shot-review --delay-seconds 5 --timeout-seconds 90

Pressing Ctrl+C during the planned wait, then checking that it shows cancelled and calls_started is zero, verifies that no call was made. Pressing Ctrl+C during the run stops this subprocess. Finally confirm that the process has exited and no periodic wake-up was left behind.

The task lock determines which session may write; the run ID identifies the action being recorded. A lock timeout needs a check of the holder and its process; if the old session can still resume writing, deleting the lock by time alone creates two writers.

Exercise 3: record a candidate playbook entry and its test, 10 minutes

Distill at most one playbook entry from this round's failure or success, writing its conditions of use, the concrete action and its source.
List which kind of unseen task it is expected to change, and the main evaluation metric.
Keep a no-playbook control, then design a placebo control in the same format and of similar length.
Mark the entry as a candidate first and put the test plan into the next batch of tasks; do not take this round's success as proof that it works.

Once the current loop is complete, set up a few timed runs after class. First confirm the stop conditions, the recovery method and what happens when quota runs out, and only then extend the unattended time.

Check and workbench summary, 5 minutes

Common mistakes and how to fix them

Redoing everything from step one on every wake-up. The state points to products and action identities, and recovery first checks which effects have already happened.

Assuming there is no concurrency because there is a lock. Check who holds the lock and whether the old session can keep writing after a takeover; all shared writes go through the same entry point.

Saying the system evolved because the number of rounds went up. Fix the unseen tasks and the scoring standard, and compare whether a repeatable gain appears.

Discarding failed runs so the results page shows only successes. Only when failed rounds retain their status and cause can you judge which stage an improvement affects.

Workbench summary

The files from earlier lessons are now connected by state transitions. The one-shot timer starts the session, the runner records run details, the reviewer assesses the conclusions, and the playbook suggests methods for future tasks. The results page gathers them into one entry point, so you can decide what to continue.

AI Scientist divides similar responsibilities among separate modules. In this lesson, first get the minimal loop working with one question of your own, then consider scaling up the workload.

After class: review and extension

Review first, 15 minutes

Reading only the class STATE.md and this round’s files, list what the next person to take over should query first. Then close the agent and walk through failure recovery on the state diagram, separating a failed program execution from a negative scientific result. Write the transitions that still rely on guessing into review-after-class.md, and add completion conditions that can be checked.

Compare the examples, 20 minutes

A sees that the status is still “not started” and resends the experiment straight away. B first queries with the recorded job identifier, finds the product already generated, and only fills in the status. Say what effect each could have in the disconnection window. Then look at an experiment that ran normally but refuted its prediction: should it retry the program, or move into the conclusion and a candidate playbook entry? Write your reasons.

Draw the recovery path first, then see the comparison notes

When the status lags behind the actual action, A may execute twice. B checks the effect from the action identity, so its recovery has a basis. A negative scientific result from a successful program with complete products can be archived normally; whether an entry works is still left to testing on unseen tasks.

Further study

First redo one interruption recovery, then choose one path that builds on the single wake-up from class. Start periodic scheduling with a few runs and check the controls for pausing and deleting the schedule; external notification and deployment keep to targets and authorization already made clear.
