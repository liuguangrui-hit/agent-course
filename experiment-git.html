3.1 Git 与 GitHub

课后深入，约 45 分钟。

半年后拿到一个好结果，提交编号把你带回了代码。数据却已经重切，依赖也升级了。复现需要同时保存代码、数据与环境信息。

代码提交与版本记录

Git 提交记录哪些受管理文件在那时是什么内容。先查看差异，再提交，正式运行从已提交代码启动。GitHub 保存远端副本，便于合作和服务器取回。

常用动作不多：看状态和差异，提交，再推送或取回。第一次在自己的账号建仓库时，先确认可见范围，取得链接后再让执行机器取代码。

建立本实验的 Git 仓库，先列出会纳入的文件。
忽略环境目录，凭据，大型数据与下载全文。代码和小型配置保留。
提交基线，记录完整提交号。若已有仓库，先查现状和未提交改动，再继续。

运行所需的其他记录

身份 要记录什么
数据 来源、切分规则与实际输入哈希
配置 命令参数和解析后的最终配置
环境 Python 与库版本，设备及关键驱动
产物 运行编号，输出清单，哈希与完成状态

配置文件中的默认值也会变化，所以保存实际解析值。运行编号指向一次执行，提交号指向代码；同一提交可以产生很多次运行。

干净状态与生成文件

启动器可以拒绝运行代码有未提交改动的正式实验。但结果目录写入后，仓库自然会变脏。检查范围要提前定义：执行代码和配置必须固定，输出写到独立运行目录，运行后的结果另行归档。

如果提交包含预测和代码，事后分析另起提交，仍引用执行提交。给预测记录时间和输入版本，私有历史保留原件，不通过事后修改把它变成命中。

为本次运行生成 run_metadata.json，记录执行提交和已跟踪代码的改动状态。
数据哈希按实际读入文件计算。记录完整命令、配置与种子。
完成后生成产物清单。分析脚本若后来修改，保存新的分析提交。

安全地回到旧版本

想比较旧代码时，在新目录建立独立检出或工作树。当前目录可能有别人的未提交文件，先看状态再决定恢复范围。

并行实验各有自己的工作树和输出目录。合并代码由一个整合者负责，实验结果按运行身份并存。目录隔离减少覆盖，服务器数据目录与输出路径仍要检查。

练习

从同一执行提交取两份代码，用相同配置运行一项短实验。比较环境与输出清单。若结果不逐字相同，先判断是浮点差异、随机源未固定，还是实际输入已经不同。

再只改变一个配置，确认新的运行能从元数据中被区分。最后写一段别人照着能重跑的说明。

常见错误与处理方法

提交号指向分析完成后的代码。 分别保存执行提交和分析提交，检查启动时的代码状态。

数据下载地址相同，就认为输入相同。 保存实际文件哈希和切分信息。

回退时覆盖同目录其他工作。 在独立目录检出旧版，恢复前检查现有改动。

参考 Pro Git 与 GitHub CLI 手册。

3.1 Git and GitHub

After-class deep dive, about 45 minutes.

Six months later you get a good result, and the commit hash takes you back to the code. But the data have been re-split and the dependencies upgraded. Reproducibility requires recording the code, data and environment together.

Record code versions with commits

A Git commit records what each tracked file contained at that time. Look at the diff first, then commit, and start full runs from committed code. GitHub keeps a remote copy, which makes collaboration and fetching onto servers easy.

The common actions are just checking status, viewing diffs, committing, pushing and pulling. The first time you create a repository in your own account, confirm its visibility first, get the link, and only then let the executing machine fetch the code.

Set up a Git repository for this experiment and first list the files that will be included.
Ignore environment directories, credentials, large data and downloaded full texts. Keep code and small configuration files.
Commit a baseline and record the full commit hash. If a repository already exists, check its current state and uncommitted changes first, then continue.

Record four other aspects of each run

Record What to record
Data Source, split rule and hash of the actual input
Configuration Command parameters and the final parsed configuration
Environment Python and library versions, device and key drivers
Outputs Run ID, output list, hashes and completion status

Default values in configuration files can also change, so save the actual parsed values. The run ID points to one execution and the commit hash points to code; one commit can produce many runs.

Clean state and generated files

A launcher can refuse to start a full experiment when the code has uncommitted changes. But once results are written, the repository naturally becomes dirty. Define the scope of the check in advance: executed code and configuration must be fixed, outputs go to a separate run directory, and results are archived separately after the run.

If a commit contains the prediction and the code, post-hoc analysis gets its own commit that still refers to the execution commit. Record the time and input version of the prediction, keep the original in private history, and do not edit it after the fact to make it look correct.

Generate run_metadata.json for this run, recording the execution commit and the change status of tracked code.
Compute data hashes from the files actually read. Record the full command, configuration and seeds.
Generate an output list when done. If the analysis script is changed later, save a new analysis commit.

Going back to an old version safely

To compare old code, create a separate checkout or worktree in a new directory. The current directory may hold someone else’s uncommitted files, so check status before deciding how much to restore.

Parallel experiments each have their own worktree and output directory. One integrator is responsible for merging code, and experiment results are stored separately by run ID. Separate directories reduce overwriting, but server data directories and output paths still need checking.

Exercise

Take two copies of the code from the same execution commit and run a short experiment with the same configuration. Compare the environments and output lists. If the results are not byte-identical, first judge whether it is a floating-point difference, an unfixed source of randomness, or actual inputs that already differ.

Then change just one configuration setting and confirm that the new run can be told apart from its metadata. Finally write a description others can follow to rerun it.

Common mistakes and how to fix them

The commit hash points to code from after the analysis. Save the execution commit and the analysis commit separately, and check the state of the code at launch.

Assuming the inputs are the same because the download address is the same. Save the hashes of the actual files and the split information.

Overwriting other work in the same directory when rolling back. Check out the old version in a separate directory, and check existing changes before restoring.

See Pro Git and the GitHub CLI manual.
