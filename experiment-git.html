3.1 Git 与 GitHub

学习目标

  1. 说明复现一次运行所需的代码、数据、配置、环境与产物身份，并据此设计运行元数据。
  2. 区分执行提交与分析提交，界定正式运行所需的代码状态，保证事前预测的时间顺序可核查。
  3. 在不影响现有工作的前提下检出旧版本复现运行，并诊断复现结果不一致的来源。

课后深入专题，约 45 分钟。

半年后得到一个好结果，提交编号可以把研究者带回当时的代码，但数据可能已经重新切分，依赖也可能已经升级。复现需要同时保存代码、数据与环境信息。

代码提交与版本记录

Git 提交记录受管理文件在某一时刻的内容。先查看差异再提交，正式运行从已提交的代码启动。GitHub 保存远端副本，便于协作和服务器取回代码。

常用操作不多：查看状态和差异，提交，推送或拉取。首次在自己的账号下建立仓库时，先确认可见范围，取得链接后再让执行机器获取代码。

建立本实验的 Git 仓库，先列出会纳入的文件。
忽略环境目录，凭据，大型数据与下载全文。代码和小型配置保留。
提交基线，记录完整提交号。若已有仓库，先查现状和未提交改动，再继续。

运行所需的其他身份记录

身份 记录内容
数据 来源、切分规则与实际输入哈希
配置 命令参数和解析后的最终配置
环境 Python 与库版本，设备及关键驱动
产物 运行编号，输出清单，哈希与完成状态

配置文件中的默认值也可能变化，因此应保存实际解析后的值。运行编号指向一次执行，提交号指向代码；同一提交可以产生多次运行。

代码状态与生成文件

启动器可以拒绝在代码存在未提交改动时运行正式实验。但结果目录写入后，仓库自然会出现改动。因此须事先界定检查范围：执行代码和配置必须固定，输出写入独立的运行目录，运行后的结果另行归档。

若某次提交同时包含预测和代码，事后分析另起提交，并引用执行提交。预测记录应带时间和输入版本，原件保留在私有历史中，不能通过事后修改把预测变成命中。

为本次运行生成 run_metadata.json，记录执行提交和已跟踪代码的改动状态。
数据哈希按实际读入文件计算。记录完整命令、配置与种子。
完成后生成产物清单。分析脚本若后来修改，保存新的分析提交。

旧版本的安全检出

需要比较旧代码时，在新目录中建立独立检出或工作树。当前目录可能有他人未提交的文件，应先查看状态再决定恢复范围。

并行实验各自使用独立的工作树和输出目录。代码合并由一位整合者负责，实验结果按运行身份并存。目录隔离可以减少覆盖，服务器上的数据目录与输出路径仍需检查。

练习

从同一执行提交取出两份代码，用相同配置运行一项短实验，比较环境与输出清单。若结果不完全相同，先判断原因是浮点差异、随机源未固定，还是实际输入已经不同。

再只改变一个配置，确认新运行可以通过元数据区分。最后写一段说明，使他人能据此重新运行。

常见错误与处理方法

提交号指向分析完成后的代码。 分别保存执行提交和分析提交，检查启动时的代码状态。

数据下载地址相同，即认为输入相同。 保存实际文件哈希和切分信息。

回退版本时覆盖同一目录中的其他工作。 在独立目录检出旧版本，恢复前检查现有改动。

参考资料：Pro Git 与 GitHub CLI 手册。

3.1 Git and GitHub

Learning outcomes

After this section, students should be able to:

  1. Specify the records of code, data, configuration, environment and outputs required to reproduce a computational result, and explain why a commit hash alone is insufficient.
  2. Separate execution commits from analysis commits and define the scope of clean-state checks so that the order of prediction, execution and analysis can be demonstrated.
  3. Reproduce a run from an independent checkout and diagnose the source of any difference between the two runs.

Extension reading and exercises, about 45 minutes.

A commit hash can return a researcher to the code that produced a result months earlier, yet the data may since have been re-split and the dependencies upgraded. Reproducibility requires the code, data and environment to be recorded together.

Recording code versions with commits

A Git commit records the content of each tracked file at that point. Review the diff before committing, and start full runs from committed code. GitHub keeps a remote copy, which supports collaboration and retrieval onto servers.

The routine operations are checking status, viewing diffs, committing, pushing and pulling. When creating a repository in one’s own account for the first time, confirm its visibility, obtain the link and only then let the executing machine fetch the code.

Set up a Git repository for this experiment and first list the files that will be included.
Ignore environment directories, credentials, large data and downloaded full texts. Keep code and small configuration files.
Commit a baseline and record the full commit hash. If a repository already exists, check its current state and uncommitted changes first, then continue.

Four further records for each run

Record Content
Data Source, split rule and hash of the actual input
Configuration Command parameters and the final parsed configuration
Environment Python and library versions, device and key drivers
Outputs Run ID, output list, hashes and completion status

Default values in configuration files can change, so the actual parsed values are saved. The run ID refers to one execution and the commit hash refers to code; one commit can produce many runs.

Clean state and generated files

A launcher can refuse to start a full experiment when the code has uncommitted changes. Once results are written, however, the repository necessarily becomes dirty. The scope of the check is therefore defined in advance: executed code and configuration must be fixed, outputs go to a separate run directory, and results are archived separately after the run.

If a commit contains the prediction and the code, post-hoc analysis receives its own commit that still refers to the execution commit. Record the time and input version of the prediction, keep the original in private history, and do not edit it afterwards to make it appear correct.

Generate run_metadata.json for this run, recording the execution commit and the change status of tracked code.
Compute data hashes from the files actually read. Record the full command, configuration and seeds.
Generate an output list when done. If the analysis script is changed later, save a new analysis commit.

Returning to an earlier version safely

To compare earlier code, create a separate checkout or worktree in a new directory. The current directory may contain another person’s uncommitted files, so check its status before deciding how much to restore.

Parallel experiments each have their own worktree and output directory. A single integrator is responsible for merging code, and experimental results are stored separately by run ID. Separate directories reduce the risk of overwriting, but server data directories and output paths still need to be checked.

Exercise

Take two copies of the code from the same execution commit and run a short experiment with the same configuration. Compare the environments and output lists. If the results are not byte-identical, determine whether the cause is a floating-point difference, an unfixed source of randomness, or inputs that already differ.

Then change one configuration setting and confirm that the new run can be distinguished from its metadata. Finally, write a description that would allow another person to rerun it.

Common errors and corrections

A commit hash that points to code written after the analysis. Record the execution commit and the analysis commit separately, and check the state of the code at launch.

Assuming identical inputs because the download address is the same. Record the hashes of the actual files and the split information.

Overwriting other work in the same directory when rolling back. Check out the earlier version in a separate directory, and check existing changes before restoring.

See Pro Git and the GitHub CLI manual.
