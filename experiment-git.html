3.1 Git 与 GitHub

课后深入，约 30 分钟。

Git 把文件夹在每次提交时的样子存成一个版本，GitHub 把这些版本存到网上。对用 Agent 做研究的人，它解决一个具体问题：Agent 改代码太快，你记不住哪个结果来自哪一版代码，也不敢放手让它大改，怕改坏了回不去。有了 Git，两件事都有了答案。

命令让 Agent 去敲。下面是用得上的几个概念，以及什么时候让它做什么。

五个动作

动作 是什么 什么时候让 Agent 做
提交 给文件夹当前的样子拍一张快照，附一句说明 每跑一次实验之前；每完成一件小事
推送 把本地的快照传到 GitHub 每天收工；要在服务器上用新代码时
拉取 把 GitHub 上的新快照取到本地或服务器 在服务器上跑实验之前
查看历史 看过去的快照和改了什么 想知道某个结果是哪版代码时
退回 把某个文件或整个文件夹恢复到某次快照 改坏了的时候

每次提交有一个编号，一串十六进制字符，平时用 Git 显示的前几位短编号就够了。这个编号就是代码版本的名字。

提交编号进结果

修改 run_experiment.py：启动时读取当前的 Git 提交编号，写进 results.csv 的每一行；
正式运行时，如果文件夹里有还没提交的改动，拒绝运行并提示先提交；冒烟测试不受这条限制。

这几行代码是整个实验可复查的基础。半年后审稿人问这个数字怎么来的，你查结果文件里的编号，切回那一版代码，用同样的数据和参数重跑一遍。数据放在哪，是哪个版本，也写进 README。

哪些东西不进仓库

.gitignore 列出不进仓库的文件。一般是：

  • 数据集和大的结果文件，它们放在服务器上或者单独的存储里；
  • 环境文件夹，比如 .venv/；
  • 密钥和含密码的配置，比如 .env；
  • 下载的论文 PDF。

GitHub 仓库默认可以设成私有，未发表的代码先放私有仓库。即使是私有仓库，密钥也不要进去：仓库以后可能公开，也可能加进新的合作者。

退回

改坏了不用慌：

run_experiment.py 改坏了，把它恢复到上一次提交的样子，其他文件不动。
我想看第 1 课那次结果对应的代码。列出最近十次提交，找到提交说明里有 baseline 的那次，告诉我那时的 run_experiment.py 和现在有什么不同。

放手让 Agent 大改代码之前，先让它提交一次。改得不好，一句话退回。

多个对话同时改

两个对话同时改同一个文件夹，会互相覆盖。要并行做两件事，用 Git 的工作树：同一个仓库在另一个文件夹里开一份副本，各改各的，最后合并。

用 git worktree 在 ../label-noise-lab-asym 开一个新分支 asym，我要在另一个对话里在那里做非对称噪声的实验。

Claude Code 桌面版新建对话时也可以直接选在工作树里开，效果相同。

提交说明

让 Agent 写提交说明时要求一句话说清做了什么，而不是改了哪些文件。好的说明：add noisy-validation early stopping。不好的说明：update run_experiment.py。半年后你按说明找版本，只有前一种找得到。

练习

在练习 3 的仓库里，让 Agent 故意把损失函数改错，跑一次冒烟测试看到结果异常，再让它退回到上一次提交，确认结果恢复。

最容易出错的地方

没提交就跑。 结果不错，但代码已经又改了三次，回不去了。在实验脚本里检查有没有未提交的改动，有就拒绝运行。

密钥进了仓库。 API Key 写在配置文件里一起提交，推到 GitHub 后即使删掉，历史里还在。密钥放进 .gitignore 列出的文件；一旦推上去，立刻作废那个 Key 重新生成。

数据进了仓库。 几 GB 的数据集被提交，仓库推不上去，或者每次拉取都很慢。数据进 .gitignore，仓库里只放下载数据的脚本。

延伸阅读

  • GitHub CLI 手册
  • Pro Git：中文版，前三章足够。

3.1 Git and GitHub

Self-study, about 30 minutes.

Git saves a version of your folder at each commit. GitHub stores those versions online. For research with agents, this solves a concrete problem: the agent changes code so quickly that you cannot remember which result came from which version. You also hesitate to let it make big changes for fear you cannot go back. Git answers both concerns.

Let the agent type the commands. Here are the concepts you need, and when to ask it to act.

Five actions

Action What it is When to ask the agent
Commit Take a snapshot of the folder, with a short description Before every experiment; after each small task
Push Send local snapshots to GitHub At the end of the day; when the server needs new code
Pull Get new snapshots from GitHub onto your computer or server Before running an experiment on the server
View history See past snapshots and what changed To find which code version produced a result
Restore Return a file or the whole folder to a snapshot When a change breaks something

Each commit has an ID, a string of hexadecimal characters. The short ID Git displays is usually enough. It is the name of the code version.

Put the commit ID in results

Change run_experiment.py: read the current Git commit ID at startup and write it into every row of results.csv.
For a full run, refuse to run if the folder has uncommitted changes and prompt me to commit first. Exempt smoke tests from this rule.

These few lines are the foundation for checking an experiment later. Six months on, if a reviewer asks where a number came from, read the ID in the result file, return to that code version, and rerun with the same data and parameters. Put the data’s location and version in the README too.

What stays out of the repository

.gitignore lists files to leave out. Usually:

  • Datasets and large result files, kept on the server or in separate storage;
  • Environment folders such as .venv/;
  • Secrets and configuration containing passwords, such as .env;
  • Downloaded paper PDFs.

You can make a GitHub repository private. Keep unpublished code in a private repository first. Even in a private repository, leave secrets out: you may later make it public or add collaborators.

Going back

If a change breaks something, don’t panic:

run_experiment.py is broken. Restore it to the last commit, leaving other files alone.
I want to see the code that produced Session 1's result. List the last ten commits, find the one with baseline in its message, and tell me how its run_experiment.py differs from the current one.

Before letting the agent make a big code change, have it commit. If the change is poor, one line takes you back.

Several conversations editing at once

Two conversations editing the same folder overwrite each other. For two jobs in parallel, use Git worktrees: open a copy of the same repository in another folder, edit separately, then merge.

Use git worktree to open a new branch asym in ../label-noise-lab-asym. I will use another conversation there for asymmetric-noise experiments.

When starting a conversation in Claude Code desktop, you can also choose to open it in a worktree. The effect is the same.

Commit messages

Ask the agent for a one-sentence description of what it did, rather than which files it changed. Good: add noisy-validation early stopping. Poor: update run_experiment.py. Six months later, only the first helps you find the version.

Exercise

In the repository from Exercise 3, have the agent deliberately break the loss function. Run a smoke test to see the abnormal result, then restore the last commit and check that the result returns to normal.

Where agents go wrong most

Running without a commit. The result is good, but the code has changed three more times and you cannot go back. Check for uncommitted changes in the experiment script and refuse to run if there are any.

Secrets in the repository. An API key in a configuration file gets committed and pushed. Deleting it leaves it in the history. Keep secrets in files listed in .gitignore. If a key is pushed, revoke it at once and generate a new one.

Data in the repository. A dataset of several GB prevents a push or makes every pull slow. Put data in .gitignore; keep only the script to download it in the repository.
