5 安全控制

给工作台画清信息流和权限边界，用无害测试验证它。完成一张能力表、一次允许与拒绝测试，以及两道有明确覆盖范围的自动检查。

选修课。课前完成准备，课上 60 分钟，课后先复习再选做深入。

课前预备 · 课上一小时 · 课后复习与拔高

同一个 Agent 能读网页、改代码，还能登录服务器。它从网页里读到的内容，怎样才不会获得执行任务的权力？需要通过实际动作与凭据权限限制这种影响。

本课使用普通测试文件和空凭据样例验证权限。涉及攻击评测时，攻击样本在专门服务器环境中生成与运行，课程页面只讲威胁模型和防御指标。

预留 20 至 40 分钟，提前处理组件下载。

课前工具准备。 检查 Python 与 Git，确认 Bash 和扫描器可用，备份现有配置。角色权限怎样划分，配置怎样合并，沙箱怎样实测，课堂一起处理。

备份现有项目配置到自己的课前目录，准备一个无真实凭据的一次性演示目录。
把系统，Agent 版本，组件状态和错误信息写到 preflight.md，不填写任何密钥值。

课上一小时

先看一条数据怎样流动，5 分钟

先核对 preflight.md 的组件与备份记录，再沿一条资料流动找权限边界。

第 2 课取回的论文经阅读助手变成笔记，再进入写作助手，最后到发布任务。若笔记保留了外部操作要求，换成内部文件也没有自动变可信。

所以资料要带来源，进入可执行任务前再检查动作是否由用户任务授权。读取外部资料的进程尽量没有发布凭据，发布器只接收经过选取的产物与固定目标。

三层权限控制，10 分钟

权限规则决定 Agent 能调用哪项工具。进程隔离限制被运行的代码能接触哪些文件和网络。凭据服务或远端账号限制最终能做什么。

其中任何一层放得很宽，其他层都要承担更大负担。允许运行任意 Python 脚本，意味着被允许的脚本也能做文件与网络操作；仅禁止 Agent 的直接读取工具还管不到这些路径。

Hooks 可在特定入口加检查。它的能力取决于挂在哪个事件，失败时是否阻断，执行者能否绕过。先说覆盖范围，再测真实行为。

练习一，按角色配权限，15 分钟

为阅读，实验，审阅和发布分别写能力表。
阅读者只向自己的笔记目录输出，实验者只在执行目录和已分配资源内运行。
审阅者只读冻结版本并输出意见，发布者只接收批准的产物和目标。
逐项说明文件范围、网络范围与凭据来源，再对照当前官方配置生成候选设置。

模型名称可以替换，权限跟任务角色走。共享写入仍指定一个整合者。

练习二，实测一条允许和一条拒绝，10 分钟

在一次性演示目录内准备普通测试文件，列出预期允许和拒绝的动作。
使用当前生效的权限和沙箱分别执行，记录实际结果、错误码与配置来源。
再从另一个受控入口测试同一边界，例如直接文件工具与子进程读取。
若某项没有真正隔离，写明缺口，修正后重测。

测试内容保持无害，越界目标由自己预先创建。系统权限、联网隔离和远端账号分别测试，不能从其中一项推断全部已生效。

练习三，两道自动检查的覆盖范围，15 分钟

运行包内 Hook 验证，再查看数字核查与推送前扫描各由哪个事件触发。
用普通测试输入分别触发成功，发现问题，检查器失败三种分支。
确认修改后检查能反馈问题，发布前检查失败会阻断。
把未覆盖的入口与最后一道全量检查写进运行说明。

扫描器测试使用失效样例或替身，输出隐藏疑似值。真实凭据由本地或服务端设施管理，Agent 只拿到完成任务所需的权限。

检查与工作台小结，5 分钟

常见错误与处理方法

笔记由自己写，就认为可信。 来源标签保留到后续步骤，执行动作重新核对任务授权。

拒绝读取文件，却允许同进程任意脚本。 检查子进程、网络和凭据边界，必要时换隔离用户或容器。

Hook 单元测试通过，就宣布沙箱安全。 分别记录脚本分支测试和实际系统边界测试。

沙箱外的 SSH 例外没有另管。 本机限制到不了服务器，远端账号与作业权限单独配置。

工作台小结

安全配置现在有可观察的含义：哪项任务能读什么，哪个进程持有什么凭据，哪些动作实际被拒绝。扩展工具以后重新沿信息流检查，测试记录跟配置版本一起保存。

课后复习与拔高

先复盘，15 分钟

从课堂实际配置重画信息流：外部材料怎样进入笔记，哪个进程能调用工具，哪里持有凭据。给每条边标上控制与一次测试结果，把尚未测试的边写到 review-after-class.md。

正反例辨析，20 分钟

甲记录文件读取工具拒绝访问，于是宣称该文件已隔离；同一进程却仍能运行任意脚本。乙分别测试文件工具和受控子进程，并记录配置版本与实际拒绝结果。指出两份记录各证明了什么。再判断 Hook 分支测试全部通过，是否已经证明本机沙箱与远端 SSH 都执行了同一边界。

先写覆盖范围，再看对照思路

甲只测到一个入口。乙把进程路径也纳入观察，仍需按实际控制逐项验证。Hook 分支、系统隔离和远端账号是不同测试对象，应各留有效配置与行为证据。

沿课堂往深处做

先在自己的练习环境补齐允许与拒绝测试，再选一条路径。复杂配置有不明处时保留最小复现，在后续答疑中共同检查。

5 Safety controls

Map the information flow and permission boundaries of your workbench, and verify them with harmless tests. Complete a capability table, one test of an allowed and a denied action, and two automatic checks with a clear scope of coverage.

Elective. Prepare before class, spend 60 minutes in class, then review and choose an optional extension.

Before class · In class · After class: review and extension

The same agent can read web pages, change code and log in to servers. How do you keep what it reads on a web page from gaining the power to carry out tasks? Enforce the boundary through controls on actions and credentials.

This lesson verifies permissions with ordinary test files and dummy credentials. Where attack evaluation is involved, attack samples are generated and run in a dedicated server environment, and the course pages cover only the threat model and defense metrics.

Before class

Allow 20 to 40 minutes, and deal with component downloads in advance.

Before-class setup. Check Python and Git, confirm that Bash and the scanner work, and back up your existing configuration. How to divide role permissions, how configuration merges and how to test the sandbox are handled together in class.

Unzip this lesson's materials. Only read settings.example.json, config.example.toml and README.md; do not copy them to where they take effect yet.
Check that Python, Git, Bash and gitleaks return versions; install anything missing from the official sources.
Check my system and components against the table below and download what is missing in advance; note system policy problems so we can judge them together in class.
Back up the existing project configuration to my own pre-class directory, and prepare a disposable demonstration directory with no real credentials.
Write the system, agent versions, component status and error messages into preflight.md. Do not fill in any key values.

Claude’s shell sandbox uses different mechanisms on different operating systems. The component check only confirms that things exist; actual isolation is tested in class. The table below is based on the official sandboxing guide.

In class

Trace information through the workbench, 5 minutes

First check the components and backup record in preflight.md, then follow one flow of material to find the permission boundaries.

Papers retrieved in Lesson 2 become notes through the reading helper, then go to the writing helper, and finally to the publishing task. If a note preserves an instruction from an external source, it does not automatically become trustworthy just because it is now an internal file.

Keep source information with the material, and before it enters an executable task, check whether the action was authorized by the user’s task. Processes that read external material should hold no publishing credentials where possible, and the publisher accepts only selected products and a fixed target.

Three layers of control, 10 minutes

Permission rules decide which tools the agent can call. Process isolation limits which files and networks the code being run can touch. A credential service or remote account limits what can ultimately be done.

If any one layer is configured too broadly, the other layers carry a heavier load. Allowing any Python script to run means an allowed script can also do file and network operations; forbidding only the agent’s direct read tool does not cover those paths.

Hooks can add checks at specific entry points. What they can do depends on which event they are attached to, whether failures block the action, and whether the executing process can bypass them. State the coverage first, then test the real behavior.

Exercise 1: assign permissions by role, 15 minutes

Write a capability table for each of reading, experimenting, reviewing and publishing.
The reader outputs only to its own notes directory; the experimenter runs only in the execution directory and on allocated resources.
The reviewer reads only frozen versions and outputs comments; the publisher accepts only approved products and targets.
For each, state the file scope, network scope and credential source, then generate candidate settings against the current official configuration.

Model names can be swapped; permissions follow the task role. Assign one integrator to handle shared writes.

Exercise 2: test one allowed and one denied action, 10 minutes

Prepare ordinary test files in a disposable demonstration directory and list the actions expected to be allowed and denied.
Execute each with the permissions and sandbox currently in effect, recording the actual result, the error code and the source of the configuration.
Then test the same boundary from another controlled entry point, for example the direct file tool versus a read from a subprocess.
If something is not really isolated, write down the gap, fix it and retest.

Keep the test content harmless, and create the out-of-bounds target yourself in advance. System permissions, network isolation and remote accounts are tested separately; you cannot infer from one of them that all are in effect.

Exercise 3: test the coverage of two checks, 15 minutes

Run the Hook verification in the package, then see which event triggers the number checker and which triggers the pre-push scan.
Use ordinary test inputs to trigger three branches for each: success, problem found, and checker failure.
Confirm that the check after an edit reports problems back, and that a failed pre-publication check blocks.
Write the entry points not covered, and the final full check, into the run instructions.

Scanner tests use invalid samples or stand-ins, and the output hides suspected values. Real credentials are managed by local or server-side facilities, and the agent gets only the permissions needed to complete its task.

Check and workbench summary, 5 minutes

Common mistakes and how to fix them

Trusting a note because you wrote it yourself. Keep the source label in later steps, and recheck task authorization before executing actions.

Denying file reads but allowing any script in the same process. Check the subprocess, network and credential boundaries, and switch to an isolated user or container where needed.

Declaring the sandbox safe because the Hook unit tests passed. Record script branch tests and actual system boundary tests separately.

SSH exceptions outside the sandbox are not managed separately. Local restrictions do not reach the server; remote accounts and job permissions are configured on their own.

Workbench summary

The safety configuration can now be assessed through observable behavior: which task can read what, which process holds which credential, and which actions are actually denied. After adding tools, check along the information flow again, and save test records with the configuration version.

After class: review and extension

Review first, 15 minutes

Redraw the information flow from the configuration actually used in class: how external material enters notes, which process can call tools, and where credentials are held. Label each edge with its control and one test result, and write the edges not yet tested into review-after-class.md.

Compare the examples, 20 minutes

A records that the file read tool was denied access, and so claims the file is isolated; yet the same process can still run any script. B tests the file tool and a controlled subprocess separately, and records the configuration version and the actual denials. Say what each record proves. Then judge whether all Hook branch tests passing already proves that both the local sandbox and remote SSH enforce the same boundary.

Write the coverage first, then see the comparison notes

A tested only one entry point. B brought the process path into view as well, but each actual control still needs verifying one by one. Hook branches, system isolation and remote accounts are different test targets, and each should keep its own effective configuration and behavioral evidence.

Further study

First complete the allowed and denied tests in your own exercise environment, then choose one path. Where complex configuration is unclear, keep a minimal reproduction and check it together in a later Q&A session.
