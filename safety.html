5 安全控制

本节课目标

完成本节课堂训练及课后练习后，学生应能：

  1. 沿信息流识别外部内容、工具调用与持久记录之间的信任边界，说明格式整理不会改变来源的可信度。
  2. 按任务角色设计文件、网络与凭据权限，说明权限规则、进程隔离与凭据控制三层各自限制的对象。
  3. 设计允许、拒绝及跨入口测试，说明每类测试结果能够支持何种边界判断，以及不能支持何种判断。
  4. 评价 Hook 与权限策略的事件覆盖、失败时的行为及其局限。

课堂在一次性演示目录中完成角色能力表、一组允许与拒绝测试和 Hook 分支检查；更换入口与执行端后的复测在课后完成。

选修课。课前完成准备，课堂 60 分钟，课后完成复习、独立实践与迁移评价，另可选做深入专题。

课前准备 · 课堂教学 · 课后复习与扩展

本节讨论的问题是：同一个 Agent 既能读取网页、修改代码，又能登录服务器时，它从网页中读到的内容怎样才不会获得执行任务的权力。这种影响需要通过实际动作与凭据权限加以限制。

本节使用普通测试文件和空凭据样例验证权限。涉及攻击评测时，攻击样本只在专门的服务器环境中生成与运行，课程页面只讨论威胁模型和防御指标。

课堂教学

数据流与信任边界，5 分钟

先核对 preflight.md 中的组件与备份记录，再沿一条数据流识别权限边界。

第 2 课取回的论文经阅读助手整理为笔记，再进入写作助手，最后到达发布任务。若笔记中保留了外部内容提出的操作要求，即使它已成为内部文件，也不会因此变得可信。

因此资料须带有来源标记，进入可执行任务之前，还要检查相应动作是否由用户任务授权。读取外部资料的进程尽量不持有发布凭据，发布器只接收经过选取的产物和固定目标。

三层权限控制，10 分钟

权限规则决定 Agent 能调用哪些工具。进程隔离限制被运行的代码能接触哪些文件和网络。凭据服务或远端账号限制最终能产生哪些效果。

任何一层放得过宽，其他各层都要承担更大的负担。允许运行任意 Python 脚本，意味着被允许的脚本也能进行文件与网络操作；仅禁止 Agent 直接读取文件的工具，无法限制这些路径。

Hooks 可在特定入口增加检查。其能力取决于挂接在哪个事件上、失败时是否阻断，以及执行者能否绕过。应先说明覆盖范围，再测试实际行为。

练习一：按角色配置权限，15 分钟

为阅读，实验，审阅和发布分别写能力表。
阅读者只向自己的笔记目录输出，实验者只在执行目录和已分配资源内运行。
审阅者只读冻结版本并输出意见，发布者只接收批准的产物和目标。
逐项说明文件范围、网络范围与凭据来源，再对照当前官方配置生成候选设置。

模型名称可以替换，权限随任务角色而定。共享写入仍指定一位整合者。

练习二：允许与拒绝行为的实测，10 分钟

在一次性演示目录内准备普通测试文件，列出预期允许和拒绝的动作。
使用当前生效的权限和沙箱分别执行，记录实际结果、错误码与配置来源。
再从另一个受控入口测试同一边界，例如直接文件工具与子进程读取。
若某项没有真正隔离，写明缺口，修正后重测。

三类测试支持的判断各不相同。允许测试成功，说明合法任务在当前配置下可以完成，即限制没有妨碍正常工作，但不说明边界存在。拒绝测试成功，说明预定的越界动作在这一入口、这一路径和这一配置版本下被阻止，不能推广到其他入口。跨入口测试检验同一边界在另一条路径上是否仍然成立，例如文件工具被拒绝后，子进程是否也无法读取同一文件。

测试内容须保持无害，越界目标由自己预先创建。系统权限、联网隔离和远端账号分别测试，不能从其中一项推断全部已经生效。

练习三：自动检查的覆盖范围，15 分钟

运行包内 Hook 验证，再查看数字核查与推送前扫描各由哪个事件触发。
用普通测试输入分别触发成功，发现问题，检查器失败三种分支。
确认修改后检查能反馈问题，发布前检查失败会阻断。
把未覆盖的入口与最后一道全量检查写进运行说明。

扫描器测试使用失效样例或替身，输出时隐藏疑似值。真实凭据由本地或服务端设施管理，Agent 只获得完成任务所需的权限。

课堂检查与本节小结，5 分钟

常见错误与处理方法

笔记由自己生成，即认为内容可信。 来源标记保留到后续步骤，执行动作前重新核对任务授权。

拒绝了文件读取工具，却允许同一进程运行任意脚本。 检查子进程、网络和凭据边界，必要时改用隔离用户或容器。

Hook 单元测试通过，即宣布沙箱安全。 脚本分支测试与实际系统边界测试分别记录。

沙箱外的 SSH 例外未单独管理。 本机限制无法作用于服务器，远端账号与作业权限须单独配置。

本节小结

安全配置现在有了可观察的含义：哪项任务能读取什么，哪个进程持有什么凭据，哪些动作被实际拒绝。增加工具后应重新沿信息流检查，测试记录与配置版本一并保存。

课后复习与扩展

概念复习、正反例分析及能力达成评价中的独立实践与迁移任务为本节必做内容；其余深入专题按研究需要选做。

概念复习，15 分钟

根据课堂的实际配置重新画出信息流：外部材料怎样进入笔记，哪个进程能调用工具，凭据保存在何处。为每条边标注控制方式和一次测试结果，把尚未测试的边写入 review-after-class.md。

正反例辨析，20 分钟

记录甲：文件读取工具被拒绝访问，因此宣称该文件已被隔离；但同一进程仍能运行任意脚本。记录乙：分别测试文件工具和受控子进程，并记录配置版本与实际拒绝结果。指出两份记录各自证明了什么。再判断：Hook 分支测试全部通过，是否已经证明本机沙箱与远端 SSH 都执行了同一边界。

先写出覆盖范围，再查看参考思路

甲只测试了一个入口。乙把进程路径也纳入观察，但仍需按实际控制逐项验证。Hook 分支、系统隔离和远端账号是不同的测试对象，应分别保留有效配置与行为证据。

能力达成评价

评价分三个层次。课堂训练层面，检查角色能力表是否逐项写明文件、网络与凭据范围，测试记录是否注明入口、配置版本和实际结果，学生能否说明每条允许或拒绝结果支持的具体判断。课后独立完成层面，学生在另一入口或执行端复测同一边界，并说明结果相同或不同的原因。迁移层面，学生为自己研究中的一个工具链画出信息流，指出未经测试的边，设计相应的允许、拒绝和跨入口测试，并说明 Hook 在其中覆盖哪些事件、无法覆盖哪些路径。评价依据为权限范围的合理性、测试覆盖及边界判断与测试证据的对应关系。

5 Safety controls

Learning outcomes

After completing this session and its review and extension work, students should be able to:

  1. Identify the trust boundaries between external content, tools, credentials and persistent records in an agent-based research workflow.
  2. Design permissions and isolation for each role according to its responsibilities, specifying file, network and credential scope.
  3. Verify a boundary through paired allowed and denied tests, and through tests at more than one entry point, stating which conclusion each test supports.
  4. Evaluate the coverage and limitations of Hooks and permission policies, distinguishing tests of script logic from tests of the actual system boundary.

The outcomes are assessed at three levels. In class, students build a role capability table, test one allowed and one denied action, and test the branches of two automatic checks. After class, they retest the same boundary through a different entry point or execution environment. The extension paths apply the same analysis to sandbox configuration and to Hooks and credential handling.

Elective. Preparation before class, a 60-minute class session, then required review, independent work and transfer assessment, with optional further study.

Preparation · Class session · Review and extension

A single agent may read web pages, modify code and sign in to servers. The central problem of this session is how to prevent content read from an external source from acquiring the authority to carry out tasks. The boundary is enforced through controls on actions and credentials, not through the agent’s judgment alone.

The session verifies permissions with ordinary test files and dummy credentials. Where attack evaluation is involved, attack samples are generated and run in a dedicated server environment, and the course pages cover only the threat model and defense metrics.

Class session

Tracing information through the workflow, 5 minutes

Check the components and backup record in preflight.md, then follow one flow of material to identify the permission boundaries.

Papers retrieved in Session 2 become notes through the reading helper, then pass to the writing helper and finally to the publishing task. If a note preserves an instruction from an external source, the instruction does not become trustworthy because it now resides in an internal file.

Source information stays with the material, and before the material enters an executable task, the action is checked against the user’s task authorization. Processes that read external material should hold no publishing credentials where possible, and the publisher accepts only selected products and a fixed target.

Three layers of control, 10 minutes

Permission rules determine which tools the agent can call. Process isolation limits which files and networks the executed code can reach. A credential service or remote account limits what can ultimately be done.

If any one layer is configured too broadly, the other layers carry more of the load. Allowing any Python script to run means that an allowed script can also perform file and network operations; forbidding only the agent’s direct read tool does not cover those paths.

Hooks can add checks at specific entry points. What they achieve depends on the event they are attached to, whether a failure blocks the action, and whether the executing process can bypass them. The intended coverage is stated first, and the actual behavior is then tested.

Exercise 1: assigning permissions by role, 15 minutes

Write a capability table for each of reading, experimenting, reviewing and publishing.
The reader outputs only to its own notes directory; the experimenter runs only in the execution directory and on allocated resources.
The reviewer reads only frozen versions and outputs comments; the publisher accepts only approved products and targets.
For each, state the file scope, network scope and credential source, then generate candidate settings against the current official configuration.

Model names can be exchanged; permissions follow the task role. A single integrator is assigned to handle shared writes.

Exercise 2: testing one allowed and one denied action, 10 minutes

Prepare ordinary test files in a disposable demonstration directory and list the actions expected to be allowed and denied.
Execute each with the permissions and sandbox currently in effect, recording the actual result, the error code and the source of the configuration.
Then test the same boundary from another controlled entry point, for example the direct file tool versus a read from a subprocess.
If something is not really isolated, write down the gap, fix it and retest.

The two tests support different conclusions. A successful allowed action shows that the configuration does not prevent the legitimate work it is meant to permit. A denied action shows that the boundary held for that action through that entry point under the configuration in effect; it does not show that the same action is blocked through other entry points. A test through a second entry point is therefore needed before the boundary can be described more generally. Test content remains harmless, and the out-of-bounds target is created in advance by the student. System permissions, network isolation and remote accounts are tested separately; none can be inferred to be in effect from a test of another.

Exercise 3: testing the coverage of two checks, 15 minutes

Run the Hook verification in the package, then see which event triggers the number checker and which triggers the pre-push scan.
Use ordinary test inputs to trigger three branches for each: success, problem found, and checker failure.
Confirm that the check after an edit reports problems back, and that a failed pre-publication check blocks.
Write the entry points not covered, and the final full check, into the run instructions.

Scanner tests use invalid samples or stand-ins, and the output masks suspected values. Real credentials are managed by local or server-side facilities, and the agent receives only the permissions needed for its task.

Common errors and summary, 5 minutes

Common errors and corrections

Trusting a note because it was written within the project. Keep the source label in later steps, and recheck task authorization before actions are executed.

Denying file reads while allowing any script in the same process. Check the subprocess, network and credential boundaries, and use an isolated user or container where needed.

Concluding that the sandbox is safe because the Hook unit tests passed. Record script branch tests and actual system boundary tests separately.

Leaving SSH exceptions outside the sandbox unmanaged. Local restrictions do not extend to the server; remote accounts and job permissions are configured separately.

Method summary

The safety configuration can now be assessed through observable behavior: which task can read what, which process holds which credential, and which actions are actually denied. When tools are added, the information flow is checked again, and test records are saved with the configuration version.

Review and extension

Conceptual review, analysis of contrasting examples, and the independent and transfer tasks specified in Assessment are required for this session. Other extension topics are optional, except for the required readings identified below.

Unaided review, 15 minutes

Redraw the information flow from the configuration actually used in class: how external material enters notes, which process can call tools and where credentials are held. Label each edge with its control and one test result, and record the edges not yet tested in review-after-class.md.

Analysis of contrasting examples, 20 minutes

Record A states that the file read tool was denied access and claims on that basis that the file is isolated, although the same process can still run any script. Record B tests the file tool and a controlled subprocess separately and records the configuration version and the actual denials. State what each record demonstrates. Then judge whether the passing of all Hook branch tests demonstrates that both the local sandbox and remote SSH enforce the same boundary.

Record the coverage before reading the commentary

A tested only one entry point. B also brought the process path into view, but each actual control still needs to be verified individually. Hook branches, system isolation and remote accounts are different objects of testing, and each should keep its own effective configuration and behavioral evidence.

Further study

First complete the allowed and denied tests in your own exercise environment, then choose one path. Where complex configuration remains unclear, keep a minimal reproduction and examine it in a later question session.

Path Next task Deliverable
5.1 Permissions and sandboxes 60 minutes: retest after changing the entry point and execution environment Capability table, configuration version and behavior matrix
5.2 Hooks and secret management 60 minutes: check event coverage and blocking on failure Branch records and a full check at a fixed delivery entry point

Finally, verify with one ordinary task that legitimate work can still be completed, then attempt one predefined out-of-bounds action. The two results together constitute the acceptance check.

Assessment

Attainment of the outcomes is judged from the student’s account of what each test shows. Students should be able to identify, for a given information flow, where untrusted content could acquire authority; justify each role’s file, network and credential scope; explain what the allowed test and the denied test each support, and why a denial at one entry point does not establish isolation; and state what the Hook tests cover and what they leave untested. Transfer is assessed by retesting the same boundary through a different entry point or execution environment and reporting where the observed permissions differed from the configured intention.
