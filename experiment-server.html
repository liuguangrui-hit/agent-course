3.2 服务器与后台任务

学习目标

  1. 设计以唯一运行编号为依据的启动与查询机制，在状态未知时避免重复执行。
  2. 依据进程状态、退出码、产物清单和数值有效性判断任务是否完成，区分成功、失败与未知。
  3. 依据执行记录恢复或重跑任务，并说明资源分配和数据位置的约束。

课后深入专题，约 50 分钟。

通过 SSH 启动实验后连接中断，此时无法确定任务是没有启动，还是已在服务器上运行。直接重试可能多运行一份。后台执行的首要要求，是能够查询并确认任务状态。

机器与目录的确认

沿用实验室的 SSH 密钥与网络方案，为主机设置简短别名，并为连接设置超时和心跳。首次连接时核对主机身份，再确认用户、工作目录与资源分配。

Host lab
    HostName lab.example.edu
    User researcher
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

示例地址须替换为自己的主机。密码和私钥保存在本地认证设施中。Tailscale 或学校 VPN 只解决连接路径，服务器的使用权限和集群调度规则仍须遵守。

以运行编号启动

每次实验先分配唯一的运行编号，配置和日志放入对应目录。启动器收到同一编号时，先检查是否已有运行、完成或失败的记录；网络重试据此决定继续查询还是重新提交。

集群配有调度器时，优先使用作业编号与状态接口。普通实验室机器可以使用 tmux，由运行脚本负责写入退出码和完成清单。启动返回作业标识后，Agent 即可结束当前等待。

为本轮准备独立目录，保存配置与执行提交。
启动前检查该运行编号是否已存在。启动后立即返回任务标识。
实验脚本把日志、退出码和产物清单写入本轮目录，只有校验完整后才写完成状态。
连接失败时先按运行编号查询，确认未启动后再提交。

状态与日志检查

日志长时间不变，可能是计算耗时，也可能是进程卡住。先查看进程或作业状态，再结合心跳和各阶段的预期时长判断。监视器记录最近一次检查时间，并分别报告成功、失败和状态未知。

日志中出现一行 done，仍须核对退出码、预期行数和数值有效性。程序可能在写出部分结果后失败，输出文件存在不足以判定任务完成。

监视器的检查间隔按任务时长设定。短演示可以较频繁，数小时的实验通常隔几分钟检查一次；任务结束后停止监视。

依据执行记录恢复

实验支持恢复时，checkpoint 应记录训练状态、随机状态与优化器状态。续跑代码须确认数据与配置一致。只能从头重跑时，新建运行编号，保留失败轮次及其与重跑的关系。

连接恢复后读取实际状态，不能凭上一段对话推断进度。停止任务时，按已确认的作业编号或进程编号操作，并先区分任务进程与共享服务。

资源与数据留在执行端

先确认资源分配，再启动实验。观察到 GPU 空闲只是一次观测，不能说明它已经分配给本任务。共享集群遵循调度器规则，普通服务器按组内约定占用资源。

数据尽量在服务器上直接获取，摘要与分析也在服务器上生成。只取回必要的小型结果、元数据和图片；模型权重等大文件记录明确的位置与校验信息。

练习

启动本课的一个短运行，中途断开终端，再从新会话按运行编号查询。模拟一次状态未知的情形：假设启动回执丢失，检查是否会重复启动。

提交一张状态表，记录每次查询所见的进程、退出码与产物。据此说明何时可以安全重试，何时需要先行核实。

常见错误与处理方法

启动未收到回执就再次提交。 先按运行编号查询执行端，避免重复消耗资源。

日志停止更新就终止任务。 结合阶段时长与进程状态，先判断任务停在哪一步。

恢复时更换了配置，仍沿用旧编号。 身份改变时新建运行，并保留续跑或重跑关系。

3.2 Servers and background jobs

Learning outcomes

After this section, students should be able to:

  1. Design a launch procedure based on unique run identifiers, so that a job’s status can be queried after a lost connection without starting a duplicate run.
  2. Determine whether a background job is running, complete or failed from process status, exit codes and verified outputs rather than from logs alone.
  3. Decide between resuming and rerunning a failed job, and record the relationship between the original run and its successor.

Extension reading and exercises, about 50 minutes.

If an SSH connection drops while an experiment is being started, it is unclear whether the job never started or is already running on the server. A simple retry may start a second copy. Background execution must first resolve this uncertainty.

Confirming the machine and directory

Use the laboratory’s SSH keys and network setup, give the host a short name, and set a timeout and keepalive for the connection. On first connection, check the host identity, then confirm the user, the working directory and the resource allocation.

Host lab
    HostName lab.example.edu
    User researcher
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

Replace the example address with your own host. Passwords and private keys remain in the local authentication setup. Tailscale or a university VPN provides only connectivity; the server’s usage permissions and the cluster’s scheduling rules still apply.

Launching with a run ID

Before each experiment, assign a unique run ID and place its configuration and logs in the corresponding directory. When the launcher receives an existing ID, it first checks for a running, finished or failed record. A retry after a network failure uses this check to decide whether to continue querying or to resubmit.

When the cluster has a scheduler, its job IDs and status interface are preferred. On an ordinary laboratory machine, tmux can be used, with the run script responsible for writing the exit code and the completion list. Once the launch returns a job identifier, the agent no longer needs to wait.

Prepare a separate directory for this round, saving the configuration and execution commit.
Before launching, check whether this run ID already exists. After launching, return the job identifier immediately.
The experiment script writes the log, exit code and product list into this round's directory, and writes the completion status only after verifying they are complete.
If the connection fails, first query by run ID, and resubmit only after confirming it did not start.

Checking status as well as logs

A silent log may indicate a long computation or a stalled process. First check the process or job status, then interpret it together with the heartbeat and the expected duration of the current stage. The monitor records the time of the last check and reports success, failure and unknown status separately.

Even when a log line reports completion, check the exit code, the expected number of rows and the validity of the values. A program can fail after writing part of its results, so the existence of an output file is not sufficient evidence of completion.

The monitor’s check interval is set according to job length. A short demonstration can be checked more often; an experiment of several hours is usually checked every few minutes. Monitoring stops when the job ends.

Recovering from run records

When an experiment can resume, the checkpoint records the training state, the random state and the optimizer. The resuming code must confirm that the data and configuration match. When the run can only be restarted from the beginning, assign a new run ID and record the failed round and its relationship to the rerun.

When the connection is restored, read the recorded status rather than inferring progress from the previous conversation. When stopping a job, act on a confirmed job ID or process ID, and first distinguish the job’s processes from shared services.

Keeping resources and data on the execution host

Confirm the resource allocation before starting the experiment. An idle GPU is an observation; it does not guarantee that the GPU is allocated to this job. On a shared cluster, follow the scheduler; on an ordinary server, agree usage with the research group.

Obtain data directly on the server wherever possible, and produce summaries and analyses there as well. Transfer back only the necessary small results, metadata and figures; large files such as model weights remain in place, with a clear location and checksum.

Exercise

Start a short run from this session, disconnect the terminal partway through, then query by run ID from a new session. Simulate an unknown status by assuming that the launch reply was lost, and check whether the job would be launched twice.

Submit a status table recording the process, exit code and products observed at each query. From the table, explain when a retry is safe and when verification must come first.

Common errors and corrections

Resending a launch because no reply arrived. First query the executor by run ID, to avoid consuming resources twice.

Terminating a job because its log has stopped changing. Combine the stage duration with the process status, and first determine where the job has stalled.

Changing the configuration on recovery while keeping the old ID. When the configuration or other run details change, create a new run and record its relationship to the old one as a resume or a rerun.
