3.2 服务器与后台任务

课后深入，约 50 分钟。

SSH 启动实验后连接断了。任务究竟没启动，还是已经在服务器上跑？直接重试可能多跑一份。后台执行首先要能查询并确认任务状态。

先确认机器与目录

沿用实验室的 SSH 密钥与网络方案，给主机起短名，连接设置超时和心跳。第一次连接核对主机身份，再确认用户、工作目录与资源分配。

Host lab
    HostName lab.example.edu
    User researcher
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

示例地址需替换成自己的主机。密码和私钥保留在本地认证设施中。Tailscale 或学校 VPN 只解决连接路径，服务器的使用权限和集群调度规则仍要遵守。

用运行编号启动

每次实验先分配唯一运行编号，把配置和日志放到对应目录。启动器收到同一编号时，先查是否已有运行、完成或失败记录。网络重试据此决定继续查询还是重新提交。

集群有调度器时，优先使用作业编号与状态接口。普通实验室机器可用 tmux，运行脚本负责写退出码和完成清单。启动返回作业标识后，Agent 可以结束当前等待。

为本轮准备独立目录，保存配置与执行提交。
启动前检查该运行编号是否已存在。启动后立即返回任务标识。
实验脚本把日志、退出码和产物清单写入本轮目录，只有校验完整后才写完成状态。
连接失败时先按运行编号查询，确认未启动后再提交。

状态与日志检查

日志静止可能是计算耗时，也可能是进程卡住。先查进程或作业状态，再结合心跳和阶段预期。监视器记录最后检查时间，成功、失败和状态未知分开报告。

日志中出现一行 done，也要核对退出码、预期行数和数值有效性。程序可能在写完部分结果后失败，输出文件存在仍不足以判完成。

监视器的检查间隔按任务时长设定。短演示可以更频繁，数小时实验通常隔几分钟查一次；任务结束后停止监视。

按执行记录恢复

实验可恢复时，checkpoint 记录训练状态、随机状态与优化器。续跑代码要确认数据与配置匹配。只能从头重跑时，新开运行编号，保留失败轮次及重跑关系。

连接恢复后读取状态，不能凭上一段聊天推断完成位置。停任务时按确认过的作业编号或进程编号操作，先区分任务进程与共享服务。

资源与数据留在执行端

先确认资源分配，再启动实验。看到 GPU 空闲只是一次观测，不能保证它已经分给本任务。共享集群遵循调度器，普通服务器与同组成员约定占用。

数据尽量在服务器直接取得，摘要与分析也在那里生成。只拉回必要的小结果、元数据和图片，模型权重等大文件留下明确位置与校验信息。

练习

启动一个本课短运行，中途断开终端，再从新会话按运行编号查询。模拟一次未知状态：假设启动回包丢失，检查会不会重复启动。

交付一张状态表，记录每次查询看到的进程、退出码与产物。根据这张表说明何时能安全重试，何时需要先核实。

常见错误与处理方法

启动没回包就再发一次。 先按运行编号查执行端，避免重复消耗资源。

日志不动就杀任务。 结合阶段时长与进程状态，先判定卡在哪里。

恢复时换了配置，沿用旧编号。 身份变化新建运行，保留续跑或重跑关系。

3.2 Servers and background jobs

After-class deep dive, about 50 minutes.

You start an experiment over SSH and the connection drops. Did the job never start, or is it already running on the server? Simply retrying may run a second copy. Background execution first has to resolve this uncertainty.

Confirm the machine and directory first

Use the lab’s SSH keys and network setup, give the host a short name, and set a timeout and keepalive for the connection. On first connection, check the host identity, then confirm the user, working directory and resource allocation.

Host lab
    HostName lab.example.edu
    User researcher
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

Replace the example address with your own host. Passwords and private keys stay in your local authentication setup. Tailscale or a university VPN only provides connectivity; the server’s usage permissions and the cluster’s scheduling rules still apply.

Start with a run ID

Before each experiment, assign a unique run ID and put its configuration and logs in the matching directory. When the launcher receives the same ID, it first checks whether a running, finished or failed record already exists. A network retry uses this to decide whether to keep querying or resubmit.

When the cluster has a scheduler, prefer its job IDs and status interface. On an ordinary lab machine you can use tmux, with the run script responsible for writing the exit code and the completion list. Once the launch returns a job identifier, the agent can stop waiting.

Prepare a separate directory for this round, saving the configuration and execution commit.
Before launching, check whether this run ID already exists. After launching, return the job identifier immediately.
The experiment script writes the log, exit code and product list into this round's directory, and writes the completion status only after verifying they are complete.
If the connection fails, first query by run ID, and resubmit only after confirming it did not start.

Check status as well as logs

A silent log may mean a long computation, or a stuck process. First check the process or job status, then interpret it alongside the heartbeat and the expected stage duration. The monitor records the last check time and reports success, failure and unknown status separately.

Even when a log line says done, check the exit code, the expected number of rows and that values are valid. A program can fail after writing part of its results, so an existing output file is not enough to judge completion.

Set the monitor’s check interval by job length. A short demonstration can be checked more often; an experiment of several hours is usually checked every few minutes. Stop monitoring when the job ends.

Recover from the run records

When an experiment can resume, the checkpoint records the training state, random state and optimizer. The resuming code must confirm that data and configuration match. When you can only rerun from scratch, assign a new run ID and keep the failed round and its relation to the rerun.

After the connection comes back, read the status; do not infer how far it got from the previous conversation. When stopping a job, act on a confirmed job ID or process ID, and first tell the job’s processes apart from shared services.

Keep resources and data on the execution host

Confirm the resource allocation before starting the experiment. Seeing a GPU idle is one observation; it does not guarantee the GPU is allocated to this job. On a shared cluster follow the scheduler; on an ordinary server, agree on usage with your group.

Get data directly on the server wherever possible, and produce summaries and analyses there too. Pull back only the necessary small results, metadata and figures; large files such as model weights stay put, with a clear location and checksum.

Exercise

Start a short run from this lesson, disconnect the terminal partway through, then query by run ID from a new session. Simulate an unknown status: suppose the launch reply was lost, and check whether the job would be launched twice.

Hand in a status table recording the process, exit code and products seen at each query. From the table, explain when it is safe to retry and when you must verify first.

Common mistakes and how to fix them

Sending the launch again because no reply came back. First query the executor by run ID, to avoid using resources twice.

Killing a job because the log is not moving. Combine the stage duration with the process status, and first judge where it is stuck.

Changing the configuration on recovery but keeping the old ID. When the configuration or other run details change, create a new run, and keep its relation as a resume or a rerun.
