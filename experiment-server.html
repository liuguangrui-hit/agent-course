3.2 服务器与后台任务

课后深入，约 30 分钟。需要一台能 SSH 登录的服务器。

实验室的服务器有 GPU，有大内存，开着不关。让 Agent 用上它，要解决三个问题：连得上，跑得久，不用守着。这一节按这个顺序讲，再讲连接卡住时怎么办。

连得上：SSH 配置

每次输入地址、用户名和端口既麻烦又容易错。让 Agent 在 ~/.ssh/config 里给服务器起个短名字：

Host lab
    HostName 100.64.0.5
    User zhang
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

之后 ssh lab 就能连上。后三行是超时设置：15 秒连不上就放弃，连上后每 15 秒确认一次对方还在，两次没回应就断开。没有这几行，网络一抖，Agent 的命令会一直挂着，它也跟着卡住。这几行管的是连接；远端命令本身卡住，要靠下面的 tmux 和日志，不让 SSH 等它。

登录用密钥，不用密码。密钥在你的电脑上生成，公钥交给服务器管理员或者自己加到服务器的 ~/.ssh/authorized_keys 里。Agent 不需要也不应该知道你的服务器密码。

校外连得上：Tailscale

服务器常在学校内网里，出了校园连不上。Tailscale 把你的电脑和服务器放进同一个虚拟局域网，只要两边都在线，在校外也能连。电脑和服务器各装一个，用同一个账号登录，服务器会得到一个 100 开头的地址，写进上面的配置。

如果服务器由学校统一管理，先问管理员能不能装；有的学校提供自己的 VPN，道理相同。

跑得久：tmux

直接在 SSH 会话里启动的程序，SSH 一断往往跟着停。tmux 在服务器上开一个不会随连接断开的会话，实验在里面跑：

ssh lab "mkdir -p ~/label-noise-lab/logs; tmux new -d -s lab 'cd ~/label-noise-lab; uv run python code/run_experiment.py > logs/run.log 2>&1; echo \$? > logs/exit_code'"

实验结束时，不管成败，退出码都会写进 logs/exit_code。-d 表示开好会话立刻返回，SSH 随即断开，实验在服务器上接着跑。日志写进文件，任何时候都能看。你自己想看实验进度，ssh lab 登录后 tmux attach -t lab 就能接进去。

不用 tmux 时，也可以用完全脱离终端的方式启动。关键是启动命令立刻返回，不让 SSH 等着后台程序。有一个容易犯的错：把几条命令用 && 连起来，最后一条放到后台，整串都会被放到后台，它的输出把 SSH 连接一直占着。启动命令单独写一句。

不用守着：监视器

实验要跑两小时。让 Agent 每隔几秒问一次跑完没有，每问一次它都要重读整个对话，又慢又贵。Claude Code 有后台命令和监视器：一条命令在后台跑，Agent 去做别的或者干脆停下来，命令有输出或者结束时再把它叫醒。

设一个监视器：每 5 分钟 ssh lab 看一次 ~/label-noise-lab/logs/exit_code 是否出现，出现就叫醒你；同时看一眼 run.log 的最后几行，日志超过 20 分钟没有变化也叫醒你。
你醒来后，退出码不是 0 或者日志停了，读日志找原因，告诉我；退出码是 0，接着做练习 3。

间隔设几分钟足够。

服务器上的环境

在服务器上用 uv 装环境，和本机一样：仓库里有 pyproject.toml 和锁文件 uv.lock，uv sync 一步装好和本机相同版本的 Python 包。系统库和显卡驱动不归它管，结果说明里记下服务器的显卡和 CUDA 版本。跑之前让 Agent 先看一眼 GPU 是不是有人在用：

ssh lab nvidia-smi，告诉我哪几块卡空着。只用空着的卡。

数据放在服务器上

服务器和你的电脑之间如果经过中转网络，速度可能只有每秒几 KB。不要从电脑传数据集到服务器，也不要把整个结果目录拉回来：

  • 数据集在服务器上直接下载；
  • 分析和汇总在服务器上做，只把汇总后的小文件拉回来；
  • 稍大的文件先压缩再拉。

停掉一个实验

最稳的办法是关掉 tmux 会话：ssh lab tmux kill-session -t lab。不要让 Agent 按命令名匹配去杀进程，它在服务器上执行的那条 SSH 命令本身也含有这个名字，会把自己一起杀掉。真要按名字找，让它先列出进程编号给你看，再按编号停。

连接卡住时

所有 SSH 突然都超时，先别重试。让 Agent 查一下 Tailscale 的状态，或者 ping 一下服务器。如果是网络问题，接着反复重连只会更堵。停下来，告诉你，等网络恢复。

练习

把练习 2 的实验分成两组种子，在服务器上开两个 tmux 会话同时跑，一个监视器看两份日志。这个实验只用 CPU；你自己的实验用 GPU 时，再让每个会话指定一块空着的卡。

最容易出错的地方

命令挂着不返回。 后台程序没有完全脱离，SSH 一直等着它。放进 tmux，启动命令立刻返回；每次 SSH 都有超时。

大文件来回传。 中转网络被堵死，所有连接一起超时。数据在服务器上下载，只拉回小文件。

超时后狂重连。 网络已经堵了，Agent 每几秒重试一次，越试越堵。超时两次就停，查网络状态，告诉你。

3.2 Servers and background jobs

Self-study, about 30 minutes. Needs a server you can SSH into.

A lab server has GPUs, plenty of memory, and stays on. To let the agent use it, solve three problems: connect, keep running, and stop waiting. This section follows that order, then covers stuck connections.

Connect: SSH configuration

Typing an address, username and port every time is tedious and error-prone. Have the agent give the server a short name in ~/.ssh/config:

Host lab
    HostName 100.64.0.5
    User zhang
    ConnectTimeout 15
    ServerAliveInterval 15
    ServerAliveCountMax 2

Then ssh lab connects. The last three lines set timeouts: give up if connection takes over 15 seconds; once connected, check every 15 seconds that the server is still there; disconnect after two missed replies. Without them, a network hiccup can leave the command hanging and the agent stuck. These lines govern the connection. For a stuck remote command, use tmux and logs below so SSH does not wait for it.

Log in with a key, not a password. Generate the key on your computer and give the public key to the server administrator, or add it to the server’s ~/.ssh/authorized_keys yourself. The agent does not need and should not know your server password.

Connect off campus: Tailscale

Servers are often on the university’s internal network and unreachable off campus. Tailscale puts your computer and the server on the same virtual local network. If both are online, you can connect from off campus. Install it on both and sign in with the same account. The server gets an address starting with 100; put it in the configuration above.

If the university manages the server, ask the administrator before installing it. Some universities provide their own VPN; the idea is the same.

Keep running: tmux

A program started directly in an SSH session often stops when SSH disconnects. tmux opens a server session that survives disconnection. Run the experiment inside it:

ssh lab "mkdir -p ~/label-noise-lab/logs; tmux new -d -s lab 'cd ~/label-noise-lab; uv run python code/run_experiment.py > logs/run.log 2>&1; echo \$? > logs/exit_code'"

When the experiment ends, success or failure, its exit code goes to logs/exit_code. -d returns as soon as the session starts. SSH disconnects and the experiment continues on the server. Logs go to a file you can read any time. To see progress yourself, log in with ssh lab, then join with tmux attach -t lab.

Without tmux, you can also launch fully detached from the terminal. The launch command must return at once so SSH does not wait for the background program. A common mistake is joining commands with && and putting the last in the background: the whole chain goes into the background, and its output holds the SSH connection open. Write the launch as a separate command.

Stop waiting: a monitor

An experiment takes two hours. If the agent asks every few seconds whether it is done, it rereads the whole conversation every time. That is slow and expensive. Claude Code has background commands and monitors: a command runs in the background while the agent does something else or stops, then wakes it when there is output or the command ends.

Set a monitor: every 5 minutes, use ssh lab to check whether ~/label-noise-lab/logs/exit_code exists. Wake when it appears. Also check the last few lines of run.log; wake if the log has not changed for over 20 minutes.
When you wake, if the exit code is not 0 or the log has stopped, read the log to find the cause and tell me. If the exit code is 0, continue with Exercise 3.

A few minutes between checks is enough.

The server environment

Use uv on the server just as locally. With pyproject.toml and the lockfile uv.lock in the repository, uv sync installs the same Python package versions in one step. It does not manage system libraries or GPU drivers. Record the server’s GPU and CUDA version in the result report. Before running, have the agent check whether anyone is using the GPUs:

Run ssh lab nvidia-smi and tell me which GPUs are free. Use only free GPUs.

Keep data on the server

If traffic between the server and your computer goes through a relay, speeds may be only a few KB per second. Do not upload datasets from your computer or bring back the whole result directory:

  • Download datasets directly on the server;
  • Analyse and summarize there, then bring back only small summary files;
  • Compress larger files before transferring.

Stopping an experiment

The most reliable way is closing its tmux session: ssh lab tmux kill-session -t lab. Do not have the agent kill processes by matching command names. Its SSH command on the server contains the same name, so it may kill itself too. If you need to search by name, have it list process IDs first, then stop by ID.

When connections hang

If all SSH calls suddenly time out, stop retrying. Have the agent check Tailscale’s status or ping the server. If the network is at fault, repeated reconnections only add congestion. The agent should stop, tell you, and wait for the network to recover.

Exercise

Split Exercise 2’s experiment into two groups of seeds and run them at once in two tmux sessions on the server, with one monitor watching both logs. This experiment uses only the CPU. For your own GPU experiments, have each session use a free GPU.

Where agents go wrong most

A command hangs instead of returning. The background program has not fully detached, so SSH keeps waiting. Put it in tmux and make the launch command return at once. Give every SSH call a timeout.

Large files going back and forth. The relay gets congested and all connections time out. Download data on the server and bring back only small files.

Reconnecting wildly after a timeout. The network is already congested, and retries every few seconds make it worse. Stop after two timeouts, check network status, and tell you.
