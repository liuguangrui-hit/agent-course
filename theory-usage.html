6.4 用量与成本核算

课后深入，约 40 分钟。

一张经验榜提高了正确率，却让每次任务多花一倍时间。它是否值得部署，需要结合学习收益和资源成本作判断。

用量来源与统计口径

记录任务与执行者并注明起止时间，再分别填写输入、输出与缓存用量。不同产品的输入字段可能已包含缓存读取，也可能只计未缓存输入，先查日志定义，再做加总。

练习包的账本明确把未缓存输入，缓存读，缓存写和输出分列，四列互不重叠。新增自己的日志时，保留原始字段与来源，转换成统一口径。读不到的数留缺失，零是一个实际测量值。

订阅费用、API 费用和按 API 价折算的资源量分别写。示例费率只是演算假设，实际价格到官方页面核对，不能当作订阅的逐 token 账单。

对话分段的简化模型

每轮增加 cc 个历史 token，共 nn 轮，若每轮完整读取累计历史，输入总量约为 cn(n+1)/2cn(n+1)/2。这是未考虑压缩与截断的模型。

均匀拆成 mm 段，每轮读交接长度 hh，每次换段另付成本 rr，忽略与 mm 无关的小项，可写：

F(m)≈cn22m+nh+(m−1)r,m*≈nc2r.F(m)\approx\frac{cn^2}{2m}+nh+(m-1)r,\qquad m^*\approx n\sqrt{\frac{c}{2r}}.

计算器另计首段启动成本，两式相差固定的 r。最优段数不受影响，节省比例以计算器的一段基准为准。把各项统一成同一种成本单位，再代入相邻整数和合法范围。实际缓存、压缩和任务切换会改变形状，用自己的逐轮日志验证。更短的会话还可能增加遗漏，交付采用率也要比较。

多做一轮的价值

再审一轮发现实质问题的概率为 pp，问题价值为 VV，本轮成本为 CC。粗略决策看 pV−CpV-C。pp 从同类历史任务估计，样本少时做敏感性分析。

既定必需核查仍应完成。这条式子适合在合格产物上决定追加审阅，不能用来略过尚未完成的验收。

并行的成本与收益

串行与并行分别花费 S,S′S,S'，实际耗时为 T,T′T,T'，时间价值为 ww。在质量相同的前提下，可比较：

(T−T′)w−(S′−S).(T-T')w-(S'-S).

并行多出的说明与整合会消耗 token，质量也可能变化。记录证据抽查通过率、返工和失败，再算每份被采用产物的总成本。

学习方案的部署目标

把回报、资源与风险写进同一目标，例如：

U(B)=J(B)−λC(B)−μR(B).U(B)=J(B)-\lambda C(B)-\mu R(B).

CC 和 RR 分别表示已定义的资源与风险指标，权重体现实际取舍。也可以把成本设成硬约束，只在预算内比较回报。选择方式事前确定，保留原始多指标结果，避免权重变化掩盖退步。

练习

运行 calc.py 复算三项编排决策。再把经验试验的写榜与评估成本加入，改变时间价值和成本上限，找出结论何时变化。然后把自己的逐轮日志接进同一口径，比较推算与实际花费。

常见错误与处理方法

缓存输入重复加总。 保留产品原始口径，转换前确认包含关系。

把折算费率当真实扣费。 分列订阅、API 支出与资源估算。

只算执行，不算写榜和挑榜。 全流程记录，比较同预算下的最终回报。

工具可参考 ccusage 与 Claude 成本管理，是否支持当前日志格式要实读验证。

6.4 Usage and cost accounting

After-class deep dive, about 40 minutes.

A playbook raised accuracy but doubled the time each task takes. Whether it is worth deploying depends on connecting the learning gain to a resource decision.

Record usage sources and accounting conventions

Record the task, the executor and the start and end times, then the input, output and cache. In different products, the input field may already include cache reads, or may count only uncached input; check the log definitions first, then add things up.

The exercise package’s ledger explicitly lists uncached input, cache reads, cache writes and output as four non-overlapping columns. When adding your own logs, keep the original fields and source, and convert to a common basis. Leave values you cannot read as missing; zero is an actual measurement.

Write subscription fees, API spending and resource estimates valued at API rates separately. The example rates are only assumptions for the worked example; check actual prices on the official pages, and do not treat them as a per-token bill for a subscription.

A simplified model of splitting conversations

If each turn adds cc tokens of history over nn turns, and every turn reads the full accumulated history, total input is about cn(n+1)/2cn(n+1)/2. This model ignores compression and truncation.

Split evenly into mm segments, with each turn reading a handover of length hh and each segment change costing an extra rr; ignoring small terms that do not depend on mm, we can write:

F(m)≈cn22m+nh+(m−1)r,m*≈nc2r.F(m)\approx\frac{cn^2}{2m}+nh+(m-1)r,\qquad m^*\approx n\sqrt{\frac{c}{2r}}.

The calculator also charges for first-segment startup, adding a constant r; this leaves the optimal segment count unchanged, and savings percentages use the calculator’s own one-segment baseline. Put all terms in the same unit of cost, then evaluate neighboring integers within the valid range. Real caching, compression and task switching change the shape, so verify with your own turn-by-turn logs. Shorter sessions may also cause more omissions, so compare how often deliverables are actually adopted too.

The value of one more round

Let the probability that another round of review finds a substantive problem be pp, the value of the problem VV, and the cost of the round CC. A rough decision looks at pV−CpV-C. Estimate pp from similar past tasks, and do a sensitivity analysis when the sample is small.

Checks already established as required must still be done. This formula is for deciding on extra review of an output that meets the required criteria; it cannot be used to skip acceptance checks not yet completed.

What parallelism buys

Let serial and parallel work cost S,S′S,S' with wall-clock times T,T′T,T', and let the value of time be ww. Given equal quality, compare:

(T−T′)w−(S′−S).(T-T')w-(S'-S).

The extra instructions and integration in parallel work consume tokens, and quality may change too. Record the pass rate of evidence spot-checks, rework and failures, then compute the total cost per product actually adopted.

Define the deployment objective

Write reward, resources and risk into one objective, for example:

U(B)=J(B)−λC(B)−μR(B).U(B)=J(B)-\lambda C(B)-\mu R(B).

CC and RR are defined resource and risk metrics, and the weights reflect the actual trade-off. You can also make cost a hard constraint and compare reward only within budget. Set the decision rule in advance and keep the raw multi-metric results, so a change of weights does not hide a regression.

Exercise

Run calc.py to recompute the three orchestration decisions. Then add the costs of writing and evaluating the playbook in the experience trial, change the value of time and the cost cap, and find when the conclusion changes. Next, connect your own turn-by-turn logs on the same basis and compare the estimate with actual spending.

Common mistakes and how to fix them

Adding cached input in twice. Keep the product’s original definitions, and confirm what includes what before converting.

Treating converted rates as real charges. List subscriptions, API spending and resource estimates separately.

Counting execution only, not writing and choosing the playbook. Record the whole process, and compare final reward under the same budget.

For tools, see ccusage and Claude cost management; check their output against your actual logs to confirm support for the current format.
