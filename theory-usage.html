6.1 用量账本

课后深入，约 30 分钟。

这一节讲账本记什么，从哪里取数，怎样分段，以及几条常用的算式。

记什么

列 说明
日期
事情 一句话，比如第 7 轮收工，读 14 篇论文写笔记
Agent Claude 或 Codex，哪个账号
对话数 这件事开了几个对话，含 Sub-agent
输入 token，缓存读取，缓存写入，输出 token 分开记，四者价格不同，输入和缓存读取通常占大头
审稿轮次，是否提出实质意见 只有审稿类的事情填，供算审稿该在第几轮停
估算费用 按官方 API 价格估；订阅用户实际付的是月费，这一列只用来比相对大小
耗时 从开工到收工的墙上时间
是否采用 产出最后是被用上了，改了一部分，还是推翻重来

最后一列最容易漏，也最重要。没有它，你只知道花了多少，不知道值不值。

从哪里取数

Claude Code 把每个对话的用量记在本机的日志里，ccusage 按天、按对话汇总这些日志。Codex 也有类似的本地记录。对话里也能随时查看当前用量和额度。

用 ccusage 列出今天每个对话的输入输出 token 和起止时间，按开始时间排序。
对照 STATE.md 的记录，把每个对话对应到账本里的一件事，填进 ledger.csv。
起止时间之差含着空闲的时间，耗时一列以 STATE.md 里记的开工和收工时间为准。

按事情分段

账要按事情记，不按天记。一天的总数告诉你今天花得多，但不告诉你花在哪。最简单的分段办法是开工和收工各记一笔：开工时记下时间和当前累计用量，收工时再记一次，差值就是这件事的用量。

第 4 课的循环里，这一步可以写进 LOOP.md：开工的第一步、收工的最后一步，各往账本里追加一行。

几条常用算式

对话长度的成本。 每轮新增约 c 个 token，n 轮的对话累计输入约 c · n² / 2。拆成 m 段，每段 n / m 轮，每轮都要连带读一遍 h 个 token 的交接文件，另外每换一段要付一次 r，用来写交接文件和重新熟悉任务。总量约 c · n² / (2m) + n · h + m · r。中间一项和 m 无关，对 m 求最小，最佳段数约为 n · √(c / 2r)。交接文件越短，每轮多读的越少；换段的代价 r 越大，段就该分得越少。

再做一轮的价值。 第 k 轮发现实质问题的概率 p_k，一个问题的价值 V，一轮的花费 C。p_k · V < C 时停。p_k 从账本里过去同类事情的记录数出来。

并行的划算条件。 串行耗时 T、花费 S；并行耗时 T′、花费 S′。你的时间每小时值 w，当 (T − T′) · w > S′ − S 时并行划算。

每个被采用结果的成本。 一段时间的总花费除以被采用的结果数。比较两种编排，比的是这个数，不是单次花费。

这些式子都很粗。它们的用处不是给出精确的答案，而是把要不要再审一轮这种问题，拆成几个能从账本里查到的数和一个你自己判断的价值。

练习

为你自己的工作台记一周账，然后挑一个你一直拿不准的编排问题，用上面的一条算式算一次。把结论和你原来的直觉对照。

最容易出错的地方

只记总数。 一周一个数字，说明不了任何编排问题。按事情分段，开工收工各记一笔。

漏了是否采用。 只比花费，省钱的流程可能一半产出被推翻。记下每个结果最后的去向。

把粗算当精算。 式子里的数都是估的，算出的是量级和方向。结论差距不大时，按你的判断来，不必为了几个百分点改编排。

6.1 Usage ledger

Self-study, about 30 minutes.

This section covers what to record, where to get numbers, how to separate tasks, and a few useful formulas.

What to record

Column Meaning
Date
Task One sentence, such as wrapping up round 7 or reading 14 papers and writing notes
Agent Claude or Codex, and which account
Conversation count Conversations used for this task, including Sub-agents
Input tokens, cache reads, cache writes, output tokens Record separately; all four have different prices. Input and cache reads usually dominate
Review round, substantive comment proposed? Only for review tasks, to calculate which round to stop at
Estimated cost At official API prices. Subscribers pay a monthly fee; this column compares relative costs only
Time taken Elapsed time from start to finish
Adopted? Used, partly revised, or rejected and redone

The last column is easiest to miss and matters most. Without it, you know what you spent but not whether it was worth it.

Where numbers come from

Claude Code records each conversation’s usage in local logs. ccusage summarizes them by day or conversation. Codex has similar local records. You can also check current usage and quota within a conversation.

Use ccusage to list today's input and output tokens and start and end times per conversation, sorted by start time.
Match conversations to tasks using STATE.md and fill ledger.csv.
Start-to-end time includes idle time. Use the start and finish times in STATE.md for the time-taken column.

Separate by task

Record by task, not day. A daily total says you spent a lot but not where. The simplest method is recording at both start and finish: note the time and cumulative usage at the start, then again at the end. The difference is that task’s usage.

In Session 4’s loop, add this to LOOP.md: append a ledger row as the first startup step and the last wrap-up step.

Useful formulas

Cost of conversation length. With about c new tokens per round, a conversation of n rounds has roughly c · n² / 2 total input tokens. Split it into m parts of n / m rounds. Each round also reads an h-token handoff file, and each new part costs r to write the handoff and get familiar with the task again. The total is about c · n² / (2m) + n · h + m · r. The middle term is independent of m. Minimizing over m gives about n · √(c / 2r) parts. Shorter handoff files mean less rereading each round; a higher switching cost r means fewer parts.

Value of another round. If round k finds a substantive problem with probability p_k, a problem is worth V, and a round costs C, stop when p_k · V < C. Count p_k from past similar tasks in the ledger.

When parallel work pays off. Sequential work takes T and costs S; parallel work takes T′ and costs S′. If your time is worth w per hour, parallel pays off when (T − T′) · w > S′ − S.

Cost per adopted result. Total cost over a period divided by adopted results. Compare orchestration methods on this number, not cost per run.

These formulas are rough. They do not give precise answers. They break questions such as whether to review again into numbers you can get from the ledger and a value you judge yourself.

Exercise

Keep a week’s ledger for your workbench. Pick an orchestration question you have been unsure about and calculate it with one formula above. Compare the conclusion with your earlier intuition.

Where agents go wrong most

Only totals. One number per week answers no orchestration question. Record by task, at start and finish.

Missing adoption. Comparing only cost may favour a workflow whose outputs are rejected half the time. Record what happened to each result.

Treating rough estimates as precise. The formula inputs are estimates; the answers give scale and direction. If the gap is small, use your judgment rather than changing orchestration over a few percentage points.
