6.4 用量与成本核算

学习目标

  1. 统一不同来源的 token 用量与费用口径，区分缺失值、实测零值、订阅费用与折算资源量。
  2. 运用对话分段、追加审阅与并行执行的简化模型作出资源决策，并检验其敏感性和适用前提。
  3. 把学习收益、资源成本与风险纳入事先确定的部署目标，评价一项学习方案是否值得部署。

课后深入专题，约 40 分钟。

一张经验榜提高了正确率，却使每次任务的耗时增加一倍。它是否值得部署，需要综合学习收益和资源成本加以判断。

用量来源与统计口径

记录任务、执行者和起止时间，再分别填写输入、输出与缓存用量。不同产品的输入字段可能已经包含缓存读取，也可能只计未缓存输入，应先查明日志定义，再做加总。

练习包的账本把未缓存输入、缓存读取、缓存写入和输出分为四列，四列互不重叠。加入自己的日志时，保留原始字段与来源，再转换为统一口径。读不到的数值记为缺失，零是一个实际测量值。

订阅费用、API 费用和按 API 价格折算的资源量分别记录。示例费率只是演算假设，实际价格须到官方页面核对，不能当作订阅的逐 token 账单。

对话分段的简化模型

设每轮增加 cc 个历史 token，共 nn 轮。若每轮都完整读取累计历史，输入总量约为 cn(n+1)/2cn(n+1)/2。这一模型未考虑压缩与截断。

均匀拆分为 mm 段，每轮读取长度为 hh 的交接内容，每次换段另付成本 rr。忽略与 mm 无关的小项，可写为：

F(m)≈cn22m+nh+(m−1)r,m*≈nc2r.F(m)\approx\frac{cn^2}{2m}+nh+(m-1)r,\qquad m^*\approx n\sqrt{\frac{c}{2r}}.

计算器另计首段的启动成本，两式相差一个固定的 r，最优段数不受影响，节省比例以计算器的单段基准为准。各项统一为同一种成本单位后，代入相邻整数并检查合法范围。实际的缓存、压缩和任务切换会改变曲线形状，应以自己的逐轮日志验证。会话更短也可能增加遗漏，交付采用率同样需要比较。

追加一轮的价值

设再审一轮发现实质问题的概率为 pp，问题的价值为 VV，本轮成本为 CC。粗略的决策依据是 pV−CpV-C。pp 由同类任务的历史估计，样本较少时做敏感性分析。

既定的必需核查仍须完成。这一公式适用于在产物已经合格的前提下决定是否追加审阅，不能用来跳过尚未完成的验收。

并行的成本与收益

设串行与并行的花费分别为 S,S′S,S'，实际耗时为 T,T′T,T'，时间价值为 ww。在质量相同的前提下，可比较：

(T−T′)w−(S′−S).(T-T')w-(S'-S).

并行需要额外的任务说明与整合，会消耗 token，质量也可能变化。应记录证据抽查通过率、返工和失败，再计算每份被采用产物的总成本。

学习方案的部署目标

把回报、资源与风险写入同一目标，例如：

U(B)=J(B)−λC(B)−μR(B).U(B)=J(B)-\lambda C(B)-\mu R(B).

CC 和 RR 分别表示已定义的资源指标与风险指标，权重反映实际取舍。也可以把成本设为硬约束，只在预算内比较回报。选择方式须事先确定，并保留原始的多指标结果，以免权重变化掩盖性能退步。

练习

运行 calc.py，复算三项编排决策。再加入经验试验中写榜与评估的成本，改变时间价值和成本上限，找出结论在何时发生变化。然后把自己的逐轮日志接入同一口径，比较推算值与实际花费。

常见错误与处理方法

缓存输入被重复加总。 保留产品的原始口径，转换前确认字段间的包含关系。

把折算费率当作实际扣费。 订阅费用、API 支出与资源估算分列。

只计算执行成本，忽略写榜和选榜成本。 记录全流程，在相同预算下比较最终回报。

工具可参考 ccusage 与 Claude 成本管理，是否支持当前日志格式须实际读取验证。

6.4 Usage and cost accounting

Learning outcomes

After this section, students should be able to:

  1. Record and reconcile usage data under explicit accounting conventions, distinguishing subscription fees, API spending and resource estimates.
  2. Use simplified cost models of conversation splitting, additional review rounds and parallel work to support orchestration decisions, and test their sensitivity to the assumptions.
  3. Define a deployment objective that combines reward, resources and risk, with the decision rule fixed in advance.

Extension reading and exercises, about 40 minutes.

A playbook that raises accuracy may also double the time each task takes. Whether it is worth deploying depends on relating the learning gain to a resource decision.

Recording usage sources and accounting conventions

Record the task, the executor and the start and end times, then the input, output and cache. In different products, the input field may already include cache reads or may count only uncached input; the log definitions are checked before any totals are computed.

The exercise package’s ledger lists uncached input, cache reads, cache writes and output as four non-overlapping columns. When adding your own logs, keep the original fields and their source, and convert to a common basis. Values that cannot be read are left as missing; zero is an actual measurement.

Subscription fees, API spending and resource estimates valued at API rates are recorded separately. The example rates are assumptions for the worked example only; actual prices are checked on the official pages and must not be treated as a per-token bill for a subscription.

A simplified model of conversation splitting

If each turn adds cc tokens of history over nn turns, and every turn reads the full accumulated history, total input is about cn(n+1)/2cn(n+1)/2. This model ignores compression and truncation.

Divide the conversation evenly into mm segments, with each turn reading a handover of length hh and each change of segment costing an additional rr. Ignoring small terms that do not depend on mm:

F(m)≈cn22m+nh+(m−1)r,m*≈nc2r.F(m)\approx\frac{cn^2}{2m}+nh+(m-1)r,\qquad m^*\approx n\sqrt{\frac{c}{2r}}.

The calculator also charges for first-segment startup, adding a constant r; this leaves the optimal segment count unchanged, and savings percentages use the calculator’s own one-segment baseline. Express all terms in the same unit of cost, then evaluate the neighboring integers within the valid range. Real caching, compression and task switching change the shape of the curve, so the model is checked against turn-by-turn logs. Shorter sessions may also cause more omissions, so the rate at which deliverables are actually adopted is compared as well.

The value of an additional round

Let the probability that another round of review finds a substantive problem be pp, the value of the problem VV, and the cost of the round CC. A first approximation to the decision considers pV−CpV-C. Estimate pp from similar past tasks, and perform a sensitivity analysis when the sample is small.

Checks already established as required must still be carried out. This formula applies to the decision on additional review of an output that meets the required criteria; it cannot be used to skip acceptance checks not yet completed.

The value of parallel work

Let serial and parallel work cost S,S′S,S' with wall-clock times T,T′T,T', and let the value of time be ww. At equal quality, compare:

(T−T′)w−(S′−S).(T-T')w-(S'-S).

The additional instructions and integration required by parallel work consume tokens, and quality may also change. Record the pass rate of evidence spot checks, rework and failures, then compute the total cost per product actually adopted.

Defining the deployment objective

Reward, resources and risk can be combined in a single objective, for example:

U(B)=J(B)−λC(B)−μR(B).U(B)=J(B)-\lambda C(B)-\mu R(B).

CC and RR are defined resource and risk metrics, and the weights reflect the actual trade-off. Alternatively, cost can be imposed as a hard constraint and reward compared only within budget. The decision rule is set in advance and the raw multi-metric results are kept, so that a change of weights does not conceal a regression.

Exercise

Run calc.py to recompute the three orchestration decisions. Then add the costs of writing and evaluating the playbook in the experience trial, vary the value of time and the cost cap, and identify when the conclusion changes. Next, connect your own turn-by-turn logs on the same basis and compare the estimate with actual spending.

Common errors and corrections

Counting cached input twice. Keep the product’s original definitions, and confirm which fields include which before converting.

Treating converted rates as real charges. List subscriptions, API spending and resource estimates separately.

Counting execution only, and not the writing and selection of the playbook. Record the whole process, and compare final reward under the same budget.

For tools, see ccusage and Claude cost management; check their output against your actual logs to confirm support for the current format.
