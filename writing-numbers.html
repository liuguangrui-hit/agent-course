1.2 数据核查

课后深入，约 35 分钟。

摘要里是 96.2%，结果表里是 96.0%。两句话都很顺，读一遍很容易放过。更难发现的是两个地方都写 25%，分母却已经换了。

数据核查分两层。脚本保证计算与复制一致，审阅者检查这一个数究竟在说什么。

明确指标与统计口径

一个结果数字至少带五项信息：数据版本与配置、指标与统计口径，以及单位。比如 GCE 在四成训练标签翻转下，五个种子的最终测试准确率均值，单位是百分比。这组信息比数字本身更适合作为键。

读 data/results.csv，列出论文实际报告的指标。
为每个指标写明配置，以及样本或种子的分母，再注明汇总方式、单位和输出位置。
先形成 code/make_numbers.py 的计算清单，再生成正文宏与结果表。

把筛选条件写进函数，避免每个段落各算一次。摘要需要整数近似时，由同一份原始值派生，记录舍入规则。

从数据生成宏与表

参考答案的 code/make_numbers.py 生成 paper/numbers.tex 和结果表。正文通过宏引用：

\input{numbers.tex}
GCE ends at \gceFinalForty\%.

更换数据后，先重新生成，再编译全文。图与表也读取同一份数据输入。这样能把人工复制的环节拿掉。

用一个变化测试这条链：复制数据到测试目录，只改一个种子的一个值，重建论文，列出所有变化的位置。改动若只到了表格，摘要仍未接上生成流程。

核查器要查对应关系

练习里的 check_numbers.py 会提取百分数，并与预定汇总值比较。它能抓到两处故意写错的数，是一个小型核查器。

候选值扩得太大，会把错误放过去。96.2 也许恰好出现在另一种配置的早期曲线上。正式项目可以把正文结果标记到唯一指标键，再核查键与值对应；一个全库数值集合只适合初步筛查。

在初稿和重讲稿上分别运行 check_numbers.py，保存输出。
抽三处数字，记录原文句子与指标键，再写明筛选条件和重算结果。
再故意把一个正确数字移到另一种配置的句子里，检查现有核查器能否发现。

差值从未舍入的数据算

把方法 A 和 B 的原始汇总值相减，再按统一位数报告。表中已经舍入的两个数相减，末位可能有一点差异，表注交代即可。统计分析和区间估计始终使用未舍入数据。

从 67.4% 到 96.0%，差值是 28.6 个百分点；相对提升则要除以前者。让脚本分别保留 delta_pp 与 relative_change，正文按指标键取数。

构建与语义核查

构建入口依次生成数字，表格，图和 PDF。检查入口再核查引用，数字与文件完整性。每次输出保留输入文件的哈希，重建时就能知道用了哪份数据。

审阅时把重复数字的上下文并排放：主语是否一致，分母是否一致，均值是否被写成单次最好成绩，标准差是否被写成置信区间。这些问题需要结合语义判断。

练习

做三次故意出错：改一个数值，调换两个配置的结果，把准确率提升改成错误率下降。每次记录谁发现了问题：生成流程、数值核查器，还是语义审阅。由此决定下一项检查应放在哪里。

常见错误与处理方法

数字在某处出现过就算通过。 要求结果与唯一配置和指标对应，抽查原始行。

表里相减更整齐，就用舍入值分析。 计算保留原始精度，展示统一舍入，表注解释末位差异。

生成脚本覆盖了手工改动。 生成文件标记为自动产物；修正放进数据处理代码，再重建。

Ten Simple Rules for Reproducible Computational Research可用来检查从数据到结论的整条记录。

1.2 Checking the numbers

After-class deep dive, about 35 minutes.

The abstract says 96.2% and the results table says 96.0%. Both sentences read smoothly, so a quick read can miss the discrepancy. Harder to catch: both places say 25%, but the denominator has changed.

Number checking has two layers. Scripts make sure computation and copying agree; the reviewer checks what each number means in context.

Define each reported result

A result number carries at least five pieces of information: data version, configuration, metric, aggregation and unit. For example: the mean final test accuracy of GCE over five seeds with 40% of training labels flipped, in percent. This identity is a better key than the number itself.

Read data/results.csv and list the metrics the paper actually reports.
For each metric, write the configuration, the denominator in samples or seeds, the aggregation, the unit and where it is output.
First build the list of calculations for code/make_numbers.py, then generate the text macros and the results table.

Put the filter conditions in functions, so each paragraph does not compute its own. When the abstract needs a rounded figure, derive it from the same raw value and record the rounding rule.

Generate macros and tables from data

In the reference answers, code/make_numbers.py generates paper/numbers.tex and the results table. The text refers to them through macros:

\input{numbers.tex}
GCE ends at \gceFinalForty\%.

When the data change, regenerate first, then compile the whole paper. Figures and tables read the same data input. This removes the manual copying step.

Test the chain with one change: copy the data to a test directory, change one value of one seed, rebuild the paper, and list every place that changed. If the change reached only the table, the abstract is not yet connected to the generation process.

Check that values match their metrics

The exercise’s check_numbers.py extracts percentages and compares them with predefined aggregate values. This small checker catches the two deliberately incorrect numbers.

If the set of candidate values grows too large, errors get through. 96.2 might happen to appear early on a curve from another configuration. A real project can tag each result in the text with a unique metric key, then check that key and value match; a set of all values in the repository is only good for a first screen.

Run check_numbers.py on the first draft and on the revised draft, and save the output.
Pick three numbers and write out the original sentence, the metric key, the filter conditions and the recomputed result.
Then deliberately move a correct number into a sentence about another configuration, and check whether the existing checker catches it.

Compute differences from unrounded data

Subtract the raw aggregate values of methods A and B, then report at a uniform number of digits. Subtracting two already-rounded numbers in a table may differ slightly in the last digit; a table note can explain that. Statistical analysis and interval estimates always use unrounded data.

From 67.4% to 96.0%, the difference is 28.6 percentage points; a relative improvement divides by the former. Have the script keep delta_pp and relative_change separately, and let the text take values by metric key.

Automate the build and review the meaning

The build command generates numbers, tables, figures and the PDF in turn. The validation command then checks citations, numbers and file completeness. Each output keeps the hashes of its input files, so a rebuild shows which data were used.

When reviewing, put the contexts of repeated numbers side by side: is the subject the same, is the denominator the same, has a mean been written as a single best result, has a standard deviation been written as a confidence interval? These checks require reading the numbers in context.

Exercise

Make three deliberate errors: change one value, swap the results of two configurations, and turn an accuracy gain into an error-rate drop. Each time, record what caught the problem: the generation process, the number checker, or a review of meaning. Use this to decide where the next check belongs.

Common mistakes and how to fix them

A number passes because it appears somewhere. Require each result to correspond to a unique configuration and metric, and spot-check the raw rows.

Analyzing rounded values because subtracting in the table looks tidier. Compute at full precision, display with uniform rounding, and explain last-digit differences in a table note.

The generation script overwrote a manual edit. Mark generated files as automatically generated outputs; put the fix into the data-processing code, then rebuild.

Ten Simple Rules for Reproducible Computational Research can be used to check the whole record from data to conclusion.
