1.2 数据核查

学习目标

  1. 为论文中的每个结果数字定义唯一的指标身份，包括数据版本、配置、统计口径、分母与单位。
  2. 设计从数据到正文宏、表格和图的生成链，并用受控改动检验其覆盖范围。
  3. 区分数值核查器与语义审阅各自能够发现的错误，据此安排检查位置。

课后深入专题，约 35 分钟。

摘要写 96.2%，结果表写 96.0%，两处文字都很通顺，通读一遍时容易放过。更隐蔽的情形是两处都写 25%，分母却已经不同。

数据核查分为两层：脚本保证计算与复制的一致性，审阅者判断一个数字究竟表达了什么。

指标与统计口径的定义

一个结果数字至少应附带五项信息：数据版本与配置，指标与统计口径，以及单位。例如：GCE 在四成训练标签翻转条件下，五个种子的最终测试准确率均值，单位为百分比。这组信息比数字本身更适合作为检索键。

读 data/results.csv，列出论文实际报告的指标。
为每个指标写明配置，以及样本或种子的分母，再注明汇总方式、单位和输出位置。
先形成 code/make_numbers.py 的计算清单，再生成正文宏与结果表。

筛选条件应写入函数，避免各段落分别计算。摘要需要取整时，由同一份原始值派生，并记录舍入规则。

由数据生成宏与表格

参考答案中的 code/make_numbers.py 生成 paper/numbers.tex 和结果表，正文通过宏引用：

\input{numbers.tex}
GCE ends at \gceFinalForty\%.

数据更新后，先重新生成，再编译全文。图与表读取同一份数据输入，从而去掉人工复制的环节。

可以用一次受控改动检验这条生成链：把数据复制到测试目录，只修改一个种子的一个值，重建论文，列出所有发生变化的位置。若改动只传到表格，说明摘要尚未接入生成流程。

核查器应检查对应关系

练习中的 check_numbers.py 提取正文中的百分数，与预定的汇总值比较。它能发现两处故意写错的数字，是一个小型核查器。

候选值集合过大时，错误会被放过。96.2 可能恰好出现在另一种配置的早期曲线上。正式项目可以把正文中的每个结果标记到唯一的指标键，再核查键与值的对应关系；全库数值集合只适合作初步筛查。

在初稿和重讲稿上分别运行 check_numbers.py，保存输出。
抽三处数字，记录原文句子与指标键，再写明筛选条件和重算结果。
再故意把一个正确数字移到另一种配置的句子里，检查现有核查器能否发现。

差值由未舍入数据计算

方法 A 与 B 的差值应由原始汇总值相减，再按统一位数报告。若用表中已舍入的两个数相减，末位可能略有出入，在表注中说明即可。统计分析和区间估计始终使用未舍入数据。

从 67.4% 到 96.0%，差值为 28.6 个百分点；相对提升则需再除以前者。脚本应分别保留 delta_pp 与 relative_change，正文按指标键取数。

构建核查与语义核查

构建入口依次生成数字、表格、图和 PDF。检查入口随后核查引用、数字与文件完整性。每次输出都保留输入文件的哈希，重建时即可确认所用数据。

审阅时，把重复出现的数字连同上下文并排列出，检查主语和分母是否一致，均值是否被写成单次最好成绩，标准差是否被写成置信区间。这些问题需要结合语义判断。

练习

人为制造三种错误：修改一个数值，调换两个配置的结果，把准确率提升写成错误率下降。每次记录由哪一层发现问题：生成流程、数值核查器，还是语义审阅。据此决定下一项检查应放在哪一层。

常见错误与处理方法

数字在某处出现过就判为通过。 要求每个结果对应唯一的配置和指标，并抽查原始数据行。

为求整齐，用表中舍入值做分析。 计算保留原始精度，展示时统一舍入，在表注中说明末位差异。

生成脚本覆盖了手工修改。 生成文件标记为自动产物；修正写入数据处理代码，再重新生成。

1.2 Checking the numbers

Learning outcomes

After this section, students should be able to:

  1. Specify each reported result by its data version, configuration, metric, aggregation and unit, and use that identity to verify it.
  2. Design a generation and checking chain in which text, tables and figures derive from the same data, and test the chain with deliberate perturbations.
  3. Distinguish errors that mechanical checks can detect from errors of meaning that require reading a number in context.

Extension reading and exercises, about 35 minutes.

Numerical inconsistencies are easy to miss because both versions of a sentence read smoothly. An abstract may report 96.2% while the results table reports 96.0%. A harder case is a value that appears as 25% in two places but with a different denominator in each.

Number checking therefore has two layers. Scripts ensure that computation and transcription agree; the reviewer checks what each number means in its context.

Defining each reported result

A reported result carries at least five pieces of information: data version, configuration, metric, aggregation and unit. For example: the mean final test accuracy of GCE over five seeds with 40% of training labels flipped, in percent. This identity is a more reliable key than the number itself.

Read data/results.csv and list the metrics the paper actually reports.
For each metric, write the configuration, the denominator in samples or seeds, the aggregation, the unit and where it is output.
First build the list of calculations for code/make_numbers.py, then generate the text macros and the results table.

Filter conditions are defined in functions so that individual paragraphs do not compute their own values. Where the abstract needs a rounded figure, it is derived from the same raw value and the rounding rule is recorded.

Generating macros and tables from data

In the reference answers, code/make_numbers.py generates paper/numbers.tex and the results table. The text refers to them through macros:

\input{numbers.tex}
GCE ends at \gceFinalForty\%.

When the data change, the numbers are regenerated first and the whole paper is then compiled. Figures and tables read the same data input, which removes manual copying from the process.

The chain can be tested with a single change: copy the data to a test directory, change one value for one seed, rebuild the paper and list every place that changed. If the change reached only the table, the abstract is not yet connected to the generation process.

Checking that values match their metrics

The exercise’s check_numbers.py extracts percentages and compares them with predefined aggregate values. This small checker detects the two deliberately incorrect numbers.

When the set of candidate values becomes too large, errors pass undetected: 96.2 might happen to occur early on a curve from another configuration. A real project can tag each result in the text with a unique metric key and check that key and value match; a set of all values in the repository is suitable only for an initial screen.

Run check_numbers.py on the first draft and on the revised draft, and save the output.
Pick three numbers and write out the original sentence, the metric key, the filter conditions and the recomputed result.
Then deliberately move a correct number into a sentence about another configuration, and check whether the existing checker catches it.

Computing differences from unrounded data

Subtract the raw aggregate values of methods A and B, then report the result to a uniform number of digits. Subtracting two already-rounded values in a table may differ in the last digit, which a table note can explain. Statistical analysis and interval estimates always use unrounded data.

From 67.4% to 96.0%, the difference is 28.6 percentage points; a relative improvement divides by the former value. The script should store delta_pp and relative_change separately, and the text should retrieve values by metric key.

Automating the build and reviewing meaning

The build command generates numbers, tables, figures and the PDF in sequence. The validation command then checks citations, numbers and file completeness. Each output records the hashes of its input files, so a rebuild shows which data were used.

In review, the contexts of repeated numbers are placed side by side: whether the subject is the same, whether the denominator is the same, whether a mean has been presented as a single best result, and whether a standard deviation has been presented as a confidence interval. These checks require reading the numbers in context.

Exercise

Introduce three deliberate errors: change one value, swap the results of two configurations, and turn an accuracy gain into an error-rate reduction. For each, record which check detected the problem: the generation process, the number checker or the review of meaning. Use the results to decide where the next check should be placed.

Common errors and corrections

Accepting a number because it appears somewhere. Require each result to correspond to a unique configuration and metric, and spot-check the raw rows.

Analyzing rounded values because subtraction in the table looks tidier. Compute at full precision, display with uniform rounding, and explain last-digit differences in a table note.

A generation script overwriting a manual edit. Mark generated files as automatically generated outputs; make the correction in the data-processing code and rebuild.

Ten Simple Rules for Reproducible Computational Research can be used to check the complete record from data to conclusion.
