5.1 权限与沙箱

学习目标

  1. 分析一条命令规则实际授予的能力，区分工具入口、子进程、网络与凭据四类边界。
  2. 设计覆盖直接工具、子进程与网络的沙箱行为测试，并说明测试结论的适用条件。
  3. 按信息流组织角色权限，单独评估 SSH 等沙箱外例外的能力范围。

课后深入专题，约 60 分钟。

允许 uv run，实际上允许了什么？它启动的脚本可以再启动其他程序，也可以使用环境中的凭据。理解这一点，才能判断权限表的实际范围。

四类能力与权限边界

能力 需要检查的边界
读文件 模型直接读取工具，子进程可见目录
写文件 工作目录、临时目录和挂载点
访问网络 可连接目标、协议与代理路径
产生外部效果 凭据的作用域，远端允许的动作

权限模式是这些边界的起点。当前配置可能同时来自组织、用户和项目三级，须读取最终有效值，再解释实际生效范围。

命令规则只覆盖特定入口

拒绝某个删除命令的写法，只能挡住这一种工具请求。其他脚本同样可以执行删除，被允许的 shell 还可以组合命令。规则应按任务选择最小入口，再在进程层限制目录和网络。

只读资料任务优先使用只读执行环境。需要写入的任务只挂载专用的输出目录。高权限的发布凭据不应放入会读取外部资料的执行进程。

沙箱行为测试

macOS、Linux 与 Windows 的隔离机制和支持范围不同。当前 Agent 的默认模式也可能被组织配置覆盖。应先记录版本和生效配置，再测试读写、子进程与网络。

练习材料提供配置起点，具体字段按 Claude 权限、Claude 沙箱和 Codex 安全说明核对。配置解析成功之后，仍须进行行为测试。

在演示目录内为每条边界建一个用例，包含预期与实际结果。
直接工具和子进程分别尝试读取普通测试文件。
允许目录写入应成功，预定隔离目录写入应失败。
测试一个允许网络目标与一个未允许目标，记录实际行为。

测试只能说明这些路径在当前配置下的行为。新增工具、改变启动方式或更新版本后，应重测受影响的路径。

SSH 例外是另一项能力

把 SSH 放到本机沙箱之外，它就获得本机进程可用的连接能力；远端命令则受服务器账号控制。应尽量缩小远端账号权限，限定工作目录，并使用集群已有的调度与网络管理。

若一项任务只需查询作业状态，可以提供只返回固定字段的查询入口。允许任意远端 shell 的权限比查询状态宽得多，配置说明应明确记录这一选择。

按信息流组织角色

外部资料进入阅读角色，带来源的笔记进入分析角色，批准的产物进入发布角色。来源标记在传递中始终保留，发布操作须核对目标与授权。

摘要和结构化 JSON 同样可能包含不可信的要求。把资料格式整理得规范，并不改变其来源。权限须在执行端落实，模型的谨慎判断只是其中一层。

练习

从第 4 课选择一次收工过程，逐项列出其中的文件读写、网络与凭据。为每项动作找到最小可用入口。然后换一个入口运行同样的无害测试，记录在何处发生了权限扩张。

常见错误与处理方法

把两家的配置逐字段对译。 先写出所需能力，再分别实现，并实测同一语义。

名单只列域名，忽略外部工具例外。 把沙箱外命令和连接器分别列入能力表。

以本机目录隔离代替远端隔离。 远端账号与进程另做边界测试。

5.1 Permissions and sandboxes

Learning outcomes

After this section, students should be able to:

  1. Analyze the effective scope of a permission by tracing the capabilities it grants to subprocesses, networks and credentials, including configuration merged from several sources.
  2. Design behavioral tests that verify read, write, subprocess and network boundaries under the configuration actually in effect.
  3. Organize roles and their permissions along the information flow, treating exceptions such as SSH as separate capabilities with their own controls.

Extension reading and exercises, about 60 minutes.

Allowing uv run allows more than a single command: the script it starts can start other programs and can use the credentials in its environment. Assessing the actual scope of a permission table requires following these consequences.

Four capabilities and their boundaries

Capability Boundary to check
Reading files The model’s direct read tools, and the directories a subprocess can see
Writing files Working directory, temporary directories and mount points
Network access Reachable targets, protocols and proxy paths
External effects The scope of credentials, and the actions the remote side allows

The permission mode is the starting point for these boundaries. The current configuration may come from the organization, the user and the project simultaneously, so the final effective values are read before the scope actually in force is described.

Command rules cover only specific entry points

Denying one form of a delete command blocks that kind of tool request. Other scripts can still delete files, and an allowed shell can combine commands. Only the commands the task needs are allowed, and the process layer then limits directories and networks.

Tasks that only read source material should use a read-only execution environment where possible. For tasks that must write files, mount only a dedicated output directory with write access. High-privilege publishing credentials are not placed in an execution process that reads external material.

Testing the sandbox’s actual behavior

macOS, Linux and Windows differ in their isolation mechanisms and in what they support. A default mode of the current agent may also be overridden by organization configuration. Record the version and the effective configuration first, then test reads and writes, subprocesses and the network.

The exercise materials provide a configuration starting point; check specific fields against Claude permissions, the Claude sandbox and Codex security. A configuration that parses still requires behavioral tests.

In the demonstration directory, create one test case for each boundary, with the expected and actual results.
Try to read an ordinary test file with the direct tool and with a subprocess, separately.
Writing to an allowed directory should succeed; writing to the designated isolated directory should fail.
Test one allowed network target and one not allowed, and record the actual behavior.

Tests show only how these paths behave under the current configuration. When tools are added, the startup method changes or versions are updated, the affected paths are retested.

An SSH exception is a separate capability

When SSH is placed outside the local sandbox, it receives the connection ability available to local processes, and remote commands are then controlled by the server account. Minimize the remote account’s permissions, restrict the working directory, and use the cluster’s existing scheduling and network management.

If a task only needs to query job status, provide a query entry point that returns fixed fields only. Access to an arbitrary remote shell grants more capability than a status query, and the configuration notes should state this choice explicitly.

Organizing roles by information flow

External material goes to the reading role, notes with sources go to the analysis role, and approved products go to the publishing role. The source label accompanies every handover, and publishing checks the target and the authorization.

Summaries and structured JSON can also contain untrusted requests. Making material tidier does not change its source. Permissions are enforced at the executor; the model’s judgment, however careful, is only one layer.

Exercise

Choose one wrap-up step from Session 4 and list, item by item, the files it reads and writes, the network access it uses and the credentials it needs. Identify the smallest usable entry point for each action. Then run the same harmless test through another entry point and record where permissions expanded.

Common errors and corrections

Translating one vendor’s configuration into the other’s field by field. First state the capability required, then implement and test the required behavior separately in each.

An allowlist that names only domains and ignores exceptions for external tools. List commands outside the sandbox and connectors separately in the capability table.

Treating local directory isolation as remote isolation. Test the remote account and processes as a separate boundary.
