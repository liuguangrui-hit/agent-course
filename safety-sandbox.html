5.1 权限与沙箱

课后深入，约 30 分钟。

这一节把权限的几层讲清楚：对话里选的权限模式，配置文件里的规则，操作系统层面的沙箱。它们各管一段，缺一层就有一段没人管。

权限模式

Claude Code 的输入框旁可以选权限模式：

模式 改文件 运行命令 适合
Manual 问 问，只读的少数命令除外 第一次接触一个项目，想看清每一步
Accept edits 不问 问，允许表里的不问 日常写作和改代码
Plan 不改 只读的命令 先让它想清楚方案，不动手
跳过权限检查 不问 不问 只在本身隔离的环境里

Codex 有对应的设置：只读，可写工作目录，完全放行，另有何时向你请求批准的选项。

模式是粗调，规则是细调。日常用 Accept edits，再用规则把常用命令放行，危险命令拒绝，是最省心的组合。

规则的写法

规则写在项目的 .claude/settings.json 里：

{
  "permissions": {
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(sudo:*)",
      "Read(~/.ssh/**)"
    ],
    "allow": [
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(uv run:*)",
      "Bash(ssh lab:*)"
    ]
  }
}

拒绝优先于允许：同一条命令同时匹配两边，以拒绝为准。规则按前缀匹配，Bash(git push:*) 放行所有以 git push 开头的命令。前缀规则只认这一种写法：拒绝了 rm -rf，换个写法删除仍可能漏过去，所以拒绝表管住常见的危险写法，兜底靠沙箱。

写规则的顺序：先写拒绝表，想清楚什么事无论如何都不能做；再看这个项目实际用了哪些命令，挑天天用的写进允许表；剩下的保持询问。不要一开始就写一张大允许表。

规则可以放三个地方：用户目录下对所有项目生效；项目里的 .claude/settings.json 随项目走，可以提交进仓库；.claude/settings.local.json 只在你这台电脑上生效，不提交。项目特有的规则放项目里。

沙箱管什么

权限规则检查的是 Agent 要发起的那条命令。命令运行起来之后，它可能调用别的程序：一个 Python 脚本里读了你的密钥文件，一个安装脚本往系统目录里写了东西。这些规则看不到。

沙箱在操作系统层面把整条命令连同它调用的一切关起来：

  • 文件：只能写项目文件夹，系统临时目录，以及你另外加进来的目录；
  • 网络：只能直接连你列出的域名，名单外的会先停下来问你；设了严格名单就直接拒绝。
{
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "excludedCommands": ["ssh lab:*"],
    "network": { "allowedDomains": ["github.com", "arxiv.org", "api.openalex.org"] }
  }
}

allowUnsandboxedCommands 设成 false，命令被沙箱拦下后不能自己换到沙箱外重试。excludedCommands 列出整条在沙箱外运行的命令：ssh 不走网站名单，放进沙箱就连不上服务器；它到了服务器上做什么，本机的沙箱也管不到，所以服务器那头的权限另外管。字段随版本会有变化，让 Agent 按当前官方文档核对。

沙箱只管命令和它启动的程序；Claude 自己读写文件的工具不在沙箱里，归上面的权限规则管，所以两层都要配。沙箱支持 macOS、Linux 和 WSL2，Windows 上要在 WSL2 里运行 Claude Code 才有。开了沙箱后，沙箱内的命令可以少问几次，因为它即使出错也碰不到外面。

两家的对应

要做的事 Claude Code Codex
项目配置文件 .claude/settings.json .codex/config.toml
只让它想，不让它改 Plan 模式 只读沙箱，codex exec 的默认
只写项目文件夹 开沙箱 可写工作目录，交互使用时的默认
限制网络 沙箱的域名名单 沙箱默认不联网，按需打开

两家同时用时，让一家按另一家的配置写一份对应的，再让另一家检查是否一致。

无人值守时

夜里没人点同意，所以第 4 课的定时任务要么事先放行需要的命令，要么在更宽的模式下运行。后一种一定要配沙箱，并且写权限只给项目文件夹。一条实用的规矩：无人值守能用的权限，不超过你白天在 Accept edits 下放行的范围。

练习

把你的工作台按本节的顺序重新配一遍：先拒绝表，再看一周的运行日志写允许表，最后开沙箱。用第 4 课的收工流程跑一次，记下还有哪些命令被询问，决定它们是放行还是保持询问。

最容易出错的地方

一开始就写大允许表。 凭想象把能想到的命令全放行，其中就有不该放的。先拒绝表，再按实际用到的命令写允许表。

只有规则没有沙箱。 规则放行了 uv run，被运行的脚本里读了密钥文件，规则看不到。放手无人值守之前开沙箱。

照抄过期的配置。 配置字段随版本变化，网上抄来的配置可能已经不生效，你以为有保护其实没有。让 Agent 按当前官方文档写，写完实际测试一次被拒绝。

5.1 Permissions and sandbox

Self-study, about 30 minutes.

This section explains the layers of permissions: the mode you choose in a conversation, rules in configuration files, and the operating-system sandbox. Each governs a part. Leave out a layer and that part goes unguarded.

Permission modes

Claude Code lets you choose a permission mode beside the input box:

Mode File edits Commands Suited to
Manual Ask Ask, except a few read-only commands A first look at a project, seeing every step
Accept edits Don’t ask Ask, except allowed commands Daily writing and code changes
Plan No edits Read-only commands Thinking through a plan before acting
Skip permission checks Don’t ask Don’t ask Only in an isolated environment

Codex has corresponding settings: read-only, writable working directory, unrestricted, plus options for when to ask you for approval.

Modes make broad choices; rules refine them. Accept edits with rules allowing common commands and denying dangerous ones is the easiest daily setup.

Rule syntax

Rules go in the project’s .claude/settings.json:

{
  "permissions": {
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(sudo:*)",
      "Read(~/.ssh/**)"
    ],
    "allow": [
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(uv run:*)",
      "Bash(ssh lab:*)"
    ]
  }
}

Deny takes precedence over allow. A command matching both is denied. Rules match prefixes: Bash(git push:*) allows all commands starting with git push. A prefix rule recognizes only that form: denying rm -rf may miss deletion written another way. Use the deny list for common dangerous forms and the sandbox as the backstop.

Write the deny list first: what must never happen? Then look at commands this project actually uses and put everyday ones in the allow list. Leave the rest asking. Do not start with a large allow list.

Rules can live in three places: in your user directory for all projects; in .claude/settings.json to travel with the project and be committed; or in .claude/settings.local.json for this computer only, uncommitted. Project-specific rules belong in the project.

What the sandbox governs

Permission rules check the command the agent wants to start. Once running, it may call other programs: a Python script reads your key file, or an installer writes to a system directory. The rules do not see this.

The sandbox confines the command and everything it calls at the operating-system level:

  • Files: write only to the project folder, system temporary directories, and directories you add;
  • Network: connect directly only to listed domains; unlisted ones ask you first. A strict list refuses them outright.
{
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "excludedCommands": ["ssh lab:*"],
    "network": { "allowedDomains": ["github.com", "arxiv.org", "api.openalex.org"] }
  }
}

With allowUnsandboxedCommands false, a blocked command cannot retry outside the sandbox on its own. excludedCommands lists whole commands that run outside it. ssh does not use the website list and cannot reach the server inside the sandbox. The local sandbox cannot govern what ssh does on the server either; manage server-side permissions separately. Fields may change by version. Have the agent check current official documentation.

The sandbox governs only commands and programs they start. Claude’s own file-reading and writing tools are outside it and governed by permission rules, so configure both layers. The sandbox supports macOS, Linux and WSL2. On Windows, run Claude Code inside WSL2 to use it. Sandboxed commands can ask less often because even a mistake cannot touch what is outside.

Matching the two vendors

Aim Claude Code Codex
Project configuration .claude/settings.json .codex/config.toml
Think without editing Plan mode Read-only sandbox, the codex exec default
Write only to the project folder Enable sandbox Writable working directory, the interactive default
Limit network Sandbox domain list Sandbox has no network by default; enable as needed

When using both, have one write equivalent settings based on the other’s configuration, then have the other check consistency.

Unattended work

Nobody can approve prompts at night. Session 4’s scheduled tasks must either have needed commands allowed beforehand or use a broader mode. The latter needs a sandbox with writes limited to the project folder. A practical rule: unattended permissions should not exceed what you allow under Accept edits during the day.

Exercise

Reconfigure your workbench in this order: deny list, allow list based on a week’s run logs, then sandbox. Run Session 4’s wrap-up workflow once. Record commands that still ask, and decide whether to allow them or keep asking.

Where agents go wrong most

Starting with a large allow list. Allowing every command you can imagine includes ones you should not allow. Start with deny, then allow commands actually used.

Rules without a sandbox. Rules allow uv run, but the script reads a key file unseen by the rules. Enable the sandbox before unattended work.

Copying outdated configuration. Fields change by version. Copied settings may no longer work, leaving you with protection you only think you have. Have the agent use current official documentation and test an actual denial afterwards.
