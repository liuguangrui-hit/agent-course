4.1 定时调度与无人值守

学习目标

  1. 为一轮研究定义各阶段的转移依据与恢复动作，分析外部动作与状态写入之间的不一致窗口。
  2. 评价写锁与接管机制的保证范围，说明在何种条件下仍可能出现两个写入者。
  3. 为调度方式规定执行环境、预算、停止条件与交接方式，并通过手动触发和故障恢复加以验证。

课后深入专题，约 65 分钟。

课堂上已用 wake_review.py 完成一次短延迟唤醒，核对了主机与时区，并检查了只读审阅结果。本节把这一次运行扩展为可以暂停的周期运行。调度器只负责按时触发任务，并不保证上一轮已经结束，也不能判断一次失败的请求是否已经产生效果。长期运行因此还需要执行协议。

以状态转移定义一轮

当前阶段 转入下一阶段的依据 恢复动作
已选题 问题与预测已保存并冻结 核对文件身份，继续准备执行
已提交执行 有作业标识，执行端可查询 查相同标识，确认是否已运行
已运行 退出码和预期输出校验完成 重做校验，保留失败清单
已审阅 意见对应当前结果身份且有判定 稿件有变化就重新交审
已归档 页面与记账行都对应本轮 检查唯一键，补未完成输出

外部动作成功后，程序可能在写入状态前崩溃。提前写入状态同样有风险：状态显示完成，动作实际并未发生。外部系统以请求键识别同一动作，以状态查询确认结果。恢复时先按该键查询：已完成则推进状态，未发生才执行，仍无法确定则等待核查。

本地动作的恢复机制

包内的 recovery_demo.py 用原子文件替换模拟一项本地产物。它先检查预定运行编号对应的产物，内容匹配则复用，不存在才创建。状态写入失败后，下一次运行通过核对产物恢复。

准备动作及其身份
检查对应产物是否已存在
执行动作并校验效果
原子写入新状态
追加有唯一事件键的记录

日志记录每一次恢复尝试，效果文件始终对应同一个运行编号。

写锁与接管

原子创建目录可以保证两个同时开工的执行者中只有一个先获得锁。持有者写入 owner 和运行编号，释放前确认归属。新会话接管前，须核对旧会话、监视器与实际作业。

若采用租约，旧持有者在网络恢复后仍可能写入。需要在共享写入端验证递增的接管代号，拒绝旧代号的写入。示例中的目录锁不提供这一强保证，因此超时锁须人工核查，演示任务在同一台机器上串行恢复。

调度方式与执行环境

桌面定时便于查看运行情况，但要求相应应用和电脑处于可执行状态。服务器调度适合长期后台运行，环境变量和命令路径须显式设置。云端调度有独立的文件系统和连接权限，应先确认它能取得哪些材料。

为本循环提出一种调度方式，说明执行机器、时区和每次输入。
先列出具体时间表与工具授权范围，再做一次手动触发和失败恢复，确认日志和输出均可查看，并找到暂停与删除入口。
明确最大轮数、运行预算和何种状态停止，再建立长期调度。

Claude 的可用调度入口见官方定时说明，Codex 见官方文档。

无人值守调用的交接

每个任务给出一份自成一体的指令，输入与输出通过文件传递。只读审阅者读取指定版本，最终意见由调用端保存。调用的退出状态、会话标识与产物身份一并记录。

在自己的项目中，应使用所选 Agent 的官方非交互入口，并为执行器设置超时、权限与结果核查。

额度耗尽时记录为等待状态，按可确认的恢复时间继续。恢复时间未知则留空，不以反复重试来试探。接管时若旧会话仍会被唤醒，两边可能重复启动同一轮。因此应先停止旧会话的监视与唤醒，再由新会话接管。

练习

为循环选择两个故障点：启动已成功但回执丢失，结果页已生成但归档状态未更新。分别写出恢复查询与唯一键。演示一次，检查最终产物和所有失败尝试是否均可追溯。

常见错误与处理方法

到达设定时间即开始新一轮。 调度先检查当前状态，上一轮仍在执行时，查询状态或退出。

把失败重试写成无条件重复。 每个有副作用的动作都须有身份和核查方法。

直接删除过期锁。 确认持有者已经停止并记录接管，再让新执行者写入。

4.1 Scheduling and unattended runs

Learning outcomes

After this section, students should be able to:

  1. Define a research round by its state transitions, specifying for each the evidence required to advance and the recovery action after an interruption.
  2. Design recovery for actions with side effects using action identities and status queries, and assess the guarantees and limits of a given locking scheme.
  3. Select and configure a scheduler for a given execution environment, with run limits, stop conditions and a safe procedure for session takeover.

Extension reading and exercises, about 65 minutes.

In class, one short-delay wake-up was configured with wake_review.py, the host and time zone were checked, and the read-only review result was verified. This section extends that single run into a periodic run that can be paused. A scheduler wakes a task on time, but it does not guarantee that the previous round has finished, nor does it determine whether a failed request took effect. Long-running workflows therefore require an execution protocol in addition to a scheduler.

Defining a round by its state transitions

Current stage Basis for moving to the next stage Recovery action
Topic chosen Question and prediction saved and frozen Check file identity, continue preparing execution
Execution submitted A job identifier exists and the executor can be queried Query the same identifier to confirm whether it ran
Ran Exit code and expected outputs verified Repeat verification, keep the failure list
Reviewed Comments correspond to the current result identity and give a verdict If the draft changed, send it for review again
Archived Page and ledger rows both correspond to this round Check the unique key, complete unfinished outputs

After an external action succeeds, the process may crash before the state is written. Writing the state early is also risky: the state may report completion when the action never took place. External systems recognize the same action by a request key and confirm the result by a status query. Recovery first queries by this key: if the action is complete, the state advances; if it did not happen, it is executed; if the outcome is still unknown, the state waits for a check.

Recovering a local file action

The packaged recovery_demo.py simulates a local output file using atomic file replacement. It first checks the output for the intended run ID, reuses it if the content matches, and creates it only when none exists. If writing the state fails, the next run recovers by checking the output.

Prepare the action and its identity
Check whether the corresponding output already exists
Execute the action and verify its effect
Write the new state atomically
Append a record with a unique event key

The log records every recovery attempt, and the effect file always corresponds to the same run ID.

Write locks and session handover

Atomic directory creation ensures that only one of two processes starting simultaneously obtains the lock. The holder writes the owner and run ID, and confirms ownership before releasing it. Before a new session takes over, it checks the old session, the monitor and the actual job.

With a lease, the old holder may still write after its network connection returns. The shared write point must verify a monotonically increasing takeover token and reject stale tokens. The example directory lock does not provide this stronger guarantee, so a timed-out lock is checked manually, and the demonstration task recovers serially on a single machine.

Choosing a scheduler for the execution environment

Desktop scheduling makes runs easy to observe but requires the app and the computer to be able to run the task. Server scheduling suits long-term background work, but environment variables and command paths must be set explicitly. Cloud scheduling has its own file system and connection permissions, so first confirm which materials it can reach.

Propose one way of scheduling this loop, stating the executing machine, the time zone and the input for each run.
First list the concrete timetable and the scope of tool authorization, then do one manual trigger and one failure recovery, confirming the log, outputs, and the controls for pausing and deleting the schedule.
Set the maximum number of rounds, the run budget and which states cause a stop, and only then create the long-term schedule.

For Claude’s scheduling options, see the official guide to scheduled tasks; for Codex, see the official docs.

Handovers in unattended runs

Each task receives one self-contained instruction, with input and output through files. A read-only reviewer reads the specified version, and the caller saves the final comments. The call’s exit status, session identifier and product identity are recorded together.

In a student’s own project, use the official non-interactive interface of the chosen agent, and add a timeout, permissions and a result check to the executor.

Exhausted quota is recorded as a waiting state, and work resumes at a recovery time that can be confirmed. If the reset time is unknown, the field is left blank rather than inferred from repeated retries. During a takeover, if the old session can still be woken, both sessions may start the same round. The old session’s monitoring and wake-ups are therefore stopped before the new session takes over.

Exercise

Choose two failure points in the loop: a launch that succeeded but whose reply was lost, and a results page that was generated while the archive state was not updated. Write the recovery query and unique key for each. Demonstrate recovery once, and check that the final products and all failed attempts can be traced.

Common errors and corrections

Starting a new round because the scheduled time has arrived. The scheduler checks the current state first; if a run is still in progress, it queries or exits.

Implementing retries as unconditional repeats. Every action with side effects requires an identity and a means of checking it.

Deleting an expired lock directly. Confirm that the holder has stopped, record the takeover, and only then allow the new executor to write.
