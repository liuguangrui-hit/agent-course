4.1 定时调度与无人值守

课后深入，约 65 分钟。

课堂用 wake_review.py 接过一次短延迟唤醒，查了主机与时区，并核对只读审阅结果。现在把这一次扩成可暂停的周期运行。调度器按时触发任务，却不保证上一轮已经结束。它也不替你判断一次失败请求有没有产生效果。长期运行还需要执行协议。

从状态转移定义一轮

当前阶段 转入下一阶段的依据 恢复动作
已选题 问题与预测已保存并冻结 核对文件身份，继续准备执行
已提交执行 有作业标识，执行端可查询 查相同标识，确认是否已运行
已运行 退出码和预期输出校验完成 重做校验，保留失败清单
已审阅 意见对应当前结果身份且有判定 稿件有变化就重新交审
已归档 页面与记账行都对应本轮 检查唯一键，补未完成输出

外部动作成功后，状态写入前可能崩溃。写状态提前也有风险：状态显示完成，动作实际未发生。外部系统用请求键识别同一动作，用状态查询确认结果。恢复先按这个键查询：已完成就推进状态，未发生才执行，仍未知就等待核查。

本地动作的恢复机制

包内 recovery_demo.py 用原子文件替换模拟一项本地产物。它先检查预定运行编号的产物，内容匹配就复用；没有产物才创建。状态写入失败后，下一次通过产物核对恢复。

准备动作及其身份
检查对应产物是否已存在
执行动作并校验效果
原子写入新状态
追加有唯一事件键的记录

日志记录每次恢复尝试，效果文件始终对应同一个运行编号。

写锁与接管

原子建目录能让两个同时开工者只有一个先获得锁。持有者写入 owner 和运行编号，释放前确认归属。新会话接管前核对旧会话、监视器与实际作业。

如果采用租约，旧持有者在网络恢复后仍可能写入。需要在共享写入端验证递增的接管代号，拒绝旧代号。示例目录锁不提供这项强保证，因此超时锁人工核查，演示任务在同一台机器中串行恢复。

调度方式与执行环境

桌面定时便于查看运行，要求相应应用和电脑可执行任务。服务器调度适合长期后台，环境变量和命令路径需显式设置。云端调度有自己的文件系统和连接权限，先确认它能取得哪些材料。

为本循环提出一种调度方式，说明执行机器、时区和每次输入。
先列出具体时间表与工具授权范围，再做一次手动触发和失败恢复，确认日志和输出均可查看，并找到暂停与删除入口。
明确最大轮数、运行预算和何种状态停止，再建立长期调度。

Claude 的可用调度入口见官方定时说明，Codex 见官方文档。

无人值守调用的交接

一个任务给一份自成一体的指令，输入与输出通过文件。只读审阅者读取指定版本，最终意见由调用端保存。调用退出状态、会话标识与产物身份一并记录。

在自己的项目中，使用所选 Agent 的官方非交互入口，再给执行器加超时、权限与结果核查。

额度耗尽写成等待状态，按可确认的恢复时间继续。未知恢复时间留为空，不靠反复重试猜测。接管时若旧会话仍会被叫醒，两边就可能重复启动同一轮。因此先停止旧会话的监视与唤醒，再让新会话接管。

练习

给循环选两个故障点：启动已成功但回包丢失，结果页已生成但归档状态未更新。分别写出恢复查询与唯一键。演示一次，检查最终产物和所有失败尝试是否都能追溯。

常见错误与处理方法

时间到了就开始新轮次。 调度先看当前状态，仍在执行则查询或退出。

把失败重试写成无条件重复。 每个有副作用的动作都要有身份与核查办法。

过期锁直接删。 确认持有者已经停止，记录接管，再让新执行者写入。

4.1 Scheduling and unattended runs

After-class deep dive, about 65 minutes.

In class you connected one short-delay wake-up with wake_review.py, checked the host and time zone, and verified the read-only review result. Now extend that single run into a periodic run that can be paused. A scheduler wakes a task on time, but does not guarantee the previous round has finished. Nor does it judge for you whether a failed request had an effect. Long-running workflows need an execution protocol as well as a scheduler.

Define a round by its state transitions

Current stage Basis for moving to the next stage Recovery action
Topic chosen Question and prediction saved and frozen Check file identity, continue preparing execution
Execution submitted A job identifier exists and the executor can be queried Query the same identifier to confirm whether it ran
Ran Exit code and expected outputs verified Redo verification, keep the failure list
Reviewed Comments correspond to the current result identity and give a verdict If the draft changed, send it for review again
Archived Page and ledger rows both correspond to this round Check the unique key, fill in unfinished outputs

After an external action succeeds, the process may crash before the state is written. Writing the state early is risky too: the state says done but the action never happened. External systems recognize the same action by a request key and confirm the result by a status query. Recovery first queries by this key: if done, advance the state; if it did not happen, execute it; if still unknown, wait for a check.

Recovering a local file action

The packaged recovery_demo.py simulates a local output file with atomic file replacement. It first checks the output for the intended run ID, reusing it if the content matches and creating it only when there is none. If writing the state fails, the next run recovers by checking the output.

Prepare the action and its identity
Check whether the corresponding output already exists
Execute the action and verify its effect
Write the new state atomically
Append a record with a unique event key

The log records every recovery attempt, and the effect file always corresponds to the same run ID.

Write locks and session handoff

Creating a directory atomically lets only one of two processes starting simultaneously get the lock first. The holder writes the owner and run ID, and confirms ownership before releasing. Before a new session takes over, it checks the old session, the monitor and the actual job.

With a lease, the old holder may still write after its network comes back. The shared write point needs to verify a monotonically increasing takeover token and reject stale tokens. The example directory lock does not give this strong guarantee, so a timed-out lock is checked by hand, and the demonstration task recovers serially on one machine.

Choose a scheduler for the execution environment

Desktop scheduling makes runs easy to watch, but requires the app and the computer to be able to run the task. Server scheduling suits long-term background work, but environment variables and command paths must be set explicitly. Cloud scheduling has its own file system and connection permissions, so first confirm which materials it can reach.

Propose one way of scheduling this loop, stating the executing machine, the time zone and the input for each run.
First list the concrete timetable and the scope of tool authorization, then do one manual trigger and one failure recovery, confirming the log, outputs, and the controls for pausing and deleting the schedule.
Set the maximum number of rounds, the run budget and which states cause a stop, and only then create the long-term schedule.

For Claude’s available scheduling options, see the official guide to scheduled tasks; for Codex, see the official docs.

Handoffs for unattended runs

Each task gets one self-contained instruction, with input and output through files. A read-only reviewer reads the specified version, and the caller saves the final comments. The call’s exit status, session identifier and product identity are recorded together.

In your own project, use the official non-interactive interface of the agent you chose, then add a timeout, permissions and a result check to the executor.

Running out of quota is written as a waiting state, and work continues at a recovery time that can be confirmed. If the reset time is unknown, leave it blank rather than inferring it from repeated retries. During a takeover, if the old session can still be woken, both sides may start the same round. So first stop the old session’s monitoring and wake-ups, then let the new session take over.

Exercise

Choose two failure points in the loop: the launch succeeded but the reply was lost, and the results page was generated but the archive state was not updated. Write the recovery query and unique key for each. Demonstrate once, and check that the final products and all failed attempts can be traced.

Common mistakes and how to fix them

Starting a new round because the time has come. The scheduler looks at the current state first; if something is still running, it queries or exits.

Writing failure retries as unconditional repeats. Every action with side effects needs an identity and a way to check it.

Deleting an expired lock outright. Confirm the holder has stopped, record the takeover, then let the new executor write.
