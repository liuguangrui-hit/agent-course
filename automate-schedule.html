4.1 定时与无人值守

课后深入，约 30 分钟。

让 Agent 自己按时开工，有几种做法，区别在于在哪台机器上跑、电脑要不要开着。这一节先讲选哪种，再讲无人值守时最要紧的三件事：状态写在文件里，一件事只有一个对话在干，限定它能写哪里。

三种定时

做法 在哪跑 电脑要醒着吗 适合
桌面应用的定时任务 你的电脑 要，应用也要开着 刚开始，想在应用里看到每次运行
对话里的循环 你的电脑，一个开着的对话 要 几个小时内反复检查一件事
服务器上的 cron 加命令行版 服务器 不要 长期每晚运行

桌面应用的定时任务最省事。在 Claude 桌面版里直接说每晚十点按 LOOP.md 跑开工，它会建好；侧栏里能看到每次运行的记录，可以暂停和手动触发，详见定时任务文档。到点时电脑睡着或者应用没开，这一次就跳过。Codex 应用里也有类似的自动化。

对话里的循环，比如 Claude Code 的 /loop，适合今天下午每半小时看一次实验这种短期的事。它在同一个对话里反复运行，跑久了上下文会变长，不适合跑一周。

服务器上的 cron 最稳：服务器不关机，你的笔记本合上也不影响。cron 每晚调用一次命令行版的 Agent：

0 22 * * * cd ~/label-noise-lab && ~/.local/bin/claude -p "按 LOOP.md 跑开工" --permission-mode acceptEdits >> logs/loop.log 2>&1

cron 运行时没有你登录终端时的环境：命令要写完整路径，服务器上要先用同一个用户登录过一次 Claude，用到的命令要事先写进项目设置的允许表。装好后先手动执行一次这一行，确认能跑通，再交给 cron。

命令行版

claude -p 和 codex exec 让 Agent 不经对话框、在命令行里完成一件事，答案打印出来或者写进文件。第 4 课收工时用它请 Codex 审稿。审稿只读不写，codex exec 默认就是只读沙箱，意见由 -o 存成文件：

codex exec -o runs/7/review.md "读 runs/7/ 下的 prediction.md，results/ 和 result.md，按 review_task.md 审查。"

无人值守时没有人点同意，所以权限要事先给好，同时要收得紧：

  • 只给它这个项目文件夹和第 2 课知识库的写权限，其他地方只读；
  • 允许它运行的命令列清楚，比如 git，uv，ssh；
  • 不给它完全跳过权限检查的模式，除非整个运行环境本身是隔离的。

权限怎么配，第 5 课讲。

状态写在文件里

每次定时开工都是一个新对话，关于上一轮它只知道文件里写的。STATE.md 至少记这几样：

当前轮次：7
阶段：开工完成，实验运行中
正在干的对话：开工 2026-10-13 22:00，开始于 22:01
服务器 tmux 会话：lab-7
上一轮结论：带噪验证集早停晚 14 轮，见 runs/6/result.md
下一步：收工

每一步做完立刻写回。中途崩了，下一个对话从这里接上，而不是从头再来。

一件事只有一个对话在干

定时任务按时开工，不管上一个还在不在跑。先读 STATE.md 看进度还不够：两个对话可能同时读到没人在干，然后同时开工。要用一个只有一方能成功的动作来占位，建文件夹就是：

用 mkdir 建一个 .lock 文件夹，并在里面写上开工时间。建不成说明有别的对话在干：
锁的最近活动在 6 小时以内，直接退出，什么都不改；超过 6 小时，说明上一轮可能崩了，推一条通知给我，然后退出。
建成了再开始干。这把锁管整整一轮：开工结束不删，监视器盯实验时定时更新锁里的活动时间，第二天早上的收工核对是同一轮后接手，收工最后一步才删掉 .lock。

换人接手也是同样的道理：原来的对话先停掉它的监视器和定时唤醒，新的对话再接手。两个对话同时盯着同一件事，很容易一个覆盖另一个的结果。

额度

订阅有用量上限，常见的是几小时一个窗口加一周的总量。夜里跑到一半额度用完，命令行版会报错退出。三条办法：

  • 开工前先查额度，不够就把等待写进状态，推通知，退出；
  • 报额度错误时不要立刻重试，等到重置时间；
  • 有多个账号的，夜里的长任务用不常用的那个，白天交互用的账号留给你自己。

练习

把练习 2 的定时任务从桌面应用搬到服务器的 cron 上，用命令行版跑。合上笔记本过一夜，第二天看通知和结果页。

最容易出错的地方

用对话里的循环跑一周。 同一个对话反复醒来，上下文越积越长。长期任务用桌面定时任务或者 cron，每次新对话。

无人值守给了全部权限。 半夜没人看着，它在错误的文件夹里批量改了文件。写权限只给项目文件夹，命令列白名单。

状态只写在最后。 干到一半崩了，状态文件还是上一轮的，下一个对话从头重来，把实验又跑一遍。每一步做完立刻写回。

4.1 Scheduling and headless runs

Self-study, about 30 minutes.

There are several ways to have the agent start on time. They differ in where they run and whether your computer must stay awake. This section covers choosing one, then three essentials for unattended work: state in files, one conversation per task, and limits on where it can write.

Three ways to schedule

Method Where it runs Must your computer stay awake? Suited to
Desktop app scheduled tasks Your computer Yes, with the app open too Starting out, seeing each run in the app
A loop in a conversation Your computer, in an open conversation Yes Repeated checks over a few hours
Server cron with a command-line agent Server No Long-term nightly runs

Desktop app scheduled tasks are easiest. Tell Claude desktop to start work following LOOP.md at ten each night, and it creates the task. The sidebar shows runs and lets you pause or trigger it manually; see the scheduled task documentation. If the computer is asleep or the app is closed at the time, that run is skipped. Codex has similar automations.

Loops in conversations, such as Claude Code’s /loop, suit short jobs like checking an experiment every half hour this afternoon. They run repeatedly in the same conversation. Context grows over time, so they do not suit a week-long run.

Server cron is the most reliable. The server stays on and closing your laptop has no effect. cron calls the command-line agent once each night:

0 22 * * * cd ~/label-noise-lab && ~/.local/bin/claude -p "Follow LOOP.md to start work" --permission-mode acceptEdits >> logs/loop.log 2>&1

cron does not have the environment of your signed-in terminal. Use full command paths, sign in to Claude on the server once as the same user, and put needed commands in the project’s allow list beforehand. Try the command manually once before giving it to cron.

Command-line agents

claude -p and codex exec finish a task from the command line without a chat window. They print the answer or write it to files. Session 4 uses this to ask Codex for a review when wrapping up. Reviewing is read-only. codex exec defaults to a read-only sandbox, and -o saves its comments:

codex exec -o runs/7/review.md "Read prediction.md, results/ and result.md under runs/7/, and review them following review_task.md."

Nobody can click approval during an unattended run. Give permissions in advance, keeping them tight:

  • Allow writes only to this project folder and the Session 2 knowledge base; make other locations read-only;
  • List allowed commands explicitly, such as git, uv and ssh;
  • Do not use a mode that skips permission checks entirely unless the whole runtime is isolated.

Session 5 covers configuring permissions.

State lives in files

Each scheduled run is a new conversation. It knows about the last round only through files. STATE.md needs at least:

Current round: 7
Stage: startup complete, experiment running
Active conversation: startup 2026-10-13 22:00, began at 22:01
Server tmux session: lab-7
Last round's conclusion: noisy-validation early stopping was 14 epochs later; see runs/6/result.md
Next step: wrap up

Write back immediately after each step. If it crashes midway, the next conversation picks up here rather than starting over.

One conversation per task

A scheduled task starts on time whether the last one is still running or not. Reading STATE.md is not enough: two conversations may both read that nobody is working, then both start. Claim the task with an action only one can succeed at, such as creating a folder:

Use mkdir to create a .lock folder and write the start time inside it. If creation fails, another conversation is working:
if the lock's last activity is under 6 hours old, exit without changing anything; if over 6 hours old, the last round may have crashed. Send me a notification, then exit.
Start work only after creating the lock. The lock covers the whole round: kick-off does not delete it, the monitor refreshes its activity time while watching the experiment, and the next morning's wrap-up takes over the same round. Wrap-up deletes .lock as its very last step.

A handover follows the same rule: the old conversation stops its monitors and scheduled wake-ups before the new one takes over. Two conversations watching the same task can easily overwrite each other’s results.

Quotas

Subscriptions have usage limits, often a window of a few hours plus a weekly total. If quota runs out overnight, the command-line agent exits with an error. Three ways to handle it:

  • Check quota before starting. If insufficient, record the wait in the state file, notify, and exit;
  • Do not retry a quota error at once; wait for the reset time;
  • If you have several accounts, use a less-used one for long overnight work and leave your daytime account for you.

Exercise

Move Exercise 2’s scheduled tasks from the desktop app to server cron with the command-line agent. Close your laptop for the night and check notifications and the results page next morning.

Where agents go wrong most

Running a conversation loop for a week. The same conversation keeps waking and accumulating context. Use desktop scheduled tasks or cron for long jobs, with a new conversation each time.

Full permissions for unattended work. Nobody watches at midnight as it changes files in the wrong folder in bulk. Allow writes only in the project folder and list allowed commands.

Writing state only at the end. A crash midway leaves last round’s state. The next conversation starts over and reruns the experiment. Write back after every step.
