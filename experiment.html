3 Agent 实验

一小时后，你从第 2 课的三个问题里挑一个，先写下预测，再让 Agent 改代码、在服务器上把实验跑完。代码的每个版本都在 GitHub 上，结果文件注明是哪一版代码跑出来的，一页结果说明把预测和结果并排摆着，另一家 Agent 已经审过结论和数字对不对得上。

课堂核心 60 分钟。课后深入 3.1 至 3.3 共约一个半小时，按需选读。

下载第 3 课练习材料

练习材料是第 1 课的实验代码和数据，加上一份 questions.md，里面是一个现成的问题，没做完第 2 课也能直接开始：训练时拿出一部分同样带噪声的数据当验证集，按它早停，还能挡住网络记住错误标签吗。

开课先装工具，1 分钟发出去

本课暗线：让实验离开你的笔记本，并且每一步都留下版本。 到第 2 课为止，Agent 做的事都在你自己的电脑上，改了什么只能靠记。这一课添四样：Git 和 GitHub 给代码留版本，SSH 和 Tailscale 让它登录实验室的服务器，tmux 让实验在服务器上关了电脑也接着跑，监视器让 Agent 盯着日志、跑完再自己醒来。

在 Claude 里打开 lesson-3 文件夹，先发：

先读 ../lesson-2/AGENTS.md，把里面的工具用法抄进本文件夹的 AGENTS.md。
这个项目还要用 Git 管版本，推到我的 GitHub，并在服务器上跑实验。检查并补上：
1. git 和 GitHub 命令行工具 gh；需要我登录 GitHub 时停下来，告诉我在浏览器里点哪里；
2. 连服务器：我的服务器地址是 <地址>，用户名是 <用户名>。如果需要 Tailscale 才能连上，装好它并告诉我怎样登录；
   给这台电脑生成 SSH 密钥，告诉我怎样把公钥加到服务器上，然后在 ~/.ssh/config 里给服务器起个短名字，每次连接设上超时；
3. 服务器上有没有 tmux 和 uv，没有就装在我的用户目录下。
装之前列出打算装什么、装在哪，等我同意。装完各用一次：gh 查我的用户名，SSH 到服务器跑一次 nvidia-smi 或者 uptime；
再在服务器的 tmux 里跑一个 sleep 60 后写出 done 的小任务，设监视器盯着它，证明它结束时你会被叫醒。
最后在 AGENTS.md 里补几行：服务器短名字，实验在服务器上的目录，长任务一律放进 tmux。

没有服务器的，跳过第 2、3 项，实验和监视器测试都在本机后台跑，其余步骤一样。

先看成品，5 分钟

打开练习材料里的 preview/，这是按本课流程真跑出来的一份成品。prediction.md 写于写代码之前，四条预测，每条一个数字和推翻条件。result.md 把预测和结果并排摆着：四条错了三条。原以为验证集带噪声会让网络晚停几轮，准确率掉三个点；实际上它平均早停 2.6 轮，最终准确率 93.25%，和干净验证集的 92.26% 差别不明显，两者都把不早停时的 68.37% 拉了回来。错的预测比对的更有用：它说明带噪的验证集仍然看得出网络什么时候开始记错误标签。review.md 是审查意见，results/ 是全部原始结果和图。

预览是在一台机器上直接做的，没有建 Git 仓库，结果里的提交编号是占位值，审查也是同一家 Agent 做的。你在课上做的时候，这三处都按任务卡来：先提交，填真实编号，换另一家审。

讲，10 分钟

先写预测，再跑实验。 结果出来后再解释，总能讲通。实验前把预测写下来并提交到 Git，事后对照才有意义：猜对了，说明你对这个现象的理解是对的；猜错了，比猜对学到的更多。

每个结果对得上一版代码。 Agent 改代码很快，一下午改十几次，第三次跑出的好结果是哪一版代码，没人记得。规矩是跑之前先提交，结果文件里写上提交编号。

实验交给服务器，Agent 别守着。 长实验放进服务器上的 tmux 会话里，SSH 连接立刻断开，实验照跑。Agent 设一个监视器，几分钟看一次日志，跑完或者出错时再醒来，而不是开着连接一直等。

结论要另一个人审。 写结果的 Agent 和跑实验的是同一个，它想让结果好看。另一家的 Agent 只看预测、结果文件和结论，查三件事：数字对不对得上，结论有没有超出数字，结果对应的是不是那一版代码。

练习 1：上 GitHub，10 分钟

把这个文件夹建成 Git 仓库，写好 .gitignore：原始数据和大文件不进仓库；代码，文档和汇总后的小结果文件进仓库。
第一次提交后，用 gh 在我的 GitHub 上建一个私有仓库，名字叫 label-noise-lab，推上去，给我链接。
在 AGENTS.md 里补一条：每次跑实验前先提交，结果文件里写上当时的提交编号。

打开链接，在网页上看到自己的代码。

练习 2：先写预测，再到服务器上跑，25 分钟

读 questions.md 里的问题和 data/ 里第 1 课的结果。
先写 prediction.md：对 CE 损失在 40% 噪声下五个种子的均值，预测按带噪验证集早停停在第几轮，最终准确率是多少，和用干净验证集早停差多少。
每个预测给一个数字和一句理由，写明什么结果算预测错了。提交，提交说明写 prediction。
然后改 code/run_experiment.py，加上按验证集早停：验证集从训练集里切出 10%，标签带同样的噪声；另加一个用干净验证集的对照。
早停看验证集的交叉熵，连续 8 轮没有改善就停，恢复最好的那一轮的权重。加上 --seeds 和 --epochs 参数，结果写到 results/。
先在本机用 1 个种子，5 轮跑一次冒烟测试，确认能跑通、结果文件格式对，再提交。

冒烟测试过了，再交给服务器：

在服务器上 clone 这个仓库，用 uv 装好环境，在一个名为 lab 的 tmux 会话里跑完整实验，日志写到 logs/run.log。
启动后立刻返回，不要等它跑完。然后设一个监视器，每 5 分钟看一次日志的最后几行，跑完或者报错时告诉我。

没有服务器的，把第二段换成：在本机后台跑完整实验，日志写到 logs/run.log，设监视器。

实验跑的时候，你可以接着讲课，或者开个新对话做别的事。

练习 3：对照预测，请 Codex 审，10 分钟

监视器报告跑完后：

只把服务器上的 results/ 拉回来，不拉别的。画一张图：两种早停和不早停在各噪声水平下的最终准确率。
写 result.md：先把 prediction.md 的每条预测和实际结果并排列出，标明对还是错；
再写这个结果说明了什么，没说明什么，一段即可。写明结果对应的提交编号。
预测错了的条目，连同实际结果写进 ../lesson-2/vault/conflicts.md。提交并推到 GitHub。

在 Codex 里：

读 prediction.md，results/，result.md 和 Git 提交历史。检查三件事：
result.md 里的每个数字能否在 results/ 里找到；结论有没有说出数字支持不了的话；结果文件里的提交编号在历史里能否找到，那一版代码的设置和结果是否一致。
只给意见，写到 review.md，第一行注明你审的是哪个提交。除 review.md 外不改任何文件。

最容易出错的地方

SSH 卡住不返回。 在服务器上用一般的后台方式启动实验，SSH 连接有时会一直挂着等这个子进程，Agent 也跟着卡住。长任务一律放进 tmux，或者用完全脱离终端的方式启动，启动命令要立刻返回；每次 SSH 都设连接超时和心跳。

在电脑和服务器之间搬大文件。 数据集从你的电脑传到服务器，或者把整个结果目录拉回来，经过中转网络时又慢又可能把连接堵死。数据在服务器上直接下载，只把小的结果文件拉回来，稍大的先压缩。

按名字杀进程把自己杀了。 让 Agent 停掉一个实验，它用按命令名匹配的方式去杀，结果连自己这条 SSH 会话也匹配上，一起断了。停实验按进程编号，或者直接关掉那个 tmux 会话。

跑完再写预测。 看过结果再写的预测都是对的，也就什么都没检验。预测先提交，先后顺序在提交记录里一查便知。

好结果不怀疑。 坏结果大家都会查，好结果往往直接写进论文。好结果要同样怀疑：换一个种子，加一个本该没有效果的对照，看效果还在不在。很多漂亮的提升，加上对照后就消失了。

每隔几秒问一次跑完没有。 Agent 守着实验反复查看，每次查看都要重读整个对话，又慢又贵。设监视器，几分钟看一次，有事再醒。

在 AI 科学家里。 AI 科学家每跑一个实验之前，先把预测登记进假设森林，实验结果出来后自动对照。它的森林里只收自己实验验证过的东西，文献里的结论只能作为待检验的假设进来。本课先写预测再跑的做法，就是这条规矩的手动版。

换成你自己的实验

3 Experimenting with Agents

In an hour you will have chosen one of Session 2’s three questions, written a prediction, and had the agent change the code and finish the experiment on a server. Every code version is on GitHub. Result files name the code version that produced them. A page of results puts predictions beside outcomes, and another vendor’s agent has checked whether the conclusions match the numbers.

Core class: 60 minutes. Self-study sections 3.1 to 3.3 take about an hour and a half in total; read what you need.

Download the Session 3 materials

The materials contain Session 1’s experiment code and data, plus a questions.md with a ready-made question so you can start even without finishing Session 2: if you hold out some equally noisy training data for validation and use it for early stopping, can you still stop the network from memorizing wrong labels?

Install tools at the start: send the card in 1 minute

This session’s hidden thread: move experiments off your laptop and keep a version at every step. Through Session 2, all the agent’s work was on your own computer, and you had to remember what changed. This session adds four things: Git and GitHub to version code, SSH and Tailscale to log in to a lab server, tmux to keep experiments running after you shut your computer, and a monitor to watch logs and wake the agent when a run ends.

Open the lesson-3 folder in Claude and send:

First read ../lesson-2/AGENTS.md and copy its tool instructions into this folder's AGENTS.md.
This project also needs Git for versioning, pushes to my GitHub, and experiments on a server. Check and set up:
1. git and the GitHub CLI gh. When I need to sign in to GitHub, stop and tell me where to click in the browser;
2. Server access: my server address is <address>, username <username>. If access needs Tailscale, install it and tell me how to sign in;
   Generate an SSH key on this computer, tell me how to add the public key to the server, then give the server a short name in ~/.ssh/config and set timeouts for every connection;
3. tmux and uv on the server; if missing, install them under my user directory.
Before installing, list what you plan to install and where, and wait for my OK. Then try each: use gh to look up my username, and SSH to the server to run nvidia-smi or uptime.
Also run a small task in tmux on the server that does sleep 60 then writes done. Set a monitor to watch it and show that you wake when it ends.
Finally add a few lines to AGENTS.md: the server's short name, the experiment directory on the server, and that all long jobs go in tmux.

Without a server, skip items 2 and 3. Run the experiment and monitor test in the background locally. The other steps are the same.

See the finished product, 5 minutes

Open preview/ in the materials. This is a finished example actually run with this session’s workflow. prediction.md was written before the code, with four predictions, each giving a number and a condition that would refute it. result.md puts predictions beside results: three of four were wrong. The expectation was that noisy validation would delay stopping by a few epochs and cost three accuracy points. Instead it stopped 2.6 epochs earlier on average, with final accuracy of 93.25%, not clearly different from clean validation’s 92.26%. Both recovered from the 68.37% without early stopping. Wrong predictions are more useful than right ones: they show that noisy validation still reveals when the network starts memorizing wrong labels. review.md holds the review, and results/ has all raw results and figures.

The preview was made directly on one machine, without a Git repository. Its commit IDs are placeholders, and the same vendor’s agent reviewed it. In class, follow the task cards for these three parts: commit first, use real IDs, and have another vendor review.

Talk, 10 minutes

Write predictions before running. After results arrive, you can always find an explanation. Writing predictions first and committing them to Git makes the comparison meaningful. A correct prediction shows you understood the phenomenon. A wrong one teaches you more.

Every result matches a code version. Agents change code quickly, perhaps a dozen times in an afternoon. Nobody remembers which version produced the good result on run three. Commit before running and put the commit ID in the result file.

Give experiments to the server; don’t have the agent sit waiting. Put long experiments in a tmux session on the server. Disconnect SSH at once; the experiment keeps running. The agent sets a monitor to check the log every few minutes and wakes when the run ends or fails, rather than holding the connection open and waiting.

Have someone else review the conclusion. The agent writing the results also ran the experiment, and wants them to look good. Another vendor’s agent reads only the predictions, result files and conclusion. It checks three things: whether the numbers match, whether the conclusion goes beyond them, and whether the results match that code version.

Exercise 1: put it on GitHub, 10 minutes

Make this folder a Git repository and write .gitignore: keep raw data and large files out; include code, documents and small summarized result files.
After the first commit, use gh to create a private repository on my GitHub called label-noise-lab. Push to it and give me the link.
Add a rule to AGENTS.md: commit before each experiment and put that commit ID in the result files.

Open the link and see your code on the web.

Exercise 2: predict first, then run on the server, 25 minutes

Read the question in questions.md and Session 1's results in data/.
First write prediction.md: for CE loss at 40% noise, predict the five-seed mean of the stopping epoch, final accuracy, and differences from clean-validation early stopping when using a noisy validation set.
Give each prediction a number and a one-sentence reason. Say what result would make it wrong. Commit with the message prediction.
Then change code/run_experiment.py to add validation-based early stopping: hold out 10% of the training set for validation, with the same label noise. Add a clean-validation control too.
Use validation cross-entropy for early stopping: stop after 8 consecutive epochs without improvement and restore the best epoch's weights. Add --seeds and --epochs parameters and write results to results/.
Run a local smoke test with 1 seed and 5 epochs. Check that it runs and the result file format is right, then commit.

Once the smoke test passes, hand it to the server:

Clone this repository on the server, set up the environment with uv, and run the full experiment in a tmux session called lab. Write the log to logs/run.log.
Return as soon as it starts; don't wait for it to finish. Set a monitor to check the last few log lines every 5 minutes and tell me when it finishes or errors.

Without a server, replace the second card with: run the full experiment locally in the background, write the log to logs/run.log, and set a monitor.

While the experiment runs, continue the class or start a new conversation for something else.

Exercise 3: compare with predictions and ask Codex to review, 10 minutes

When the monitor reports completion:

Bring back only results/ from the server, nothing else. Draw one figure: final accuracy at each noise level for both early-stopping methods and no early stopping.
Write result.md: first put every prediction from prediction.md beside the actual result and mark it right or wrong.
Then give one paragraph on what this result shows and does not show. Name the commit ID that produced the results.
Add wrong predictions and their actual results to ../lesson-2/vault/conflicts.md. Commit and push to GitHub.

In Codex:

Read prediction.md, results/, result.md and the Git history. Check three things:
Can every number in result.md be found in results/? Do the conclusions say anything the numbers cannot support? Are the commit IDs in the result files in the history, and do that version's code settings match the results?
Give only comments. Write them to review.md, with the first line naming the commit you reviewed. Change no files except review.md.

Where agents go wrong most

SSH hangs instead of returning. Starting an experiment with ordinary backgrounding sometimes leaves SSH waiting for the child process, and the agent gets stuck too. Put all long jobs in tmux, or detach them fully from the terminal. The launch command must return at once. Set connection timeouts and keepalives for every SSH call.

Moving large files between computer and server. Uploading datasets from your computer or bringing back an entire results directory can be slow over a relay and may block the connection. Download data directly on the server. Bring back only small result files, compressing larger ones first.

Killing by name kills its own session. Asked to stop an experiment, the agent matches processes by command name and catches its own SSH session too. Stop by process ID or close that tmux session.

Predicting after the run. Predictions written after seeing results are always right and test nothing. Commit predictions first; the commit history shows the order.

Trusting good results. Everyone checks bad results; good ones often go straight into a paper. Question good results too. Change the seed and add a control that should have no effect. Does the effect remain? Many impressive gains disappear with a control.

Asking every few seconds whether it is done. The agent keeps checking the experiment, rereading the whole conversation each time. It is slow and expensive. Set a monitor to check every few minutes and wake only when something happens.

Inside the AI Scientist. Before each experiment, the AI Scientist records a prediction in its hypothesis forest, then compares it automatically with the result. The forest holds only things verified by its own experiments. Conclusions from papers enter only as hypotheses to test. This session’s predict-then-run method is the manual version of that rule.

The agent can now go from finding material to running experiments: ask a question, predict, run, write results, and have another vendor review. Next session connects these steps so they run while you sleep.

Now with your own experiment

Pick an experiment your group is doing that takes at most an hour per run. Have the agent read the code and write its understanding of the experiment for you to confirm. Then follow this session’s order: repository, prediction, smoke test, server run, comparison, another vendor’s review.
