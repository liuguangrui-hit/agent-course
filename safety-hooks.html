5.2 Hooks 与密钥管理

课后深入，约 60 分钟。

改完文件后的检查能告诉 Agent 数字错了，却撤不回已经发生的编辑。推送前的检查可以阻断发布，但前提是那次推送经过了这个入口。

事件与检查时机

时刻 作用 需要补的边界
编辑之后 快速发现格式或数字问题 命令行改文件是否也覆盖
工具调用之前 在指定入口阻断危险动作 其他工具是否能做相同动作
提交或发布入口 核查即将交付的完整产物 检查器故障时是否阻断
任务结束 核查未完成项与状态 会话崩溃后由谁接续

包内 hooks/check_tex.py 处理编辑事件，hooks/pre_push_secrets.sh 处理受支持的单分支推送。先读 README 的支持范围，再看测试，避免把一种入口的保护推到所有动作上。

分支测试与实际触发分开

先给脚本喂事件输入，确认成功，发现问题和内部失败的退出行为。再在 Agent 的真实配置里触发同一事件，检查脚本是否被调用，错误是否可见，预期阻断是否发生。

运行 code/test_hooks.py，保存分支验证结果。
接到自己的演示配置后，再用一个无害编辑和一次本地测试推送触发。
记录配置版本，事件名，脚本退出码与 Agent 实际反馈。
扫描器不可用或超时时，发布入口应失败关闭，不能跳过检查继续。

Hook 配置和事件字段随产品版本变化，当前格式查 Claude Hooks。Codex 的可用事件与接口查它自己的当前文档，分别测试。

交付入口的全量检查

单个编辑 Hook 用来快速反馈，发布入口再对冻结产物做全量检查。把受检文件哈希和结果保存，发布器确认将发布的就是这一版。

若 Agent 有权删除 Hook 或改核查器，保护强度也随之变化。需要更强边界时，把发布凭据和最终检查放到由另一权限主体维护的环境中。

进程与凭据访问

.gitignore 防止常规提交，不阻止程序读取；环境变量也会被子进程继承。一个能运行任意代码的 Agent，通常能借这些路径接触同一用户下的凭据。

按能力选存放方式：普通本地使用可以让工具从钥匙串读取；需要隔离时，把敏感调用交给受限服务，向任务提供短期、窄作用域的凭据。变量名留在文档，值不进对话与仓库。

凭据泄露后的处理

先在服务端吊销或轮换凭据，限制继续使用。再检查访问记录和影响范围，更新依赖它的配置，最后处理仓库历史与缓存副本。

历史清理不能召回已被复制的凭据。测试时用失效样例或扫描器替身，日志隐藏疑似值。误报应逐项核实并限定忽略范围，扫描器错误继续按失败处理。

练习

在一次性目录创建无效样例，验证扫描器会报问题且输出已脱敏。再模拟扫描器不在 PATH 中，检查发布是否被阻断。把这两种失败分别记在验证表里。

常见错误与处理方法

PostToolUse 能阻止已经完成的编辑。 把反馈与发布阻断分别设计，先后时刻写清。

扫描器崩溃被当成没有发现问题。 检查成功状态、退出码和报告完整性。

密钥从仓库挪进环境变量，就宣布 Agent 看不到。 检查实际进程与凭据能力，必要时隔离执行者。

继续读 gitleaks 官方说明，对照实际版本配置扫描范围。

5.2 Hooks and secret management

After-class deep dive, about 60 minutes.

A check after a file edit can tell the agent a number is wrong, but cannot undo the edit that already happened. A pre-push check can block publication, but only if that push went through this entry point.

Choose the right event for each check

Moment What it does Coverage to verify
After an edit Catches format or number problems quickly Are edits made from the command line covered too
Before a tool call Blocks dangerous actions at the specified entry Can other tools do the same action
Commit or publication entry Checks the complete product about to be delivered Does it block when the checker fails
End of the task Checks unfinished items and state Who picks up if the session crashes

The packaged hooks/check_tex.py handles edit events, and hooks/pre_push_secrets.sh handles supported single-branch pushes. First read the supported scope in the README, then look at the tests, so the protection of one entry point is not assumed to cover every action.

Test script branches and actual event handling separately

First feed event input to the script and confirm its exit behavior on success, on finding a problem and on internal failure. Then trigger the same event in the agent’s real configuration and check whether the script was called, whether errors are visible, and whether the action was blocked as expected.

Run code/test_hooks.py and save the branch verification results.
After connecting it to my own demonstration configuration, trigger it with one harmless edit and one local test push.
Record the configuration version, event name, script exit code and the agent's actual feedback.
When the scanner is unavailable or times out, the publication entry should fail closed and must not skip the check and carry on.

Hook configuration and event fields change with product versions; look up the current format in Claude Hooks. For Codex, look up its available events and interfaces in its own current docs, and test them separately.

The final check relies on the delivery entry point

A single edit Hook gives quick feedback; the publication entry then does a full check on the frozen product. Save the hashes of the checked files and the results, so the publisher can confirm that what it is about to publish is this version.

If the agent has permission to delete Hooks or change the checker, the strength of the protection changes with it. When you need a stronger boundary, put the publishing credentials and the final check in an environment maintained by a separate authority.

Process access to credentials

.gitignore prevents ordinary commits but does not stop programs from reading; environment variables are also inherited by subprocesses. An agent that can run arbitrary code can usually reach the credentials of the same user through these paths.

Choose storage by capability: for ordinary local use, a tool can read from the keychain; when isolation is needed, hand sensitive calls to a restricted service and give the task short-lived, narrowly scoped credentials. Variable names stay in the documentation; values stay out of conversations and repositories.

Responding to a credential leak

First revoke or rotate the credential on the server side, to stop further use. Then check access records and the extent of impact, update the configuration that depends on it, and finally deal with repository history and cached copies.

Cleaning history cannot recall credentials that have already been copied. Tests use invalid samples or scanner stand-ins, and logs hide suspected values. False positives are verified one by one with a limited ignore scope, and scanner errors are still treated as failures.

Exercise

Create an invalid sample in a disposable directory and verify that the scanner reports the problem and its output is masked. Then simulate the scanner not being on PATH and check whether publication is blocked. Record the two kinds of failure separately in the verification table.

Common mistakes and how to fix them

Believing PostToolUse can block an edit that has already been made. Design feedback and publication blocking separately, and state when each check runs.

A crashed scanner is taken as having found no problems. Check the success status, the exit code and the completeness of the report.

Declaring the agent cannot see a key because it moved from the repository to an environment variable. Check the actual process and credential capabilities, and isolate the executor where needed.

Further reading: official gitleaks documentation; configure the scan scope against the version you actually use.
