5.2 Hooks 与密钥管理

学习目标

  1. 依据事件时机分析各类 Hook 能够反馈或阻断的动作，以及仍需补充的边界。
  2. 分别验证 Hook 的脚本分支与实际触发，检验检查器故障时发布入口是否失败关闭。
  3. 依据进程和凭据的实际可达范围选择凭据存放方式，并制定泄露后的处置顺序。

课后深入专题，约 60 分钟。

文件编辑之后的检查能告诉 Agent 数字有误，却无法撤回已经发生的编辑。推送前的检查可以阻断发布，但前提是这次推送经过了该入口。

事件与检查时机

时刻 作用 需要补的边界
编辑之后 快速发现格式或数字问题 命令行改文件是否也覆盖
工具调用之前 在指定入口阻断危险动作 其他工具是否能做相同动作
提交或发布入口 核查即将交付的完整产物 检查器故障时是否阻断
任务结束 核查未完成项与状态 会话崩溃后由谁接续

包内的 hooks/check_tex.py 处理编辑事件，hooks/pre_push_secrets.sh 处理受支持的单分支推送。应先阅读 README 中的支持范围，再查看测试，避免把对某一入口的保护推广到所有动作。

分支测试与实际触发

先向脚本输入模拟事件，确认成功、发现问题和内部失败三种情况下的退出行为。再在 Agent 的真实配置中触发同一事件，检查脚本是否被调用、错误是否可见、预期的阻断是否发生。

运行 code/test_hooks.py，保存分支验证结果。
接到自己的演示配置后，再用一个无害编辑和一次本地测试推送触发。
记录配置版本，事件名，脚本退出码与 Agent 实际反馈。
扫描器不可用或超时时，发布入口应失败关闭，不能跳过检查继续。

Hook 的配置和事件字段随产品版本变化，当前格式见 Claude Hooks。Codex 的可用事件与接口以其当前文档为准，须分别测试。

交付入口的全量检查

单个编辑 Hook 用于快速反馈，发布入口再对冻结的产物做全量检查。保存受检文件的哈希和检查结果，发布器据此确认将要发布的就是这一版本。

若 Agent 有权删除 Hook 或修改核查器，保护强度也随之改变。需要更强的边界时，应把发布凭据和最终检查放到由另一权限主体维护的环境中。

进程与凭据访问

.gitignore 防止凭据被常规提交，但不阻止程序读取；环境变量也会被子进程继承。能运行任意代码的 Agent，通常可以借助这些路径接触同一用户下的凭据。

凭据的存放方式按所需能力选择：普通本地使用可以由工具从钥匙串读取；需要隔离时，把敏感调用交给受限服务，向任务提供短期、窄作用域的凭据。变量名可以写入文档，变量值不进入对话与仓库。

凭据泄露后的处置

首先在服务端吊销或轮换凭据，阻止继续使用。然后检查访问记录和影响范围，更新依赖该凭据的配置，最后处理仓库历史与缓存副本。

清理历史记录无法召回已被复制的凭据。测试时使用失效样例或扫描器替身，日志中隐藏疑似值。误报应逐项核实，并限定忽略范围；扫描器出错仍按失败处理。

练习

在一次性目录中创建无效样例，验证扫描器会报告问题且输出已经脱敏。再模拟扫描器不在 PATH 中的情形，检查发布是否被阻断。两种失败分别记入验证表。

常见错误与处理方法

认为 PostToolUse 能阻止已经完成的编辑。 反馈与发布阻断分别设计，写明各自的触发时刻。

扫描器崩溃被当作未发现问题。 检查成功状态、退出码和报告的完整性。

密钥从仓库移入环境变量，即宣布 Agent 无法读取。 检查实际进程与凭据的可达范围，必要时隔离执行者。

延伸阅读：gitleaks 官方说明，按实际版本配置扫描范围。

5.2 Hooks and secret management

Learning outcomes

After this section, students should be able to:

  1. Select the event at which a check should run according to what it must prevent or report, and identify the actions it does not cover.
  2. Verify a check at two levels, the script’s branch behavior and its handling in the agent’s real configuration, including failure of the checker itself.
  3. Assess which processes can reach a credential, choose storage and isolation accordingly, and specify the response to a credential leak.

Extension reading and exercises, about 60 minutes.

A check after a file edit can report that a number is wrong but cannot undo the edit that has already occurred. A pre-push check can block publication, but only if the push passes through that entry point. The value of a check therefore depends on when it runs and which actions pass through it.

Choosing the event for each check

Moment Function Coverage to verify
After an edit Detects format or number problems quickly Whether edits made from the command line are also covered
Before a tool call Blocks dangerous actions at the specified entry point Whether other tools can perform the same action
Commit or publication entry point Checks the complete product about to be delivered Whether it blocks when the checker fails
End of the task Checks unfinished items and state Who takes over if the session crashes

The packaged hooks/check_tex.py handles edit events, and hooks/pre_push_secrets.sh handles supported single-branch pushes. Read the supported scope in the README first, then the tests, so that protection at one entry point is not assumed to cover every action.

Testing script branches and actual event handling separately

First feed event input to the script and confirm its exit behavior on success, on detecting a problem and on internal failure. Then trigger the same event in the agent’s real configuration and check whether the script was called, whether errors are visible and whether the action was blocked as expected.

Run code/test_hooks.py and save the branch verification results.
After connecting it to my own demonstration configuration, trigger it with one harmless edit and one local test push.
Record the configuration version, event name, script exit code and the agent's actual feedback.
When the scanner is unavailable or times out, the publication entry should fail closed and must not skip the check and carry on.

Hook configuration and event fields change with product versions; consult the current format in Claude Hooks. For Codex, consult its own current documentation for available events and interfaces, and test them separately.

The final check depends on the delivery entry point

An edit Hook gives rapid feedback; the publication entry point then performs a full check on the frozen product. The hashes of the checked files and the results are saved, so that the publisher can confirm that what it is about to publish is this version.

If the agent has permission to delete Hooks or modify the checker, the strength of the protection changes accordingly. When a stronger boundary is required, the publishing credentials and the final check are placed in an environment maintained under separate authority.

Process access to credentials

.gitignore prevents ordinary commits but does not stop programs from reading files; environment variables are also inherited by subprocesses. An agent that can run arbitrary code can usually reach the credentials of the same user through these paths.

Storage is chosen according to capability: for ordinary local use, a tool can read from the keychain; when isolation is required, sensitive calls are delegated to a restricted service and the task receives short-lived, narrowly scoped credentials. Variable names appear in the documentation; values are kept out of conversations and repositories.

Responding to a credential leak

First revoke or rotate the credential on the server side to stop further use. Then examine access records and the extent of the impact, update dependent configuration, and finally deal with repository history and cached copies.

Cleaning history cannot recall credentials that have already been copied. Tests use invalid samples or scanner stand-ins, and logs mask suspected values. False positives are verified individually with a limited ignore scope, and scanner errors are still treated as failures.

Exercise

Create an invalid sample in a disposable directory and verify that the scanner reports the problem and masks its output. Then simulate the scanner being absent from PATH and check whether publication is blocked. Record the two kinds of failure separately in the verification table.

Common errors and corrections

Assuming that PostToolUse can block an edit that has already been made. Design feedback and publication blocking separately, and state when each check runs.

Interpreting a crashed scanner as having found no problems. Check the success status, the exit code and the completeness of the report.

Assuming the agent cannot see a key because it was moved from the repository to an environment variable. Check the actual process and credential capabilities, and isolate the executor where necessary.

Further reading: official gitleaks documentation; configure the scan scope for the version actually in use.
